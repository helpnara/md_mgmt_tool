# 사례 공유 — 혼자 쓰던 도구를 여러 사람이 동시에 읽게 만들기

> **팀 내 공유용** (2026-10-14). 「느린 나이테」(팀 과제 이력 관리 웹)를 팀장 한 명이 쓰던 1.0 에서,
> 팀원 여럿이 **동시에 읽는** 1.5 로 바꾼 하루의 기록이다. 무엇을 바꿨는지와 **무엇을 배웠는지**를 같이 적는다.
> 이 도구의 사례지만, **사내에서 혼자 만든 도구를 남에게 열 때** 누구나 부딪히는 일이라 묶어 둔다.
> 실측 숫자는 지어낸 자료(과제 204건 · 진행일지 약 1,000건)로 잰 것이며, 실제 과제 · 사람 · 금액은 들어 있지 않다.
> 자세한 경위는 [검토 기록](검토-다중접속-2026-10-13.md)과 [TODO 190~194](TODO.md) 에 있다.

## 0. 한 장 요약

**질문 하나에서 시작했다** — *"팀원들에게 읽기만 하는 형태로 공유하면, 10명 · 100명이 동시에 접속할 때 무슨 일이 생기나?"*

| | 전 (1.0) | 후 (1.5) |
|---|---|---|
| 혼자 쓸 때 첫 화면 | 0.04초 | 0.04초 (그대로) |
| **10명**이 동시에 첫 화면 | **6.9초** | **1.3초** |
| **50명** | **48초** | **0.7초** |
| **100명** | **시간 초과** (60초 넘김, 오류 340건) | **2.8초** (오류 0) |
| 50명이 읽는 동안 주인이 저장 | 최대 22초 | 1.1초 |
| 바깥에서 설정 변경 · 삭제 · 전체 백업 내려받기 | **모두 가능** (막는 것이 없었다) | 서버가 403 으로 막는다 |
| 켜는 법 | 명령 옵션을 알아야 했고, README 에 없었다 | `run.bat --share` 한 줄 |

세 문장으로 줄이면 —

1. **느려지는 것이지 틀려지지는 않았다.** 50명이 읽는 동안 고치고 다시 읽기를 걸어도 데이터는 끝까지 맞았다. 1.0 때 넣어 둔 "쓰기 줄 세우기 · 한 번에 커밋" 이 제 몫을 했다.
2. **느려지는 원인은 서버 사양이 아니라 코드였다.** 화면 하나가 SQL 1,164 문장을 보내고 있었고, 열 사람이 오면 같은 계산을 열 번 했다. 둘을 고치자 프로세스 하나로 100명을 받는다.
3. **"읽기만 공유" 는 아무것도 안 하면 "전부 공유" 다.** 서버가 "어디서 온 요청인가" 를 보고 막아야 한다. 단추를 숨기는 것은 편의이고, 막는 것은 서버다.

코드 56 파일 · 1,182줄 추가 · 하루. 혼자 쓰는 사람에게는 **달라진 것이 없다** — 바뀐 것은 전부 "여럿이 올 때" 와 "바깥에서 올 때" 만 작동한다.

## 1. 배경 — 왜 지금 이것을 했나

* 도구는 팀장 한 명의 PC 에서 돌고, 서버는 `127.0.0.1` 로만 듣는다. 그것이 유일한 울타리였고, 혼자 쓰는 동안은 충분했다.
* 확산 로드맵은 1.5(각자 설치) → 2(여러 팀장이 함께) → 2.5(팀원이 보기만) → 3(팀원까지 쓰기) 순서였다.
  그런데 **쓰기 권한은 나중에 주더라도 "보기만" 은 지금 열 수 있지 않나** 라는 질문이 나왔다 — 2.5 단계를 2 단계보다 먼저 가져오는 것이다.
* 전제 — 서버 PC 는 팀장 PC 한 대(켜 둔다), 네트워크는 보통 수준, 로그인은 없다.

**원칙을 먼저 정했다** — 읽기부터 고치고, 쓰기를 여는 일은 접수만 해서 2.0 으로 보낸다. 지금 하는 일이 혼자 쓰는 사람의 화면 · 동작을 바꾸면 안 된다.

## 2. 먼저 쟀다 — 고치기 전에

추측으로 고치지 않으려고 **부하 시험 도구를 먼저 만들었다** (`tests/load/loadtest.py`, 105줄).

* 사용자 한 명 = 첫 화면(HTML + JS + 메타 + 홈 + 대시보드 + 목록) 뒤에 상세 · 기록 · 보고대상 · 검색 · 로드맵 · 팀원역량 — 12 요청.
* N 명이 **같은 순간** 시작해 두 바퀴. 지연의 p50 · p95 · 최대, 오류 수, 그리고 **목록의 과제 수**(읽는 도중 숫자가 어긋나는지 감시).
* 변형 세 벌 — ① 지금 코드 ② 압축만 씌움 ③ 프로세스 4개. 그리고 ④ 50명이 읽는 동안 한 사람이 0.2초마다 고치기.

| 동시 사용자 | 홈 p95 | 과제목록 p95 | 가벼운 끝점(메타) p95 | 오류 |
|---|---|---|---|---|
| 1 (순차) | 38ms | 14ms | 6ms | — |
| 10 | 6.9초 | 2.4초 | 0.1초 | 0 |
| 50 | 48초 | 15초 | **21초** | 0 |
| 100 | 62초 | 42초 | 28초 | 340 (시간 초과) |

**재 보니 보인 것 셋.**

* 홈 한 번이 SQL **1,164 문장**이었다. 과제마다 담당자 · 유관부서 · 태그 · 선행 과제 · 기록 수를 따로 묻는 N+1. 혼자 쓸 때 38ms 라 전에 "대용량 확인 해소" 로 닫았던 것이다.
* **가벼운 요청까지 수십 초**였다. 자기 비용이 아니라 앞에 선 무거운 요청에 **밀려서**다. 스레드 풀(40)이 홈 · 대시보드 · 목록으로 차면 뒤는 줄을 선다.
* 같은 코드를 프로세스 4개로 돌리자 10명 p95 가 6.9초 → 0.27초, **26배**. 넷으로 나눴는데 넷보다 훨씬 빨라졌다는 것은 CPU 가 모자란 것이 아니라
  **한 프로세스 안에서 스레드들이 잠금(GIL)을 주고받는 비용**이 병목이라는 뜻이다. 그래서 "프로세스 늘리기" 가 아니라 **"문장 수 줄이기"** 를 먼저 하기로 했다 — 같은 효과를 프로세스 하나로 낼 수 있다.

쓰기를 섞은 시험(④)에서는 오류 0, `database is locked` 0, 과제 수는 처음부터 끝까지 204. **다만 주인이 저장 단추를 누르면 최대 22초를 기다렸다** — 쓰기가 읽기 뒤에 줄을 서기 때문이다.

## 3. 고친 것 — 네 묶음

### 3.1 읽기 성능 (TODO 190) — 세 단계, 매번 같은 자로 다시 쟀다

**① 묶음 질의.** 과제마다 다섯 번 묻던 것을 "목록의 과제 번호를 모아 다섯 번" 으로. 사람마다 마지막 보고일을 묻던 것은 `GROUP BY` 한 번으로.
"과제별 최근 3건" 은 창 함수(`ROW_NUMBER() OVER (PARTITION BY …)`) 한 문장으로.

| 끝점 | SQL 문장 수 전 | 후 |
|---|---|---|
| 홈 | 1,164 | 52 |
| 대시보드 | 968 | 20 |
| 과제목록 | 1,022 | 7 |
| 보고 후보 | 482 | 8 |

그런데 **10명 p95 가 6.9초 → 3.2초뿐**이었다. 문장을 20분의 1 로 줄였는데 절반이다. 첫 진단이 절반만 맞았던 것이다.

**② 답 나눠 쓰기(읽기 캐시) + 같은 요청은 한 번만.** 다시 재 보니, 열 사람이 같은 순간 같은 화면을 여는데 **같은 답을 열 번 계산**하고 있었다.
무거운 읽기(홈 · 대시보드 · 목록 · 후보 · 메타 · 로드맵 · 팀원역량 요약 · 접수 · 보고)의 답을 **5초 동안 같이 쓰고**, 같은 순간에 온 같은 요청은 **한 번만 계산**해 나눠 준다(single-flight).
규칙 하나가 중요하다 — **쓰기 요청이 하나라도 지나가면 전부 버린다.** DB 를 안 거치는 설정 저장도 포함. 그래서 "저장했는데 홈이 옛것" 은 없다.
캐시 열쇠에 "읽기 전용 여부" 를 넣어 바깥 사람의 답(면담 칸이 빈)이 주인의 답을 덮지 않게 했다.

**③ 줄 길이와 파일 크기.** 스레드 풀 40 → 64. 메타에 ETag(두 번째부터 304). 화면 JS 574KB 는 **빌드 때 미리 압축**해 181KB 로 보내고(요청마다 압축하지 않는다),
이름에 해시가 있는 파일은 1년 캐시 — 두 번째 방문부터 0바이트.

| 동시 사용자 | 홈 p95 전 | ① 묶음 질의만 | **① + ② 답 나눠 쓰기** | 오류 |
|---|---|---|---|---|
| 10 | 6.9초 | 3.2초 | **1.3초** | 0 |
| 50 | 48초 | 15초 | **0.7초** | 0 |
| 100 | 62초 | 37초 | **2.8초** | 0 |

주인의 저장은 22초 → 1.1초. 남은 것 하나 — 전체 다시 읽기(재색인 55초)가 도는 동안은 읽는 쪽도 함께 느려진다. 드문 일이라 그대로 두고 적어 두었다.

**다시 안 생기게 못 박은 것** — 끝점마다 **SQL 문장 수 상한을 시험으로**(`test_query_budget.py`: 과제 60건에서 홈 80 · 대시보드 40 · 목록 20 …). 다음에 누가 "과제마다 한 번 더 묻는 줄" 을 더하면 시험이 잡는다.

### 3.2 읽기 전용 공유 모드 (TODO 191) — 서버가 지킨다

바깥에 열기 전에 **무엇이 새는지 세었다.** 쓰기 끝점 53개(POST 32 · PUT 5 · PATCH 7 · DELETE 9) 전부, 그리고 읽기지만 보여서는 안 되는 것 —

| 끝점 | 무엇이 새나 |
|---|---|
| 폴더 목록 | **서버 PC 의 드라이브 · 폴더 구조** (백업 폴더 고르기용) |
| 전체 백업 | **자료 전체 zip** 을 한 번에 |
| 설정 · 명부 | 백업 경로 · 작성자 · 사번 칸 |
| 면담 기록 | 팀장 본인만 보기로 이미 정해 둔 것 |
| 오류 기록 · 휴지통 · 이전 버전 · 임시 보관 | 동작 꼬리, 지운 것, **남이 쓰다 만 글** |
| 메타의 폴더 경로 | 서버 PC 의 경로가 모든 화면 머리에 |

**설계 결정 셋.**

* **켜는 방법은 실행 옵션 하나** `run.bat --share`. 바깥(0.0.0.0)에 여는 것과 읽기 전용 규칙이 **같은 순간** 켜진다. 설정 화면의 토글은 "켜 놓고 잊는" 위험이 있어 피했다.
* **막는 기준은 "누구" 가 아니라 "어디서"** — 요청이 127.0.0.1 에서 왔으면 지금처럼 전부, 아니면 GET · HEAD 만. 로그인 · 사용자 개념 없이도 안전하다. 1.5 에서 "주인 PC 앞에 앉은 사람 = 쓰는 사람" 이 곧 권한이다.
* **규칙은 미들웨어 한 곳**(`share.py`, 91줄 + `main.py` 의 미들웨어 하나). 끝점 53개를 하나씩 고치지 않는다. 쓰기는 403, 민감한 읽기도 403, 면담은 **빈 목록**(있는지조차 안 보이게), 메타의 폴더 경로는 빈 값.

화면은 **편의로** 따라간다 — 메타가 읽기 전용이라고 하면 머리에 "읽기 전용" 띠, 설정 메뉴 · 작성자 안내 · 폴더 경로 없음, 쓰기 단추 숨김.
여기서 직전에 한 **단추 색 통일(TODO 189)** 이 뜻밖의 보상을 줬다 — 채운 단추 · 확정 · 보고 · 삭제에 갈래를 붙여 둔 덕에 "쓰기 단추" 가 곧 CSS 선택자 하나였다.
갈래 없는 흰 단추 37개만 손으로 표시(`data-write`)했다.

**시험** — 한 서버에 바깥 주소(10.0.0.2)와 안쪽(127.0.0.1) 클라이언트를 같이 붙여, 쓰기 · 민감 읽기 · 면담 · 메타 · 접속 기록을 확인(`test_share.py`).
화면 시험은 실제로 0.0.0.0 에 띄워 LAN 주소로 열고 여섯 화면에서 쓰기 단추 0개 · 서버가 403 · 127.0.0.1 은 그대로인지 본다.

### 3.3 켜기 · 운영 (TODO 192) — 켜는 사람이 알아야 할 것

* 켜면 창에 **공유 주소**(`http://<PC 이름>:8000` — IP 는 바뀌니 PC 이름으로)와 방화벽 안내. 화면 머리에 "공유 중 · 주소 · 오늘 N명" 칩, 설정 → 점검에 주소 · 오늘 접속 · 요청 수.
* README 에 "팀원에게 보여 주기" 절 — 윈도우 방화벽이 처음 묻는 창(허용), 회사 정책으로 막혀 있으면 IT 에 포트 하나, PC 를 켜 두어야 한다는 것.
* 공유 모드에서만 접속 기록(주소 · 시각 · 끝점 · 결과)을 하루 파일로. 누가 무엇을 봤는지는 적지 않는다 — "팀원이 실제로 보는가" 에 답할 숫자만.
* **결함 하나를 덤으로 찾았다** — "이미 켜져 있나" 검사가 듣는 주소(0.0.0.0)로 접속을 시도해, 윈도우에서는 늘 실패하고 두 번 뜨는 문제. 0.0.0.0 은 *듣는* 주소지 *가는* 주소가 아니다.
* 프로세스 늘리기(`--workers`)는 **쓰지 않기로** — 기동 재색인 · 자동 백업 루프 · 쓰기 줄 세우기가 프로세스마다 돌아 겹친다. 190 으로 프로세스 하나가 100명을 받으니 지금은 필요 없다.

### 3.4 떠난 사람 (TODO 194) — 공유하려니 보인 것

명부에 "떠난 날" 을 적어도 팀원역량 화면은 그 사람을 몰랐다 — "면담에서 먼저 볼 사람" 에 서고, 면담 상대 목록에도 있었다. 혼자 볼 때는 그러려니 했지만 **팀원이 보는 화면**이 되자 고쳐야 했다.
떠난 사람은 표 맨 아래에 흐리게, 이름 옆에 사유 딱지, 먼저 볼 사람 · 면담 상대에서 뺀다. 기록 수 · 마지막 활동 · 지난 면담은 사실이라 그대로 둔다.

## 4. 혼자 쓰는 사람에게 달라진 것

**없다.** 그것이 목표였고, 체크리스트 A 묶음("혼자 쓸 때 그대로")으로 확인했다. 알아 둘 것 둘 —

* 공유는 `run.bat --share` 로 켤 때만. 평소 `run.bat` 은 전과 같다.
* 공유를 켠 PC 에서 **PC 이름 주소로 열면 거기서도 읽기 전용**이었다(쓰려면 127.0.0.1) — "어디서" 로 막는 방식의 자연스러운 결과였는데, 다음 묶음(TODO 206)에서 서버 PC 의 자기 주소도 주인으로 넣어 없앴다.

| 1 | **성능은 "혼자서 몇 ms" 가 아니라 "동시 10명에서 p95" 로 잰다** | 순차로 재어 8ms · 11ms 를 보고 "대용량 확인 해소" 로 닫았다. 한 요청이 SQL 1,164 문장이라는 것은 순차로는 안 보인다. 동시에 열 명이 오자 180배 | 남에게 열기 전에 **동시 부하 시험을 먼저** 만든다. 끝점의 **SQL 문장 수**를 시험으로 묶어 둔다 |
| 2 | **한 단계 고치고 같은 자로 다시 잰다 — 첫 진단은 절반만 맞는다** | N+1 을 20분의 1 로 줄였는데 지연은 절반. 두 번째 병목(같은 계산을 열 번)은 첫 측정에 숨어 있었다 | 고치기 → 재기 → 다음 병목, 을 멈출 때까지. 진단 하나로 끝까지 가지 않는다 |
| 3 | **"프로세스를 늘리자" 는 마지막 지렛대다** | 프로세스 4개로 26배가 났지만, 그것은 코드 안 잠금 비용이 크다는 증거였다. 늘리면 기동 재색인 · 백업 루프 · 쓰기 잠금이 겹친다 | 먼저 한 요청의 일을 줄인다. 늘리는 것은 "한 프로세스만 할 일" 을 분리한 뒤에 |
| 4 | **읽기 공유의 모양은 "많은 사람이 같은 순간 같은 화면"** | 열 명이 홈을 열면 답은 하나인데 열 번 계산했다 | 답을 잠깐 나눠 쓰고(쓰기가 지나가면 버린다), 같은 순간의 같은 요청은 한 번만 계산한다. 이것이 N+1 보다 큰 지렛대였다 |
| 5 | **캐시는 "언제 버리나" 가 전부다** | DB 를 안 거치는 설정 저장을 빠뜨리면 "저장했는데 옛것" 이 된다 | 버리는 규칙은 단순하게 — **쓰기 요청이 하나라도 지나가면 전부**. 열쇠에는 "누가 보는 답인가" 를 넣는다 |
| 6 | **"읽기만 공유" 는 아무것도 안 하면 "전부 공유" 다** | 127.0.0.1 이 유일한 울타리였다. 열면 폴더 목록 · 전체 백업 · 설정 · 남이 쓰다 만 글까지 다 보였다 | 열기 전에 **쓰기 끝점을 세고, 읽기 중 새는 것을 표로** 만든다. 숨기는 것은 편의, 막는 것은 서버 — 둘 다 |
| 7 | **막는 기준을 "누구" 가 아니라 "어디서" 로 두면 로그인 없이 안전하다** | 사용자 개념 · 권한은 2.0 의 일이다. 1.5 는 그것 없이 가야 했다 | 단계에 맞는 가장 단순한 울타리를 고른다. 다음 단계의 재료를 미리 만들지 않는다 |
| 8 | **여는 것과 막는 것은 한 스위치로** | 옵션 둘(`--host 0.0.0.0` 과 읽기 전용)이 따로면 "열렸는데 안 막힌" 날이 온다 | `--share` 하나. 설정 토글은 "켜 놓고 잊는" 쪽이라 피했다 |
| 9 | **앞서 한 통일 작업이 다음 일을 공짜로 만든다** | 단추 색을 갈래로 통일(189)해 둔 덕에 "쓰기 단추 숨김" 이 CSS 한 줄이 됐다 | 화면 요소에 **뜻을 붙이는 작업**(갈래 · 속성)은 당장 쓸모가 작아 보여도 한다 |
| 10 | **시험 환경에서 "안쪽" 과 "바깥" 을 한 서버에 같이 붙인다** | 막는 규칙은 둘을 나란히 놓아야 "하나는 통과, 하나는 403" 이 확인된다 | 화면 시험도 실제로 0.0.0.0 에 띄워 LAN 주소로 연다. 127.0.0.1 로만 시험하면 규칙이 한 번도 안 돈다 |
| 11 | **남에게 보이는 화면이 되면 "그러려니" 하던 것이 결함이 된다** | 떠난 사람이 "먼저 볼 사람" 에 서던 것(194) | 공유 직전에 **팀원의 눈으로 화면을 한 바퀴** 돈다 |
| 12 | **0.0.0.0 은 듣는 주소지 가는 주소가 아니다** | "이미 켜져 있나" 검사가 0.0.0.0 으로 접속해 윈도우에서 늘 실패 → 두 번 떴다 | 접속 검사 · 브라우저 열기는 늘 127.0.0.1 로 |

작업 과정에서의 실수도 둘 적어 둔다 — ① 시험 중 프로세스를 이름 패턴으로 죽이다 내 작업 셸까지 두 번 죽였다(PID 파일로만 죽인다).
② 배포본에 홍보 영상 · 블로그 그림이 딸려 들어가 14MB 가 21MB 가 됐다(`export-ignore` 로 뺀다). 둘 다 [회고](LESSONS-LEARNED.md) 8절의 "내 손으로 낸 사고" 에 더했다.

| 로그인 · 사용자 · 팀 권한 | "어디서" 로 충분했다. 만들어 놓고 안 쓰면 통째로 버린다 | 2.0 — "팀원도 쓰게 하자" 신호에 (TODO 193) |
| 프로세스 늘리기 | 프로세스 하나로 100명. 늘리려면 한 프로세스만 할 일을 먼저 분리 | 100명이 같은 순간 첫 화면을 여는 일이 실제로 잦을 때 |
| 재색인 중 느려짐 | 55초 · 드문 일 · 끝나면 돌아온다 | 자주 걸리면 재색인을 잘게 |
| 면담 기록 보이기 | 팀장 본인만 보기로 정한 것 | 따로 결정할 때 |

**다음 질문은 코드가 아니다** — *팀원이 실제로 보는가.* 설정 → 점검의 "오늘 접속 N명" 이 그 답이다. 보면 2.0 은 자연스럽고, 안 보면 2.0 은 만들 이유가 없다.

## 7. 다른 도구를 열 때의 점검표

혼자 만든 도구를 남에게 열기 **전날** 쓰는 것이다.

- [ ] 동시 사용자 10 · 50 · 100 으로 **부하 시험**을 만들어 p95 를 잰다 — 순차 측정은 세지 않는다
- [ ] 무거운 화면의 **SQL 문장 수**를 센다. 100 을 넘으면 N+1 이다
- [ ] 쓰기 끝점을 **센다**. 읽기 중 **새는 것**(폴더 · 백업 · 설정 · 남의 임시 글 · 경로)을 표로
- [ ] 막는 규칙은 **서버 한 곳**에. 화면의 숨김은 그 다음
- [ ] 여는 것과 막는 것을 **한 스위치**로
- [ ] 시험에 "안쪽" 과 "바깥" 클라이언트를 **같이** 붙인다
- [ ] 켜는 사람을 위한 안내 — 주소(PC 이름) · 방화벽 · PC 를 켜 둘 것
- [ ] 혼자 쓰는 사람에게 **달라진 것이 없는지** 체크리스트로 확인한다
- [ ] "실제로 보는가" 를 셀 숫자 하나를 남긴다
