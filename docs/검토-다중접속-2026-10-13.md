# 검토 — 여러 사람이 동시에 읽을 때 (2026-10-13)

> 그날의 **검토 기록**이다. 반영된 것은 TODO 190~193 에, 결정과 구현은 거기에 쌓인다. 이 문서는 고쳐 쓰지 않고 각주만 붙인다.

**질문** (사용자, 2026-10-13) — *"팀원들에게 지금 사이트를 수정 권한은 나중에 준다고 생각하고, 단순 공유용 형태로 공유한다고 하면 동시에 여러
사람이 접속할 때 생길 수 있는 다양한 이슈를 검토해 줘. 혼자 쓸 때는 특이사항이 없지만 사용자가 10명, 100명으로 넘어간다면 … 읽기부터
보완하고 수정은 나중에 할 일도 남겨 두자. 서버 사양과 네트워크는 안정적이라고 가정. 1.0 이었다면 1.5, 2.0 으로 가기 위한 준비."*

**전제** — 팀장 PC(또는 사내 PC 한 대)에서 지금 도구를 켜 두고, 팀원들은 브라우저로 **읽기만** 한다. 서버 사양 · 네트워크는 보통 수준.
확산 로드맵의 **1.5 단계와 2.5 단계(팀원이 보기만) 사이**에 해당한다.

## 0. 한 장 요약

| | 지금(1.0) | 10명이 동시에 열면 | 100명이면 |
|---|---|---|---|
| 첫 화면(홈) | 0.04초 | **6.9초** (p95) | **시간 초과**(60초 넘김) |
| 과제목록 | 0.014초 | 2.4초 | 42초 |
| 과제 상세 · 기록 | 0.004초 | 0.06초 | 수 초 ~ 수십 초(앞 요청에 밀려) |
| 처음 받는 화면 파일(JS) | 574KB | 574KB × 10 | 574KB × 100 — 가장 늦은 사람 51초 |
| 오류 · 어긋난 숫자 | 없음 | 없음 | 시간 초과만 — 데이터는 끝까지 맞았다 |

세 가지로 요약된다.

1. **느려지는 것이지 틀려지지는 않는다.** 50명이 읽는 동안 한 사람이 0.2초마다 고치고 중간에 전체 다시 읽기를 걸어도 `database is locked` 는
   한 번도 없었고, 목록의 과제 수는 처음부터 끝까지 204건으로 같았다. 요청마다 커넥션 · 쓰기 줄 세우기 · 한 번에 커밋(TODO 64 · 8.1)이 제 몫을 했다.
2. **느려지는 원인은 서버 사양이 아니라 질의 수다.** 홈 한 번이 SQL **1,164 문장**, 대시보드 968, 과제목록 1,022 — 과제마다 담당자 · 태그 · 선행 과제 ·
   기록 수를 따로 묻는 N+1 이다. 혼자 쓸 때는 38ms 라 안 보이지만, 열 사람이 동시에 들어오면 스레드 열 개가 작은 문장 만 개를 놓고
   파이썬 인터프리터 잠금(GIL)을 주고받느라 **180배**로 늘어난다. 같은 코드를 프로세스 넷으로 돌리자 10명 p95 가 **6.9초 → 0.27초(26배)** 가 됐다 — CPU 가 모자란 것이 아니라 **한 프로세스 안의 잠금 주고받기**가 병목이라는 증거다.
3. **읽기만 공유해도 "읽기만" 이 아니다.** 지금은 누구나 설정을 바꾸고 · 지우고 · 전체 백업을 내려받고 · 서버 PC 의 폴더 목록을 보고 · 면담 기록을 읽을 수
   있다. 막는 것이 없다. 공유를 켜는 순간 **쓰기 53개 끝점과 민감한 읽기 끝점 열 몇 개**를 서버가 막아야 한다.

**추천 순서** — 190(읽기 성능) → 191(읽기 전용 공유 모드) → 192(켜는 법 · 운영) 을 1.5 로 한 묶음, 193(쓰기를 여는 준비)은 2.0 으로 접수만.

## 1. 어떻게 쟀나

* **자료** — 지어낸 팀(팀원 8 · 과제 204 · 진행일지 ~1,000 · 보고 23). T23 에서 재던 규모와 같다.
* **사용자 한 명** = 첫 화면(index.html + JS + meta + 홈 + 대시보드 + 과제목록) 뒤에 과제 상세 · 기록 · 보고대상 · 검색 · 로드맵 · 팀원역량 — 12 요청.
  N 명이 **같은 순간** 시작해 두 바퀴. 지연의 p50 · p95 · 최대, 오류, 목록의 과제 수(어긋남 감시).
* **세 벌** — ① 지금 코드 그대로(프로세스 1) ② 같은 코드에 GZip 만 바깥에서 씌움 ③ 같은 코드, 프로세스 4개(`--workers 4`).
* **쓰기 섞기** — 50명이 읽는 동안 한 사람이 0.2초마다 과제를 고치고(PATCH), 다섯 번째에 전체 다시 읽기(POST /api/reindex).
* 이 컨테이너의 CPU 에서 쟀다. 절대값은 PC 마다 다르지만 **배수와 모양**은 같다.

|---|---|---|

### 2.4 프로세스 4개 (`--workers 4`, 코드 그대로)

| 동시 사용자 | 프로세스 1 (홈 p95 / 전체) | 프로세스 4 (홈 p95 / 전체) | 오류 |
|---|---|---|---|
| 10 | 6.9초 / 32초 | **0.27초 / 2.3초** | 0 |
| 50 | 48초 / 153초 | **1.4초 / 14초** | 0 |
| 100 | 62초 / 310초 | **3.3초 / 24초** | 2 (연결 끊김 1 · 4xx 1) |

코드 한 줄 안 바꾸고 **14~26배**. 넷으로 나눴는데 넷보다 훨씬 많이 빨라진 것은 **프로세스 하나 안에서 스레드들이 잠금(GIL)을 주고받는 비용**이 CPU 일
자체보다 컸다는 뜻이다 — 즉 3.1 의 N+1(문장 수)을 줄이면 프로세스 하나로도 같은 효과가 난다. 그래서 순서는 **N+1 먼저, 프로세스 늘리기는 그다음**.

프로세스를 늘리려면 먼저 풀어야 할 것 셋(지금 코드로는 겹친다): ① 기동 재색인이 프로세스마다 돌았다(로그에 "과제 204건을 읽었습니다" 넷 — 운 좋게 안 겹쳤을 뿐)
② 자동 백업 루프가 넷 ③ 쓰기 줄 세우기(`_write_lock`)가 프로세스 안의 잠금이라 **넷이 동시에 쓸 수 있다**. 읽기 전용 공유에서는 ③ 이 문제 되지 않지만
①② 는 "한 프로세스만" 으로 바꿔야 한다.

## 3. 읽기 성능 — 무엇이 느린가, 어떻게 고치나 (→ TODO 190)

### 3.1 N+1

과제목록 한 줄을 그릴 때 `_serialize` 가 과제마다 **담당자 · 유관부서 · 태그 · 선행 과제 · 기록 수** 를 따로 묻는다(5 문장 × 204 = 1,020).
홈의 팀원별 표는 사람마다 마지막 보고일을 따로 묻고, 대시보드는 담당자별 수를 사람마다 센다. 혼자 쓸 때 8~38ms 라 T23 에서 "해소" 로 적었다 —
**순차로 재면 안 보이는 비용**이다.

| 고칠 곳 | 지금 | 뒤 |
|---|---|---|
| 과제목록 `_serialize` | 과제마다 5 질의 | 목록의 과제 번호를 모아 `WHERE project_id IN (…)` 다섯 번 → 과제별로 나눠 붙인다 |
| 홈 `_members` | 사람마다 마지막 보고일 | `GROUP BY po.name` 한 번 |
| 대시보드 `_owner_counts` | 사람마다 | 한 번의 GROUP BY |
| `stage_map` · `_predecessors_of` | 이미 한 번에 — 그대로 | |

기대: 홈 · 목록 · 대시보드가 **1,000 문장 → 10 문장 안쪽**, 혼자 쓸 때 38ms → 5ms 안팎, 10명에서 6.9초 → 0.2초 안팎(GIL 주고받기가 100분의 1).
**시험으로 못 박는다** — 끝점마다 SQL 문장 수 상한을 재는 백엔드 시험(`set_trace_callback`) 한 벌. 다음에 누가 과제마다 묻는 줄을 더하면 그 시험이 잡는다.

### 3.2 가벼운 요청이 무거운 요청 뒤에 서지 않게

* 스레드 풀 기본 40 → **64~96**(설정으로). 100명이 동시에 첫 화면을 열 때 줄의 길이가 반으로.
* `/api/meta` 는 사람 목록 · 연도 · 설정을 한 번에 들고 온다(5KB) — 그대로 두되 **ETag** 를 붙여 두 번째부터는 304.

### 3.3 화면 파일

* JS 574KB → 빌드 때 `.gz`(184KB) · `.br` 를 함께 내고, 있으면 그것을 보낸다(즉석 압축 없음).
* `/assets/` 는 이름에 해시가 있으니 `Cache-Control: max-age=1년` — 두 번째 방문부터 0바이트.

### 3.4 100명 이상이라면

읽기 성능만 고쳐도 **단일 프로세스로 수십 명**은 편하게 받는다. 100명이 같은 순간 첫 화면을 여는 일은 드물지만(회의 시작), 그때를 위해 프로세스를
늘리는 길은 **2.4 의 조건**을 먼저 풀어야 한다 — 기동 재색인 · 백업 루프 · 쓰기 줄 세우기가 프로세스마다 돌아 겹친다.

## 4. 읽기 전용으로 공유한다는 것 — 막아야 할 것 (→ TODO 191)

지금 서버에는 **"누가 보내는가" 를 보는 곳이 없다.** 127.0.0.1 에서만 열린다는 것이 유일한 울타리였다. 공유를 켜면 그 울타리가 사라진다.

### 4.1 쓰기 — 53개 끝점

POST 32 · PUT 5 · PATCH 7 · DELETE 9. 과제 만들기 · 고치기 · 지우기 · 보고 확정 · 설정 바꾸기 · 번호 다시 매기기 · 다시 읽기 · 백업 실행 · 접수 판정 ·
면담 쓰기 · 임시 보관 저장 … 전부. 읽는 사람의 브라우저에서도 단추가 그대로 보이고 눌린다.

### 4.2 읽기지만 보여 주면 안 되는 것

| 끝점 | 무엇이 새나 |
|---|---|
| `GET /api/folders` | **서버 PC 의 드라이브 · 폴더 목록**(백업 폴더 고르기용) — 파일 탐색기를 열어 주는 셈 |
| `GET /api/backup` | **vault 전체 zip** — 모든 과제 · 첨부 · 면담을 한 번에 |
| `GET /api/settings` · `/backup/status` | 백업 폴더 경로 · 작성자 · 명부(사번 칸) · 서식 |
| `GET /api/meetings` · 팀원역량의 면담 칸 | **면담 기록** — 182 에서 "팀장 본인만" 으로 정했다 |
| `GET /api/errors` · `/api/trash` · `/api/versions/*` · `/api/drafts/*` · `/api/linkfix` | 오류 기록(동작 꼬리) · 지운 것 · 이전 버전 · **남이 쓰다 만 글** · 깨진 링크 |
| `GET /api/meta` 의 `vault` | 서버 PC 의 폴더 경로가 모든 화면 머리에 |
| `GET /files/…` · 첨부 미리보기 | 첨부 그대로 — 읽기 공유의 범위 안이지만 **면담 폴더는 없는지** 확인(지금 첨부는 과제 폴더 안에만 — 괜찮다) |

### 4.3 제안 — "공유 모드" 는 서버가 지킨다

* **실행 옵션 하나** `run.bat --share` (또는 설정 → 공유): 바깥(0.0.0.0)에 열면서 **같은 순간에** 읽기 전용 규칙이 켜진다. 둘이 따로 켜지지 않게.
* 규칙은 **미들웨어 한 곳**에 — 요청이 127.0.0.1 에서 왔으면 지금처럼 전부, 아니면:
  * GET · HEAD 만 통과. 나머지는 **403 "읽기 전용으로 공유 중입니다"**.
  * 4.2 의 끝점은 GET 이어도 403(또는 빈 결과 — 면담은 **빈 목록**으로, 있는지조차 안 보이게).
  * `meta.vault` 는 빈 값, `meta.readonly = true`.
* 화면 — `meta.readonly` 면 머리에 **"읽기 전용"** 띠, 쓰기 단추(저장 · 추가 · 삭제 · 확정 · 설정 메뉴 · 임시 보관)는 **숨긴다**(189 에서 갈래를 붙여 둔 단추가
  바로 그 목록이다). 숨기는 것은 편의, 막는 것은 서버 — 둘 다 한다.
* 임시 보관(170) — 읽는 사람이 편집기를 열고 타자하면 0.7초 뒤 PUT 을 보내는데, 403 이 돼도 화면은 조용하다(`unsaved.ts` 가 실패를 삼킨다 — 확인함). 읽기 전용에선 편집기 자체를 안 연다.
* **주인 PC 의 브라우저는 지금 그대로** — 127.0.0.1 로 들어오므로 쓰기가 열려 있다. 1.5 에서 "쓰는 사람 = 주인 PC 앞에 앉은 사람" 이 곧 권한이다.

### 4.4 1.5 에서 **하지 않는 것**

로그인 · 사용자 개념 · 팀 권한. 2단계(로드맵-확산단계 3.3 의 1~4)로 보낸다. 읽기 전용은 그것 없이도 안전하다 — 막는 기준이 "누구" 가 아니라 "어디서" 라서.
