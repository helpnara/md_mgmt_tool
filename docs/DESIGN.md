## 1. 배경과 문제 정의

현재 팀의 과제별 수행 이력을 Obsidian 등 외부 클라우드 기반 마크다운 도구로 관리하고 있으나 다음 한계가 있다.

| 문제 | 영향 |
|---|---|
| 파일 첨부가 사실상 불가 | 실험 데이터(xlsx), 보고서 초안(docx/pptx), 참고 논문(PDF)을 별도 위치에 보관 → 이력과 자료가 분리됨 |
| 이미지 첨부/붙여넣기 불편 | 스크린샷 기반 기록(계측 화면, 그래프)이 누락되거나 외부 링크로 관리됨 |
| 과제 단위 관리 정보 부재 | 상태·마감일·분류를 문서 본문에 수기로 적어야 하고 목록에서 한눈에 안 보임 |
| 이력 취합 어려움 | 보고 시점에 과제 전체 이력을 하나로 묶어 내보내기 곤란 |
| 보고 이력이 남지 않음 | 매주 전체가 아니라 2–3개 과제만 보고하는데, **어느 과제를 언제 마지막으로 보고했는지** 추적되지 않아 보고 시점을 감으로 판단하게 됨 |
| 보고 당시 문서를 다시 못 봄 | 보고에 쓴 정리 문서(엑셀)가 이력과 분리 보관되어, 나중에 "그때 뭐라고 보고했는지" 확인이 어려움 |

**목표**: 마크다운의 가벼움과 이식성은 유지하면서, 첨부 파일·이미지를 이력과 같은 자리에 붙이고, 과제 단위로 진행 상황을 조회·검색·내보내기 할 수 있는 웹 기반 도구를 만든다.
아울러 **보고 이력과 보고 당시 문서를 과제에 함께 남겨**, 매주 어느 과제를 보고할지 근거를 가지고 고를 수 있게 한다.

## 2. 확정된 전제 조건

| 항목 | 결정 |
|---|---|
| 실행 환경 | **로컬 우선** (localhost 단독 실행), 이후 사내 서버 확장 가능하도록 구조만 미리 확보 |
| 데이터 위치 | 프로젝트 **로컬 하위 폴더 `./vault/`** (설정으로 변경 가능, git 추적 제외) |
| 기존 문서 이관 | **하지 않음.** 새 구조에 맞춰 과제별로 새로 작성 → 마이그레이션 도구 대신 **과제/일지 템플릿**에 투자 |
| 첨부 용량 | **상한 없음.** 대신 대용량 업로드 시 **진행률 표시**와 스트리밍 저장 필수 |
| 저장 방식 | **파일시스템(.md + 첨부) + SQLite 메타/인덱스 DB** |
| 사용 범위 | **1인 사용** (인증 없음, 동시 편집 충돌 처리 불필요) |
| 기술 스택 | **Python / FastAPI + SQLite** |
| 문서 구조 | 과제 1건 = **개요 문서 1개 + 날짜별 진행일지 N개**, 단 **전체를 하나의 긴 md로 다운로드** 가능해야 함 |
| 첨부 유형 | 이미지 붙여넣기(스크린샷), 오피스 문서(xlsx/docx/pptx), PDF/논문 자료 |
| 과제 목록 표시 정보 | 상태 / 기간·마감일 / 분류 태그·과제 그룹 / 최근 업데이트 일시 |
| 보고 이력 | 과제별 **보고 이력**과 **보고 당시 문서**를 함께 보관. 현재는 **날짜만** 기록하고 유형·피보고자는 추후 확장 |
| 보고 자료 형태 | **엑셀(xlsx)** 로 보고. 본문은 텍스트, 필요 시 이미지 포함 |
| 보고 대상 선정 기준 | **마지막 보고 후 경과 기간** + **보고 이후 쌓인 새 진행 분량** |
| 과제 상태 | 예정 / 검토중 / 진행중 / 보류 / 완료 / 중단 (진행 단계만) |
| 과제 속성 | 스마트과제 / R&D / 투자 / 기획보고 / 국책과제 (과제당 하나) |
| 과제 그룹 | 지금은 **단일 값**. 연도·팀명 등 체계가 생기면 계층으로 확장 (4.6) |
| 과제 담당자 | **한 명부터 여러 명까지** 지정. 담당자별 필터 제공 |
| 보고 리듬 | **주간 업무 보고** — 기준 주기 7일. **월요일에 보고 항목 선정 → 화요일 보고** |
| 보고 엑셀 양식 | 셀 한 칸에 여러 줄 텍스트를 넣는 형식. **줄바꿈이 살아 있는 평문**만 잘 전달되면 충분 |
| 저장 방식 | 수동 저장 + 브라우저 초안 복구. **자동 저장 토글**을 두고, 켜면 입력이 멈춘 뒤 **10초** 후 저장 |
| 첨부 파일명 | `001-원본명.xlsx` — 순번 접두사 + 원본 파일명 |
| 편집기 | 단순 텍스트 편집 + 실시간 미리보기 유지 (문법 강조·위지윅은 도입하지 않음) |
| 사용 환경 | **윈도우 + Python**. Node.js 없이 실행되도록 프론트엔드 빌드 결과를 저장소에 포함 |

## 3. 설계 원칙

1. **마크다운 파일이 진실의 원천(Source of Truth)이다.**
   DB는 검색·필터를 위한 파생 인덱스일 뿐이며 언제든 파일에서 전부 재생성할 수 있어야 한다. 도구를 쓰지 않게 되더라도 데이터는 폴더 째로 남는다.
2. **첨부는 문서 위치 기준 상대 경로로 저장한다.**
   진행일지는 `logs/` 안에 있으므로 링크는 `![](../assets/2026-09-01/screenshot-01.png)`, 보고 문서는 자기 폴더의 자료를 `![](assets/001-…)` 로 가리킨다. 이렇게 해야 Obsidian·VS Code·GitHub 등 어떤 마크다운 뷰어에서도 이미지가 그대로 보인다. (해시 기반 중앙 저장소 방식은 이식성을 잃으므로 채택하지 않음 — 5.3 참조)
   > 구현 중 발견: 처음에는 링크를 과제 폴더 기준(`assets/…`)으로 적었는데, 이러면 웹앱에서만 열리고 외부 뷰어에서는 `logs/assets/…` 를 찾아 깨진다. 이식성이 핵심 가치이므로 문서 위치 기준으로 정정했다.
3. **로컬 단독이지만 서버 확장을 막지 않는다.**
   저장소 접근은 storage 계층 뒤로 감추고, 인증이 들어갈 자리(의존성 주입 지점)만 비워 둔다. 지금은 구현하지 않는다.
4. **외부 편집과 공존한다.**
   사용자가 Obsidian이나 편집기로 같은 폴더를 직접 수정할 수 있다고 가정하고, 파일 변경 감지 → 재인덱싱 경로를 항상 유지한다.
5. **보고 스냅샷은 불변이다.**
   보고는 "그 시점에 무엇을 보고했는가"라는 사실 기록이므로, 확정된 보고 문서는 이후 진행일지가 바뀌어도 함께 바뀌지 않는다. 진행 이력(계속 자라는 것)과 보고 기록(그 시점에 고정되는 것)을 별도 폴더로 분리한 이유다.

## 4. 데이터 구조

### 4.1 디렉터리 레이아웃 (Vault)

```
vault/                                  # 데이터 루트 (설정으로 위치 변경 가능)
├── projects/
│   ├── 2026-001-리튬전지-수명평가/
│   │   ├── index.md                    # 과제 개요 (메타데이터는 front matter)
│   │   ├── logs/
│   │   │   ├── 2026-09-01-실험셋업.md
│   │   │   ├── 2026-09-03-1차측정결과.md
│   │   │   └── 2026-09-10-중간보고.md
│   │   ├── reports/                    # 보고 이력 (보고 시점에 고정된 스냅샷)
│   │   │   └── 2026-09-05/
│   │   │       ├── report.md           # 보고 당시 정리된 문서 (읽기 전용)
│   │   │       └── assets/
│   │   │           ├── 001-주간보고.xlsx    # 실제 보고에 사용한 원본 파일
│   │   │           └── 002-보고화면.png
│   │   └── assets/
│   │       ├── 2026-09-03/
│   │       │   ├── 001-측정그래프.png
│   │       │   └── 002-raw-data.xlsx
│   │       └── 2026-09-10/
│   │           └── 001-중간보고초안.pptx
│   └── 2026-002-.../
├── .trash/                             # 삭제 항목 보관 (즉시 삭제하지 않음)
└── .index/
    └── index.sqlite3                   # 파생 인덱스 (삭제해도 재생성됨)
```

* 폴더명 = `{연도}-{일련번호}-{슬러그}`. 사람이 파일 탐색기에서 봐도 정렬·식별이 되도록 한다.
* **이름이 바뀌면 폴더·파일도 따라간다.** 과제명을 고치면 과제 폴더가, 진행일지의 제목·날짜를 고치면 그 md 파일명이 새 이름으로 바뀐다. 화면에서 보는 이름과 탐색기에서 보는 이름이 갈라지지 않게 하기 위함이다.
  * 이름을 바꿔도 **기록의 정체성은 유지**된다 (내부 id를 그대로 들고 이동하므로 열려 있던 화면이 그대로 이어진다).
  * 이미 보고에 담긴 진행일지의 이름을 바꾸면 보고 문서가 가리키는 경로도 함께 고친다. 그러지 않으면 이미 보고한 내용이 '미보고'로 되살아난다. 보고 문서의 **내용**은 건드리지 않는다.
  * 첨부는 날짜 폴더(`assets/<날짜>/`) 기준이라 이름 변경과 무관하게 그대로 유효하다.
* 과제 ID는 폴더명 접두사(`2026-001`)로 고정하고, 제목이 바뀌어도 슬러그만 변경한다.
* 진행일지 파일명 = `YYYY-MM-DD-슬러그.md`. 같은 날 여러 건이면 `YYYY-MM-DD-2-슬러그.md`.

### 4.2 과제 개요 문서 (`index.md`)

```markdown
---
id: 2026-001
title: 리튬전지 수명평가
status: in_progress        # 7단계 — 4.6 참조
group: 차세대전지          # 과제 그룹 (단일)
tags: [수명평가, 셀설계]    # 분류 태그 (복수)
owners: [권경락, 홍길동]     # 한 명부터 여러 명까지
start_date: 2026-03-02
due_date: 2026-12-20
created_at: 2026-03-02T09:12:00+09:00
updated_at: 2026-09-01T14:03:00+09:00
---

## 과제 개요
(배경, 목표, 산출물 등 고정 정보)

## 관련 링크
```

### 4.3 진행일지 (`logs/YYYY-MM-DD-*.md`)

```markdown
---
date: 2026-09-03
title: 1차 측정 결과
tags: [측정]
attachments:
  - assets/2026-09-03/001-측정그래프.png
  - assets/2026-09-03/002-raw-data.xlsx
---

오늘 셀 3종에 대해 1차 측정을 진행함.

![측정그래프](assets/2026-09-03/001-측정그래프.png)

원시 데이터: [raw-data.xlsx](assets/2026-09-03/002-raw-data.xlsx)
```

> `attachments` front matter는 본문에서 참조되지 않는 첨부(순수 자료 보관)도 추적하기 위한 목록이다. 본문에 삽입된 첨부는 인덱싱 시 자동으로 여기에 병합된다.

### 4.4 보고 문서 (`reports/YYYY-MM-DD/report.md`)

보고 시점에 **고정(freeze)** 되는 스냅샷이다. 확정된 뒤에는 도구 UI에서 읽기 전용으로 열리며, 이후 진행일지를 수정해도 이 문서는 바뀌지 않는다. "그때 무엇을 어떻게 보고했는가"가 그대로 남는 것이 목적이다.

```markdown
---
report_date: 2026-09-05
title: 2026-09-05 보고
covers_from: 2026-08-22        # 이 보고가 포함한 진행일지 기간
covers_to: 2026-09-05
covered_entries:               # 이 보고에 반영된 진행일지 (미보고 분량 계산의 기준)
  - logs/2026-08-25-셀조립.md
  - logs/2026-09-03-1차측정결과.md
attachments:
  - assets/001-주간보고.xlsx
frozen_at: 2026-09-05T17:40:00+09:00
# 아래는 예약 필드 — 지금은 비워 두고 필요해질 때 UI에 노출
report_type:                   # weekly | monthly | ad_hoc | interim | final
audience:                      # 팀회의 / 부서장 / 고객사 …
---

## 보고 요약
- 셀 3종 조립 완료, 1차 수명 측정 착수
- 초기 용량 유지율 A안 98.2% / B안 95.7%

## 특이사항 및 이슈
...

## 다음 계획
...
```

* `report.md` 본문은 **마지막 보고 이후의 진행일지에서 자동 생성한 초안**을 사용자가 다듬은 결과다 (5.6).
* 실제 보고에 사용한 **엑셀 파일 원본**은 `reports/<날짜>/assets/`에 함께 보관되어 언제든 같은 화면에서 열린다.

### 4.5 과제 상태와 속성 — 서로 다른 두 축

처음에는 `기획보고 / 제안 / 검토 / 진행중 / …` 을 한 줄로 세웠는데, 실제로 써 보니 **기획보고는 과제의 성격이지 진행 단계가 아니다.** 상태로 두면 그 과제는 영영 '완료'가 될 수 없다. 그래서 두 축으로 나눴다.

**진행 상태 (`status`)** — 얼마나 진행됐는가. 과제는 결국 완료·중단 중 하나로 끝난다.

| 순서 | 키 | 라벨 | 보고 후보 포함 |
|---|---|---|---|
| 1 | `planned` | 예정 | ○ |
| 2 | `reviewing` | 검토중 | ○ |
| 3 | `in_progress` | 진행중 | ○ |
| 4 | `on_hold` | 보류 | ✕ (토글로 포함) |
| 5 | `done` | 완료 | ✕ |
| 6 | `dropped` | 중단 | ✕ |

**과제 속성 (`type`)** — 어떤 성격의 과제인가. 과제당 **하나만** 지정하며, 시간이 지나도 잘 바뀌지 않는다.

| 키 | 라벨 |
|---|---|
| `smart` | 스마트과제 |
| `rnd` | R&D |
| `investment` | 투자 |
| `plan_report` | 기획보고 |
| `national` | 국책과제 |

* 보드의 칸은 **상태**를 따른다. 속성은 카드·목록에 배지로 표시하고 필터로 거른다.
* 상태·속성 목록은 `config.py` 상수 한 곳에서 관리한다.
* **예전 값 자동 변환**: 상태에 `기획보고`가 들어 있던 과제는 읽는 시점에 `상태=예정 + 속성=기획보고` 로, `제안`은 `예정`, `검토`는 `검토중`으로 옮긴다. 파일을 손댈 필요가 없다.

### 4.6 과제 그룹 — 지금은 단일 값, 나중에 계층

현재는 `group: 차세대전지` 처럼 **문자열 하나**다. 입력 시 기존 값 자동완성만 제공한다.

나중에 연도·팀명 같은 체계가 생길 것을 대비해 다음 두 가지만 미리 지킨다.

1. **구분자 예약** — 값에 `/`를 쓰면 곧 계층으로 해석할 수 있게 한다 (`2026/소재팀/차세대전지`). 지금은 단순 문자열로 저장·표시만 하고 분해하지 않는다.
2. **별도 컬럼 유지** — 그룹을 태그에 섞지 않고 `project.grp` 컬럼으로 분리해 둔다. 계층 도입 시 `group_node` 테이블을 추가하고 기존 문자열을 파싱해 채우면 되며, md 파일은 그대로 둬도 된다.

> 지금 계층 구조를 만들지 않는 이유: 실제로 어떤 축(연도·팀·과제군)으로 묶게 될지는 데이터가 쌓여야 드러난다. 미리 만든 분류 체계는 대개 안 맞는다.

> **한국어 검색**: FTS5 기본 토크나이저는 한국어 형태소를 나누지 못한다. 별도 형태소 분석기(konlpy 등) 의존성을 추가하지 않고, `trigram` 토크나이저로 부분 문자열 검색을 지원한다. 수천 건 규모의 개인 vault에서는 충분하며, 성능이 문제되면 그때 대체한다.
>
> trigram은 이름 그대로 **3글자 미만은 매칭하지 못한다.** "B안", "셀" 같은 짧은 검색어도 써야 하므로, 2글자 이하 질의는 `LIKE '%…%'` 로 물러나 처리한다. 첨부는 본문이 없으므로 파일명만 LIKE로 찾는다.

## 5. 핵심 기능 설계

### 5.1 화면 구성

| 화면 | 내용 |
|---|---|
| **메인 대시보드** | 과제 목록 화면 맨 위. 상태별·속성별 과제 수(누르면 그 조건으로 목록이 걸러짐), 이번 주 보고 대상 후보 5건(누르면 상세로), 마감 임박·기한 초과를 작게. 접을 수 있고 접은 상태를 기억한다. 지표를 늘리지 않는 것이 규칙이다 — 숫자가 많아지면 대시보드가 아니라 또 하나의 표가 된다 (5.8) |
| **과제 목록 / 보드** | 기본 진입 화면. 상태별 칸반 보드 ↔ 테이블 뷰 전환. 컬럼: 제목, 상태, 그룹, 태그, 마감일(D-day 배지), 최근 업데이트, **마지막 보고일 / 보고 후 경과일 / 미보고 진행 건수**. 필터: 상태·그룹·태그·기간, 정렬: 최근 업데이트순(기본)/마감일순/**보고 경과일순** |
| **과제 상세** | 상단에 개요(index.md) 렌더링 + 메타 편집 패널, 하단에 진행일지 타임라인(최신순). 각 일지는 접기/펼치기, 인라인 편집 진입. 타임라인에 **보고 시점 마커**가 함께 찍혀 "어디까지 보고했는지"가 한눈에 보임 |
| **보고 이력 (과제 상세 내 탭)** | 해당 과제의 보고를 날짜 역순으로 나열. 각 행에서 보고 당시 `report.md`(읽기 전용)와 보고에 사용한 엑셀 원본을 바로 열람 |
| **보고 대상 후보** | 전체 과제를 "마지막 보고 후 경과일 × 미보고 진행 분량" 기준으로 정렬한 대시보드. 매주 보고할 2–3개를 고르는 전용 화면 (5.7) |
| **일지 편집기** | 좌: 마크다운 편집기 / 우: 실시간 미리보기(접을 수 있음). 이미지 붙여넣기·드래그앤드롭 업로드, 첨부 목록. 편집기를 열면 2단이 잠시 1단이 되어 전체 폭을 쓰고, **화면이 그 자리로 따라간다 — 닫을 때도 원래 기록 자리로 되돌아간다** (5.9) |
| **검색** | 전체 과제 통합 검색(제목+본문+첨부 파일명), 결과에서 과제/일지로 이동 |
| **내보내기** | 과제 단위 단일 md / zip / HTML 다운로드 |

### 5.2 첨부 업로드 흐름

```
[에디터에서 Ctrl+V 또는 드래그]
        │
        ▼
POST /api/entries/{entry_id}/attachments  (multipart, 스트리밍)
        │
        ├─ 파일명 정규화 (경로 traversal 차단, 순번 접두사 부여)
        ├─ 청크 단위(1MB)로 임시 파일에 기록 — 전체를 메모리에 올리지 않음
        │  └─ 같은 패스에서 sha256 누적 계산 (파일 재읽기 없음)
        ├─ 디스크 여유 공간 확인 → 부족하면 즉시 중단하고 임시 파일 정리
        ├─ 완료 후 vault/projects/{proj}/assets/{일지날짜}/{NNN}-{이름} 으로 원자적 이동(os.replace)
        ├─ 같은 과제 내 동일 sha256이면 기존 경로 재사용(중복 저장 방지)
        └─ attachment 레코드 생성
        │
        ▼
응답: { rel_path, markdown_snippet, size_bytes }
        │
        ▼
에디터가 커서 위치에 스니펫 삽입
   이미지 → ![이름](assets/…)   그 외 → [이름](assets/…)
```

**대용량 업로드 처리 (용량 상한 없음)**

상한을 두지 않는 대신, 큰 파일에서도 화면이 멈춘 것처럼 보이지 않아야 한다.

| 항목 | 처리 |
|---|---|
| 진행률 표시 | `XMLHttpRequest.upload.onprogress`로 바이트 단위 진행률을 받아 **파일별 프로그레스 바 + 전송 속도 + 남은 시간**을 표시 (`fetch`는 업로드 진행률을 주지 못하므로 업로드에 한해 XHR 사용) |
| 취소 | 업로드 중 [취소] 버튼 → `xhr.abort()`, 서버는 임시 파일 삭제 |
| 다중 업로드 | 여러 파일을 드롭하면 큐에 쌓아 **순차 전송**(동시 2건까지), 각 항목별 진행률 표시 |
| 편집 차단 없음 | 업로드는 백그라운드로 진행되고 에디터는 계속 사용 가능. 진행 중에는 평문 자리표시자(`⏳ 업로드 중: 파일명`)를 넣고 완료 시 마크다운 링크로 치환한다 (이미지 문법으로 두면 미리보기에 깨진 이미지가 보임) |
| 서버 측 | Uvicorn/Starlette의 `UploadFile`을 `shutil.copyfileobj`로 청크 복사. 프록시·타임아웃 제한을 늘리고, 요청 본문 크기 제한을 해제 |
| 이미지 처리 | 썸네일 생성은 이미지에 한해 수행하고, 초대형 이미지(예: 8000px 초과)는 축소본만 생성. 이미지가 아닌 대용량 파일은 아이콘 + 용량 표시만 |
| 목록 표시 | 과제별·전체 첨부 용량을 표시해 저장소가 얼마나 커지는지 사용자가 인지할 수 있게 함 (차단은 하지 않음) |

> 상한을 두지 않으므로 **백업 부담**이 커질 수 있다. vault를 통째로 복사하는 방식이 느려지면, 첨부를 제외한 문서만 백업하는 옵션(`format=zip&assets=none`)을 함께 제공한다.

* **미리보기 정책**: 이미지는 인라인 렌더링(썸네일 캐시 생성), PDF는 브라우저 내장 뷰어로 새 탭, 오피스 문서는 다운로드 링크 + 아이콘 표시(서버 측 변환 없음).
* **고아 파일 정리**: 어떤 문서에서도 참조되지 않는 assets 파일은 재인덱싱 시 표시만 하고 자동 삭제하지 않는다. 사용자가 "정리" 메뉴에서 확인 후 `.trash/`로 이동시킨다.

**첨부하는 방법은 세 가지** — 붙여넣기(Ctrl+V), 끌어다 놓기, 그리고 **[📎 파일 첨부] 버튼**(파일 선택 대화상자). 앞의 두 가지만 있으면 "첨부 기능이 어디 있는지 모르겠다"는 반응이 나온다. 눈에 보이는 버튼이 있어야 한다.

**첨부와 진행일지의 연결**

* 첨부는 진행일지에 속하므로, 아직 저장하지 않은 새 기록에 파일을 붙이면 **기록을 먼저 만든 뒤** 업로드한다.
* 업로드·삭제 시 진행일지 front matter의 `attachments` 목록을 실제 파일과 동기화한다. 본문에서 참조하지 않는 자료도 md 파일만 보고 알 수 있다.

### 5.3 채택하지 않은 대안 — 중앙 첨부 저장소

`attachments/ab/cd/<sha256>.png` 형태의 콘텐츠 주소 저장은 중복 제거에 유리하지만, md 파일을 외부 도구로 열었을 때 이미지가 깨지고 사람이 파일 탐색기에서 자료를 찾을 수 없다. 이식성이 이 도구의 핵심 가치이므로 **과제 폴더 내 상대경로 저장**을 택하고, 중복 제거는 같은 과제 내 sha256 비교 수준으로 한정한다.

### 5.4 단일 md 내보내기

과제 상세 → "전체 이력 다운로드". 개요 + 모든 진행일지를 날짜 오름차순으로 병합한다.

```
GET /api/projects/{id}/export?format=md&assets=zip|inline|link
```

| 옵션 | 결과 |
|---|---|
| `assets=zip` (기본) | `2026-001-리튬전지-수명평가.zip` = 병합된 `과제명.md` + `assets/` 폴더. 상대경로가 그대로 유효 |
| `assets=inline` | 단일 `.md` 하나만. 이미지는 base64 data URI로 인라인, 비이미지 첨부는 파일명만 각주로 표기 |
| `assets=link` | 단일 `.md` 하나만. 첨부 링크는 로컬 서버 URL로 치환 (도구를 계속 쓰는 전제) |

구현하면서 두 가지를 보탰다.

* **보고에 쓴 파일은 본문에 링크하지 않아도 zip에 담는다.** 보고 자료(엑셀)는 보통 본문에서 참조하지 않는데, "그때 그 파일"이야말로 함께 가야 할 대상이다. 병합 문서의 보고 이력 줄에도 파일명을 적어 둔다.
* **다운로드 파일명**은 RFC 5987(`filename*=UTF-8''…`)로 한글을 보내되, 그것을 모르는 도구를 위해 ASCII 대체 이름을 함께 넣는다.

병합 결과 구조:

```markdown
# 리튬전지 수명평가
> 상태: 진행중 · 기간: 2026-03-02 ~ 2026-12-20 · 그룹: 차세대전지 · 태그: 수명평가, 셀설계

## 과제 개요
(index.md 본문)

---
# 수행 이력

## 2026-09-01 실험 셋업
...
## 2026-09-03 1차 측정 결과
...
```

병합 문서 말미에는 **보고 이력 요약**(보고일 목록 + 각 보고의 요약 첫 줄)을 덧붙이며, `?include=reports_full`을 주면 각 보고의 `report.md` 전문도 함께 포함한다.

추가로 `format=html`(단일 HTML, 이미지 인라인 — 보고용 공유에 편리), `format=zip`(원본 파일 구조 그대로 백업)을 제공한다.

### 5.5 외부 편집 동기화

* 앱 기동 시 vault 전체 스캔 → `file_mtime` 비교로 변경분만 재인덱싱.
* 실행 중에는 `watchdog`으로 vault 감시, 변경 파일만 증분 인덱싱(디바운스 500ms).
* `POST /api/reindex`로 전체 재구축 가능. DB를 지워도 데이터 손실이 없다.

### 5.6 보고 작성 흐름 (초안 자동 생성 → 정리 → 확정)

```
[과제 상세 → "보고 작성"]
        │
        ▼ 마지막 보고 이후의 진행일지를 자동 수집
POST /api/projects/{id}/reports/draft
        │
        ├─ 기간: 직전 보고의 covers_to 다음날 ~ 오늘
        ├─ 해당 구간 진행일지 본문·이미지를 모아 report.md 초안 생성
        └─ 상태: 초안 (frozen_at = NULL, 자유롭게 편집 가능)
        │
        ▼ 사용자가 편집기에서 보고용으로 다듬음
        │  · 요약 / 특이사항 / 다음 계획 3단 구성 기본 템플릿
        │  · 엑셀 붙여넣기용 복사 버튼 (아래 참조)
        │  · 실제 보고에 쓴 .xlsx 업로드
        ▼
POST /api/reports/{report_id}/freeze
        │
        ├─ report.md 읽기 전용 전환 (frozen_at 기록)
        ├─ 포함된 진행일지를 report_entry에 기록 → 이후 '미보고 분량'은 여기서부터 재계산
        └─ 과제의 last_reported_at 갱신
```

**엑셀 보고 지원** — 실제 보고는 엑셀로 하므로, 도구는 엑셀을 대체하지 않고 **엑셀로 옮기는 마지막 한 걸음을 줄이는 데** 집중한다.

| 기능 | 동작 |
|---|---|
| 엑셀 붙여넣기용 복사 | **한 칸에 여러 줄**로 들어가야 하므로, 클립보드에 `text/html`과 `text/plain`을 함께 올린다. 엑셀은 HTML 플레이버를 우선 인식하므로 `<table><tr><td>줄1<br>줄2</td></tr></table>` 형태면 **줄바꿈이 살아 있는 단일 셀**로 붙는다. `text/plain` 쪽은 RFC4180 규칙대로 전체를 큰따옴표로 감싸(내부 `"`는 `""`로 이스케이프) 같은 결과를 내고, 셀 편집 모드(F2) 붙여넣기도 지원한다 |
| 평문 변환 규칙 | 제목(`#`)은 제거하고, 목록 `- `는 그대로 유지(엑셀에서도 읽기 좋음), 강조(`**`, `*`), 링크는 텍스트만 남김, 이미지 삽입은 `[이미지: 파일명]`으로 치환. 변환 결과를 복사 전에 미리보기로 보여 준다 |
| 보고 엑셀 원본 보관 | 보고에 사용한 `.xlsx`를 `reports/<날짜>/assets/`에 첨부. "그때 그 파일"이 이력에 붙어 있음 |
| 엑셀 내용 미리보기 | 업로드된 xlsx를 `openpyxl`로 읽어 첫 시트의 표와 삽입 이미지를 HTML로 렌더링. 서식은 재현하지 않으며 원본 다운로드를 항상 함께 제공 |
| 이미지 첨부 | 보고에 쓴 그래프·화면 캡처는 진행일지와 동일하게 붙여넣기 업로드 |

> 보고 유형(주간/월간/수시)과 피보고자는 스키마와 front matter에 **예약 필드로만 넣어 두고 UI에는 노출하지 않는다.** 필요해지는 시점에 입력란과 필터만 추가하면 되고, 그 전에 기록된 보고들도 그대로 유효하다.

### 5.7 보고 대상 예측

매주 전체 과제를 보고하는 것이 아니라 2–3건만 고르므로, **"지금 보고해야 할 과제"를 도구가 먼저 제시**한다. 근거는 두 가지다.

| 지표 | 정의 |
|---|---|
| `days_since_report` | 오늘 − 마지막 보고일 (보고 이력이 없으면 과제 시작일 기준) |
| `unreported_entries` | 마지막 보고 이후 작성된 진행일지 건수 (`report_entry`에 없는 일지) |

정렬 기본값은 두 지표를 함께 반영한 단순 점수이며, **점수와 함께 원본 수치를 항상 같이 표시**해 왜 위에 올라왔는지 바로 보이게 한다.

```
elapsed = min(days_since_report / 기준주기(7일), 8.0)   # 상한: 오래 방치된 과제의 독점 방지
if unreported_entries == 0: elapsed *= 0.25             # 보고할 새 내용이 없으면 후순위
score = elapsed + unreported_entries × 0.5
```

> 구현 중 발견: 상한만 두면 **11년째 방치됐지만 보고할 새 내용이 하나도 없는 과제**가 1순위로 올라온다.
> 후보 목록의 목적은 "보고할 거리가 쌓인 과제"를 찾는 것이므로, 미보고 진행일지가 없으면 경과 항을 크게 깎는다.
> 목록에서 아예 지우지는 않는다 — 오래 조용한 과제는 그 자체로 확인할 거리이기 때문이다.

* **기준주기는 7일**(주간 보고). 가중치와 함께 설정값으로 두어 나중에 조정할 수 있다.
* 상태가 `보류`·`완료`·`중단`인 과제는 후보에서 제외(토글로 포함 가능).
* 각 행에 "보고 경과 D+21 · 미보고 4건" 배지와 **[보고 초안 만들기]** 버튼을 두어, 후보 선정 → 초안 생성이 한 화면에서 이어진다.
* 과제 상세와 목록에도 같은 배지를 노출해 어디서든 보고 시점을 가늠할 수 있게 한다.

**주간 리듬에 맞춘 동작** — 월요일에 항목을 고르고 화요일에 보고하는 흐름을 그대로 화면에 반영한다.

| 시점 | 동작 |
|---|---|
| 월요일 (선정) | 앱 진입 시 "보고 대상 후보"를 첫 화면으로 제안. 후보에서 2–3건을 **체크해 담아 두면** 그 주의 보고 묶음이 된다 |
| 월~화 (정리) | 담아 둔 과제마다 보고 초안이 생성되어 있어, 이동 없이 순서대로 다듬는다 |
| 화요일 (보고) | 보고일 기본값은 **그 주 화요일**. 보고 후 [확정]을 누르면 묶음의 모든 과제가 한 번에 확정되고 경과일이 0으로 리셋된다 |

> 주 단위 묶음은 `reports/`의 개별 보고 문서를 대체하지 않는다. 화면상의 선택 묶음일 뿐이며, 확정 결과는 언제나 과제별 `report.md`로 남는다.

> 향후 확장 여지: 과제별 목표 보고 주기(예: 이 과제는 2주에 한 번)를 지정하면 `days_since_report`를 그 주기로 나눠 과제마다 다른 리듬을 반영할 수 있다. 지금은 전역 기준주기 하나로 시작한다.

### 5.8 메인 대시보드 — 세는 수와 거르는 수는 같아야 한다

대시보드가 "기한 초과 1건"이라고 적어 놓고 그 숫자를 눌렀을 때 2건이 나오면,
그 화면의 모든 숫자를 못 믿게 된다. 그래서 **집계와 필터가 같은 기준을 공유하도록**
`FINISHED_STATUSES` 를 `config.py` 한 곳에 두고 양쪽이 함께 참조한다.

여기서 정한 규칙 셋:

* **끝난 과제(완료·중단)는 마감 경고에서 뺀다.** 이미 끝난 일에 빨간 배지를 다는 것은
  경고가 아니라 소음이다. 화면(`util.ts`)이 이미 그렇게 하고 있었는데
  집계와 필터가 따라가지 못했다. 보류는 멈춰 있을 뿐 끝난 것이 아니라서 그대로 센다.
* **"N일 이내"는 앞으로 N일이라는 뜻이다.** 이미 지난 과제는 '기한 초과'가 따로 맡는다.
  한 과제가 두 칸에 동시에 잡히면 합이 맞지 않는다.
* **0건인 칸은 그리지 않는다.** 빈 칸이 늘어나면 눈이 갈 곳을 잃는다.

이 규칙은 `test_dashboard.py::test_numbers_match_what_the_list_filters` 가
대시보드의 모든 수를 실제 목록 필터 결과와 대조해 고정한다.

### 5.9 편집기를 열고 닫을 때 화면이 따라간다

편집기는 여는 순간 2단을 1단으로 바꾸고 편집 중인 칸을 맨 위로 올린다.
넓게 쓰자고 만든 규칙인데, **스크롤 위치는 그대로 남는다.**
목록 아래쪽 기록을 고치려고 [수정]을 누르면 편집기가 화면 밖으로 밀려
다시 찾아 내려가야 한다. 배치를 바꾸는 기능은 화면을 옮기는 짝이 반드시 따라와야 한다.

* 편집기가 **뜰 때** 그 자리로 (`block: "start"`), **닫을 때** 원래 기록 자리로
  (`block: "center"` — 닫으면서 목록을 다시 읽어 높이가 조금 달라지기 때문).
* 배치가 다시 그려진 다음에 움직여야 하므로 한 프레임(`requestAnimationFrame`) 기다린다.
* 상단 헤더는 화면 폭에 따라 접혀 67px에서 183px까지 자란다. 고정 여백을 두면
  좁은 화면에서 제목이 가리므로, `App.tsx` 가 헤더의 실제 높이를 `--header-h` 로
  내보내고 `scroll-margin-top` 이 그것을 쓴다.

### 7.1 윈도우 실행 환경 대응

실사용 환경이 윈도우 + Python이므로 다음을 코드 차원에서 지킨다.

| 항목 | 대응 |
|---|---|
| 금지 문자 | 파일명에서 `\ / : * ? " < > |` 와 제어문자를 제거 (첨부·과제명 공통) |
| 예약어 | `CON`, `NUL`, `COM1` 등은 뒤에 `_`를 붙여 회피 |
| 끝의 점·공백 | 탐색기에서 잘려 나가므로 제거 |
| 경로 길이 | 260자 제한을 감안해 슬러그 60자, 첨부 파일명 90자로 제한 |
| 한글 정규화 | NFD로 들어온 이름을 NFC로 합쳐 저장 (맥에서 복사해 온 파일 대비) |
| 인코딩 | 모든 파일 입출력에 `encoding="utf-8"` 명시, 콘솔은 `PYTHONUTF8=1` / `chcp 65001` |
| 실행 | `run.py`·`setup.py`(공통, 한글 안내 담당) + `run.bat`·`setup.bat`(더블클릭용) |
| 배치 파일 | **순수 ASCII + CRLF.** cmd는 `.bat`을 cp949로 읽어 UTF-8 한글이 들어가면 파싱이 깨지고, LF만 있는 파일에서는 `goto`/라벨을 잘못 해석한다. 한글 안내는 전부 파이썬이 출력하고, `.gitattributes`로 `*.bat`을 CRLF로 고정한다 |
| 파이썬 버전 | 3.10 미만이면 실행 시점에 안내하고 중단 |

| **M6. 서버 확장 (선택)** ◀ 선택 | Docker 이미지, 간단 인증, 다중 사용자 대비 잠금 | 사내 서버에 올려 팀원이 조회 가능 |

M1~M2까지가 첨부 관련 불편을 해소하는 최소 유용 제품(MVP)이고, **M4가 "보고 시점 예측"이라는 두 번째 핵심 가치**를 완성한다.

## 8.1 1차 리뷰에서 발견해 고친 것

구현을 마친 뒤 엣지 케이스를 실제로 두드려 본 결과다. 모두 회귀 테스트로 고정했다.

| 심각도 | 문제 | 대응 |
|---|---|---|
| 높음 | **날짜가 검증 없이 파일 경로에 들어갔다.** `date="../../탈출"` 로 과제 폴더 밖에 파일이 생성됐고, `2026/13/45` 는 500 오류를 냈다 | 날짜는 `YYYY-MM-DD` 만 허용하고 어긋나면 400. 파일명 전체를 슬러그로 만들고 `safe_join` 으로 한 번 더 가둔다 |
| 높음 | **md 파일 하나가 깨지면 전체 인덱싱이 멈췄다.** 메모장으로 편집하다 front matter 형식이 어긋나면 도구 전체가 뜨지 않는다 | 파일 단위로 오류를 잡아 건너뛰고, 읽지 못한 파일 목록을 화면과 콘솔에 알린다. 나머지 과제는 정상 표시 |
| 중간 | **외부 편집을 말없이 덮어썼다.** 옵시디언·탐색기로 고친 내용이 웹에서 저장하면 사라졌다 | 저장 전 파일 수정 시각을 비교해 어긋나면 409와 안내. 편집기에 [지금 다시 읽기] 버튼 제공 |
| 중간 | **중복 제거가 파일명을 무시했다.** 내용이 같은 빈 파일 두 개가 한 파일로 합쳐져 이름·확장자가 어긋났다 | 내용(sha256)과 파일명이 **모두** 같을 때만 중복으로 본다 |
| 중간 | **윈도우 파일 잠금 미고려.** 엑셀이 열어 둔 파일을 삭제·보관하면 500 | `PermissionError` 를 잡아 423과 "파일을 연 프로그램을 닫고 다시 시도하세요" 안내 |
| 낮음 | 내보낸 HTML이 본문의 raw HTML을 그대로 실행 | 앱 화면과 같게 비활성화(글자로 표시) |
| 낮음 | 과제명 변경 시 폴더명이 겹치면 조용히 넘어감 | 유일한 이름을 만들어 실제로 이동 |

성능은 **과제 60건 × 진행일지 300건** 기준으로 검색 34ms, 목록 8ms, 보고 후보 9ms, 전체 재인덱싱 146ms 로 여유가 있다.

### 8.2 색인 구조가 바뀔 때 (2차 리뷰에서 발견)

업데이트 후 실행하면 `table project has no column named type` 오류로 실행이 막혔다.

* **원인**: 스키마를 `CREATE TABLE IF NOT EXISTS` 로만 만들어, 예전에 생성된 DB에는 새 컬럼이 추가되지 않는다. 마이그레이션 장치가 아예 없었다.
* **대응**: `PRAGMA user_version` 에 스키마 버전을 새겨 두고, 값이 다르면 **색인을 통째로 버리고 다시 만든다.** 색인은 md 파일에서 파생된 캐시이므로 잃을 것이 없고, 이 방식이면 앞으로 컬럼을 추가할 때마다 마이그레이션을 쓸 필요도 없다 (버전 숫자만 올리면 된다).
* 색인 파일이 손상돼 SQLite가 열지 못하는 경우도 같은 계열의 문제로 보고, 파일을 지운 뒤 다시 만든다. 실행이 막히는 대신 스스로 복구한다.
* 다시 만드는 동안 화면·콘솔에 "작성한 내용은 그대로"임을 알린다.

> 교훈: "인덱스는 언제든 재생성 가능하다"고 설계해 놓고, 정작 **재생성해야 할 시점을 판단하는 장치**를 넣지 않았다. 파생 데이터라는 설계 원칙을 코드가 실제로 실행하게 만들어야 한다.

## 9. 리스크 및 대응

| 리스크 | 대응 |
|---|---|
| vault를 외부 도구로 동시 편집하며 덮어쓰기 | 저장 전 `file_mtime` 비교 → 변경 감지 시 사용자에게 알리고 덮어쓰기 여부 확인 |
| 첨부 누적으로 저장소 비대화 | 용량 상한을 두지 않기로 했으므로 **차단 대신 가시화** — 과제별·전체 첨부 용량 표시, 중복 파일 감지, 문서만 백업하는 옵션 제공 |
| 백업 부재 | vault 폴더를 그대로 복사하면 완전 백업. 첨부가 커지면 문서만 백업하는 옵션 병행. vault를 git 저장소로 두는 방식은 대용량 첨부와 상성이 나쁘므로 보류 |
| 한국어 전문 검색 품질 | trigram으로 시작, 부족하면 형태소 분석기 도입 |
| 확정된 보고 문서를 나중에 고치고 싶어짐 | 원칙은 읽기 전용이나 `unfreeze`로 해제 가능하게 하되, 해제·재확정 시각을 front matter에 남겨 사후 수정 여부가 드러나게 함 |
| 엑셀 미리보기가 원본 서식과 다름 | 표와 이미지 추출 수준으로만 제공하고 원본 다운로드를 항상 병행. 서식 재현이 목적이 아님을 UI에 명시 |
| 보고 없이 오래 방치된 과제의 경과일이 무한정 커짐 | 후보 점수 상한을 두고, 상태가 보류·완료·중단이면 후보에서 제외 |
| 경로 traversal / 파일명 충돌 | 모든 경로를 vault 루트 기준으로 정규화 후 검증, 파일명은 순번 접두사로 유일성 확보 |
