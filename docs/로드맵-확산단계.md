# 로드맵 — 쓰는 사람이 늘어나는 순서

> 2026-09-18 작성. **누가 쓰는가**를 축으로 세운 로드맵이다.
> 기능 축으로 정리한 [ROADMAP.md](ROADMAP.md)(R1~R3)와 같은 것을 다른 각도로 본다 —
> 아래 [8절](#8-기존-문서와의-관계)에 서로를 어떻게 읽는지 적었다.
>
> 이 문서의 목적은 "언제 무엇을 만드나"가 아니다. **지금 내리는 결정이 다음 단계를 막지
> 않게 하는 것**이다. 날짜는 적지 않는다 — 대신 단계마다 **넘어가는 신호**를 적는다.

---

## 0. 한 장 요약

사용자가 제시한 세 단계에 **두 단계를 더 쪼개기를 제안한다.** 이유는 각 절에 적었다.

| 단계 | 누가 쓰나 | 어디서 도나 | 지금 상태 |
|---|---|---|---|
| **1** | 팀장 한 명 | 내 PC | ✅ **완료** (TODO 1~127) |
| **1.5** ← 제안 | 팀장 여럿, **각자 따로** | 각자 PC, 서버 없음 | 🔜 **지금 할 일** — 옆 팀장 설치 |
| **2** | 팀장 여럿, **함께** | 사내 서버 한 대 | 결정 넷이 먼저 |
| **2.5** ← 제안 | 팀원이 **보기만** | 2단계 서버 또는 정적 HTML | 선택 — 3단계의 위험을 먼저 던다 |
| **3** | 팀원까지 **쓰기** | 사내 서버 | 성격이 바뀐다 — 5절 |

**왜 1.5 를 따로 두나.** 옆 팀장이 지금 쓰기 시작하는 것은 2단계가 **아니다.** 서버도 로그인도
없이 각자 1인 체제로 도는 것이고, **코드는 한 줄도 바뀌지 않는다.** 둘을 같은 칸에 넣으면
"여러 팀장이 쓴다 = 서버가 필요하다"로 읽혀 실제로 지금 당장 할 수 있는 일이 미뤄진다.

**왜 2.5 를 따로 두나.** 3단계는 사용자가 다섯에서 서른으로 늘고 도구의 성격이 바뀌는,
이 로드맵에서 **가장 큰 걸음**이다. 그 앞에 *팀원이 보기만 하는* 단계를 두면 "팀원이 실제로
이것을 보는가"를 **코드를 거의 안 쓰고** 확인할 수 있다. 안 보면 3단계는 만들 이유가 없다.

## 1. 1단계 — 팀장 1인 ✅ 완료

과제 하나가 폴더 하나이고, 진행일지·보고·첨부가 그 안에 쌓인다. 주간 보고가 손에서
도구로 옮겨 왔고, 연말 성과가 홈 한 화면에서 나온다.

되짚어 둘 것은 **이 단계에서 정한 것들이 다음 단계를 열어 두었다**는 점이다.

| 결정 | 다음 단계에 무엇을 열어 두었나 |
|---|---|
| **파일이 원본, 색인은 파생물** | 합치고 나누는 일이 **폴더 복사**가 된다. 2단계 이관의 근거 |
| 과제 번호에 **팀 코드 자리** | 팀장이 여럿이어도 번호가 안 겹친다 (1.5절의 핵심) |
| **누가·언제**를 기록 (작성자·생성자·완료일·상태 변경) | 소급이 안 되는 것들. 2단계에 가서 넣으면 그 전 자료가 빈칸이다 |
| 담당자 명부에 **사번 칸** | 3단계 로그인의 재료 |
| 서버가 `127.0.0.1` 로만 듣는다 | 지금은 안전, 2단계에 **일부러** 연다 |

**하지 않은 것도 기록해 둔다** — git 자동 커밋(사내망 밖으로 나가는 오해), AI API 직접 호출
(인터넷 차단 + 자료 유출), 실시간 잠금(파일이 원본인 구조와 싸운다).

## 2. 1.5단계 — 배포 확산 (각자 1인 체제) 🔜

**지금 옆 팀장이 쓰겠다고 하면 여기다.** 만들 것은 없고 **건네주는 일**이다.

### 2.1 건네주기 전에 물어볼 것

| 질문 | 왜 |
|---|---|
| **파이썬 버전** | 배포본의 `vendor/` 가 그 버전용이어야 설치된다. 다르면 그 버전으로 배포본을 새로 만든다 |
| 프로그램 설치 권한 | 없으면 파이썬 설치부터 막힌다 |
| 데이터를 둘 폴더 | **개인 PC 에 둔다.** 공유 폴더 위의 SQLite 색인은 깨진다 |
| 백업 폴더 | 네트워크 드라이브나 외장 디스크. 데이터 폴더 안에는 못 넣는다 |

### 2.2 설치 순서

1. **배포본 ZIP 전달** — 원하는 폴더에 푼다.
2. **`setup.bat`** 한 번 (가상환경 + 패키지). 인터넷이 막혀 있어도 동봉된 `vendor/` 로 설치된다.
3. **`run.bat`** — 브라우저가 열린다. 두 번째부터는 이것만 누른다.
4. **첫 설정 5분** (아래 2.3).
5. **연습 한 바퀴** — 과제 1건 → 진행일지 1건 → 보고 초안 → 확정. 20분이면 흐름이 잡힌다.
6. **메뉴 끝의 [도움말]** 을 읽게 한다. 주간 흐름·화면 지도·자주 묻는 것이 거기 있다.

### 2.3 첫 설정에서 정할 다섯

| 항목 | 왜 첫날인가 |
|---|---|
| **과제 번호의 팀 코드** | 아래 2.4 — **이 단계에서 가장 중요한 한 가지** |
| 작성자 이름 | 안 정하면 진행일지·보고에 작성자가 빈 채로 쌓인다 |
| 담당자 명부 | 자동완성의 기준. 나중에 넣으면 표기가 이미 흔들려 있다 |
| 보고 요일 | 보고 예정일·배너·초안 날짜가 전부 이 값을 따른다 |
| 백업 폴더 | 층을 나눠 남긴다 (일 7 · 주 4 · 월 6 = 반년) |

### 2.4 팀 코드를 첫날 정해야 하는 이유

팀 코드를 비우면 과제 번호가 `2026-001` 이 된다. 두 팀이 각자 그렇게 쌓으면 2단계에서 합칠 때
**양쪽에 `2026-001` 이 생긴다.** 지금 `2026-설비기술팀-001` 로 정해 두면 **합치는 일이 폴더
복사**가 된다.

번호를 나중에 바꾸는 기능(일괄 재부여)이 있기는 하다. 그러나 번호는 **이미 보고 자리에서 불린
이름**이라, 바꾸면 지난 보고 자료와 어긋난다. 첫날 30초가 나중의 하루를 아낀다.

> 팀 코드는 **윈도우 폴더 이름에 그대로 들어간다.** `: * ? " < > | / \` 와 공백은 막혀 있고,
> 20자를 넘지 못한다. 팀 이름이 길면 줄여서 정한다.

### 2.5 이 단계에서 하지 않을 것

* **vault 를 공유 폴더에 두지 않는다.** "그러면 같이 볼 수 있지 않나" 는 유혹이지만, 공유
  폴더 위에서 여럿이 열면 색인이 깨진다. 함께 보는 것은 2단계의 일이다.
* **자료를 합치지 않는다.** 각자 쌓는다. 합치는 것은 2단계 8번.
* **버전을 맞추려 애쓰지 않는다.** 배포본은 각자 쓰던 것을 덮어쓰면 되고, 서로 달라도
  파일이 원본이라 문제가 없다.

### 2.6 운영 — 문의가 올 때

두 가지만 받으면 대부분 가려진다.

1. **설정 → 점검**의 *지금 실행 중인 배포본* 이름 (덮어썼는데 안 바뀌는 문제를 한 줄로 가른다)
2. 같은 화면의 **[최근 오류] 복사본** — 과제 내용은 담기지 않으므로 그대로 보내도 된다

## 3. 2단계 — 여러 팀장이 함께

### 3.1 코드보다 결정이 먼저 — 넷

| # | 갈림길 | 선택지 | 제 의견 |
|---|---|---|---|
| ① | **저장 방식** | 각자 vault / 하나를 공유 | **공유.** 대표 아이템 선정(R3)이 "한곳에 모인 것 중 고르기" 라 각자 두면 성립하지 않는다 |
| ② | **접속 방식** | 사내 서버 한 대 / 각자 PC + 공유 폴더 | **서버 한 대.** 공유 폴더 위의 SQLite 는 깨진다. 사내 PC 한 대를 켜 두는 것으로 시작해도 된다 |
| ③ | **로그인** | 사번+비밀번호 / 사내 인증 / 이름 고르기 | **이름 + 사번 확인.** 사내 인증은 IT 협의라 일정이 손을 벗어난다 |
| ④ | **권한** | 내 팀만 수정 / 모두 수정 | **내 팀만 수정, 나머지 읽기.** 남의 보고를 실수로 확정하는 사고를 막는 최소선 |

### 3.2 이미 되어 있는 것

1단계에서 미리 넣어 둔 것들이다 — 2단계에 가서 넣으면 그 전 자료가 빈칸이 된다.

과제 생성자 · 진행일지와 보고의 작성자 · 과제 번호의 팀 코드 · 담당자 명부와 사번 칸 ·
완료일 · 상태 변경 이력 · 떠난 담당자 표시. 그리고 **파일이 원본**이라는 구조 자체.

### 3.3 만들 것 — 여덟 단계

각 단계가 **혼자서도 배포 가능**하도록 잘랐다. 4번을 넣기 전까지는 지금과 똑같이 동작한다.

```
1  사용자 개념      요청마다 "지금 누구인가" 를 정하는 한 곳 (지금은 설정의 작성자 값)
2  소유 팀          과제에 team 한 줄. 번호의 팀 코드에서 초기값
3  로그인           이름 고르기 + 사번 확인 → 작성자 자동 채움
4  권한             내 팀만 쓰기. API 한 곳에서 막는다
5  동시 편집        지금의 수정 시각 비교에 "누가 열어 두었나" 를 더한다 (잠금이 아니라 안내)
6  서버 배포        외부 접속 허용 · 윈도우 서비스 등록 · 방화벽 · HTTPS 는 사내 정책 따라
7  화면             홈·목록에 팀 거르기
8  자료 합치기      각자 쌓은 vault 를 하나로 (팀 코드가 다르면 폴더 복사)
```

규모는 1~2가 하루, 3~5가 3~4일, 6~7이 2일 정도로 본다.

### 3.4 2026-09-18 검토에서 새로 보인 것 둘

앞선 검토(6절)에 없던 것이다. **둘 다 "공유하는 순간" 드러난다.**

**(1) 설정이 vault 하나에 하나뿐이다.** 보고 요일·진행일지 서식·과제 속성이 전부 공용 설정
파일(`settings.json`)에 있다. vault 를 공유하면 **팀마다 다를 수 있는 보고 요일이 하나로
묶인다.** 팀별 설정을 나눌지, 팀장끼리 하나로 맞출지 정해야 한다.
→ 제안: **보고 요일만 팀별**, 나머지(서식·속성)는 공용. 속성이 팀마다 다르면 집계 축이
갈라져 "팀 전체 현황" 이라는 말 자체가 성립하지 않는다.

**(2) 홈의 합계가 팀을 가로질러 합쳐진다.** 효과 금액·과제 수·팀원별 성과가 vault 전체를
센다. 7번(팀 거르기)이 들어오기 전까지는 **"우리 팀 성과" 를 볼 수 없다.** 그래서 7번을 뒤로
미루기 어렵다 — 8번(합치기)과 **같은 날** 들어가야 한다.

### 3.5 기술 외적으로 필요한 것

코드보다 이쪽이 자주 발목을 잡는다.

| 항목 | 내용 |
|---|---|
| 서버로 쓸 PC 한 대 | 계속 켜 둘 것. 끄면 전원이 못 쓴다 |
| 그것을 관리할 사람 | 업데이트·재시작·디스크. 팀장 중 한 명이 맡거나 IT 에 맡긴다 |
| 백업 주체 이동 | 개인 PC → 서버. **서버의 백업 폴더가 곧 팀 전체의 안전망**이라 첫날 정한다 |
| 담당자 명부 통합 | 동명이인·표기 흔들림. 합치기 **전에** 양쪽 명부를 맞춰 본다 |
| 사내 IT 협의 | 방화벽·포트·HTTPS. 사내 인증까지 간다면 일정이 크게 는다 |
| 운영 규칙 합의 | 남의 과제를 고칠 때 · 보고를 확정할 때 · 담당자를 넘길 때 |

### 3.6 미리 알아 둘 위험

* **동시 편집은 완전히 막지 않는다.** 파일이 원본인 구조에서 실시간 잠금은 구조와 싸운다.
  "누가 열어 두었다" 안내 + 저장 시 충돌 감지까지가 현실적이다.
* **오류 기록에 *누가* 가 남기 시작한다.** 과제 내용을 담지 않는 원칙은 그대로 간다.
* **성능** — 팀장 다섯이면 과제 천 건이다. 색인은 그 열 배도 버티지만 홈의 집계 몇 개는
  다시 재야 한다.

### 3.7 넘어가는 신호

날짜가 아니라 **조건**이다. 아래가 둘 이상 맞으면 2단계를 시작한다.

* 팀장 **둘 이상이 석 달 넘게** 실사용 중이다 (1.5단계가 굴러간다는 증거)
* **합쳐서 봐야 할 일**이 실제로 생겼다 — 대표 아이템 선정, 부문 단위 보고
* 서버로 쓸 PC 와 관리할 사람이 정해졌다
* 위 결정 ①~④ 에 답할 수 있다

## 4. 2.5단계 — 팀원이 보기만 (선택 · 제안)

3단계로 바로 가기 전에 **저비용으로 절반의 가치**를 먼저 가져오는 길이다.

**두 가지 방법이 있다.**

| 방법 | 내용 | 비용 |
|---|---|---|
| (가) **정적 HTML 내보내기** | 과제 하나 또는 전체를 HTML 묶음으로 내보내 메일·공유폴더로 전달 | S — 서버가 없어도 된다 |
| (나) 2단계 서버에 **읽기 전용 계정** | 팀원은 로그인해서 보기만 | 2단계 3~4번이 있어야 한다 |

**왜 이 단계가 위험을 더나.** 3단계의 진짜 질문은 기술이 아니라 **"팀원이 실제로 쓰는가"** 다.
쓰기를 만들어 놓고 아무도 안 쓰면 그 노력은 통째로 버려진다. 보기만 하는 단계를 먼저 두면
**코드를 거의 안 쓰고 그 질문에 답할 수 있다.** 팀원이 자기 과제를 들여다보기 시작하면
3단계는 자연스럽고, 안 본다면 3단계는 만들 이유가 없다.

## 5. 3단계 — 팀원까지 쓰기

### 5.1 여기서 도구의 성격이 바뀐다

| | 2단계까지 | 3단계 |
|---|---|---|
| 사용자 수 | 다섯 안팎 | **서른 안팎** |
| 성격 | 팀장의 **보고 도구** | 팀의 **협업 도구** |
| 쓰는 사람 | 기록하는 사람 = 보고하는 사람 | **기록하는 사람과 보고하는 사람이 다르다** |
| 권한 | 두 단계 (내 팀 / 남의 팀) | **세 단계** (팀원 / 팀장 / 관리자) |
| 실수의 무게 | 내 것만 | 남의 기록을 건드린다 |

**가장 큰 변화는 세 번째 줄이다.** 지금 이 도구는 "쓴 사람이 곧 보고하는 사람" 을 전제로
설계돼 있다. 팀원이 진행일지를 쓰고 팀장이 보고를 만드는 순간, 지금은 없는 것들이 필요해진다.

### 5.2 필요한 것

| 항목 | 왜 |
|---|---|
| **팀원 화면** | 홈이 팀 현황이 아니라 **내 과제**로 시작해야 한다. 팀원에게 팀 전체 집계는 소음이다 |
| 권한 세 단계 | 팀원은 자기 과제의 진행일지만. 보고 확정은 팀장만 |
| **알림** | 팀장이 "이번 주 진행일지 써 주세요" 를 매번 말로 하게 되면 도구가 진 것이다 |
| 지시사항의 왕복 | 지금은 팀장이 혼자 적는다. 팀원에게 전달되고 답이 돌아와야 한다 |
| 첨부 용량 | 사람이 여섯 배면 첨부도 여섯 배다. 서버 디스크와 백업 시간을 다시 잰다 |
| 교육 | 팀장 한 명 가르치는 것과 서른 명은 다르다. [도움말] 화면이 그래서 먼저 들어갔다 |

### 5.3 채택이 진짜 위험이다

기술은 2단계에서 대부분 풀린다. 3단계의 위험은 **"팀원이 귀찮아한다"** 이고, 그것은 코드로
풀리지 않는다. 그래서 2.5단계로 먼저 재 보기를 권한다.

한 가지 더 — **팀원이 쓰는 것이 늘면 팀장이 쓰는 것이 줄어야 한다.** 둘 다 늘면 도구가
일을 만든 것이다. 3단계의 성공 기준은 "팀원이 쓴다" 가 아니라 **"팀장의 보고 준비 시간이
더 줄었다"** 로 잡는 편이 정직하다.

### 5.4 넘어가는 신호

* 2단계가 **반년 이상** 안정적으로 돌았다
* 2.5단계에서 **팀원이 실제로 들여다본다**는 것이 확인됐다
* 팀원이 "내가 직접 쓰면 안 되나" 라고 **먼저 묻는다** ← 가장 좋은 신호
* 서버·백업·계정을 관리할 사람이 계속 있다

## 6. 단계를 가로지르는 원칙 넷

1. **앞 단계를 깨지 않는다.** 2단계 코드가 들어가도 1인 사용자는 지금과 똑같이 쓸 수 있어야
   한다. 파일이 원본이라 가능한 일이고, 이것이 깨지면 되돌아갈 길이 없어진다.
2. **소급이 안 되는 것부터.** 누가·언제·어디서는 그 순간이 지나면 다시 만들 수 없다.
   단계마다 "이 값을 6개월 뒤에 넣으면 그 전 자료는 어떻게 되나" 를 묻는다.
3. **단계는 날짜가 아니라 신호로 넘어간다.** 위 각 절의 *넘어가는 신호*가 그것이다.
   신호 없이 다음 단계를 시작하면 만들어 놓고 안 쓰는 것이 생긴다.
4. **한 단계 안에서도 혼자 배포 가능하게 자른다.** 2단계 여덟 걸음이 그렇게 잘려 있다.
   중간에 멈춰도 그때까지가 쓸모 있어야 한다.
