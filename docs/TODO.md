## 1. 보고 초안의 기본 내용 — 다 채울지, 비워 둘지

**접수**: 2026-09-02 · **상태**: **B안으로 결정** (2026-09-02)

**현상**
[보고 초안 만들기]를 누르면 마지막 보고 이후의 진행일지 **본문 전체**가 초안에 붙어 나온다.

**불편한 점**
실제로는 그중 필요한 것만 골라 직접 정리해 쓰고 싶은데, 쓰기 전에 지우는 일부터 해야 한다.

**선택지**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 초안을 **빈 칸**으로 시작 (요약·특이사항·다음 계획 뼈대만) | 바로 쓰기 시작 가능 | 무엇을 보고할지 다시 찾아봐야 함 |
| **B ← 채택** | 지금처럼 채우되 **[내용 지우기]** 버튼 추가 | 참고하며 쓰다가 필요할 때 지움 | 기본은 여전히 긴 초안 |
| C | 기본값을 **설정으로 선택** (빈 칸 / 채움) | 취향대로 | 설정 항목이 하나 늘어남 |

**구현 제안값** (이대로 만들고, 써 보고 조정)

| 항목 | 제안값 |
|---|---|
| 버튼 위치 | 보고 편집 화면 위쪽, [엑셀 셀로 복사] 옆 |
| 지우는 범위 | **"진행 내용" 절만** 지우고 `## 보고 요약` · `## 특이사항 및 이슈` · `## 다음 계획` 뼈대는 남긴다. 전부 지우면 목차까지 사라져 결국 다시 타이핑하게 된다 |
| 문구 | `진행 내용 지우기` (무엇이 지워지는지 버튼에 드러나게) |
| 실수 방지 | 누르면 확인창 한 번. 지운 뒤에는 저장하지 않고 화면을 닫으면 원래대로 돌아온다 |

전부를 비우고 싶을 때는 편집창에서 Ctrl+A 로 지우면 되므로 별도 버튼은 두지 않는다.

**영향 범위**: `backend/app/services/reports.py`의 `_draft_body`, `frontend/src/components/ReportEditor.tsx`

## 2. 같은 과제에 보고를 여러 번 남길 수 없음

**접수**: 2026-09-02 · **상태**: **B안으로 결정** (2026-09-02) · **중요도**: 높음

**현상**
보고 이력이 1건 있는 상태에서 [보고 초안 만들기]를 누르면
`2026-09-08 보고 문서가 이미 있습니다.` 가 뜨고 더 이상 진행되지 않는다.

**원인 (확인함)**
보고 문서를 `reports/<보고일>/report.md` 로 저장하기 때문에 **날짜 하나당 보고 하나**다.
그런데 과제 상세의 [보고 초안 만들기] 버튼은 날짜를 묻지 않고 **항상 그 주 화요일**을
기본값으로 쓴다. 그래서 같은 주에 두 번째 보고를 만들려 하면 막힌다.

| 시도 | 결과 |
|---|---|
| 1회차 초안 생성 | 201 정상 |
| 2회차, 같은 날짜 | **409 막힘** ← 지금 겪는 상황 |
| 2회차, 날짜를 직접 지정(예: 2026-09-15) | 201 정상 |
| 1회차를 확정한 뒤 같은 날짜 | 409 막힘 |

즉 기능 자체는 여러 번 보고를 지원하지만, **버튼이 날짜를 고를 방법을 주지 않는 것**이 문제다.
(보고 대상 후보 화면에는 보고 예정일 입력칸이 있어 그쪽에서는 지정할 수 있다)

**선택지**

| 안 | 내용 | 비고 |
|---|---|---|
| A | [보고 초안 만들기]를 누르면 **보고일을 먼저 묻는다** | 가장 단순하고 의도가 분명함 |
| **B ← 채택** | 같은 날짜면 **자동으로 뒤에 번호를 붙인다** (`reports/2026-09-08-2/`) | 누르면 바로 만들어진다. 하루에 중간·완료 보고를 각각 남기는 경우도 대응 |
| C | A + B 둘 다 | 날짜는 고르되, 같은 날 여러 건도 허용 |

**B안 구현 시 정할 것**
- 폴더명 규칙: `reports/2026-09-08/`, 두 번째부터 `reports/2026-09-08-2/`, `-3/` …
- 같은 날짜에 **아직 작성 중인** 보고가 있으면 새로 만들지, 그것을 열지
  (→ 3번 항목의 피보고자 구분이 들어오면 새로 만드는 쪽이 자연스럽다)
- 보고 문서의 `report_date` 는 폴더명이 아니라 front matter 값을 따른다 (둘 다 같은 날짜)

**함께 볼 것**
- 409 메시지가 다음 행동을 알려 주지 않는다. "이미 있는 보고를 열까요, 새 날짜로 만들까요?" 처럼
  선택지를 주는 편이 낫다.
- 이미 있는 그 날짜의 보고가 **작성 중**이면 새로 만들 것이 아니라 그것을 열어 주는 게 자연스럽다.

**결정 필요**: A / B / C 중 선택

**영향 범위**: `backend/app/services/reports.py`의 `create_draft`,
`frontend/src/components/ProjectDetail.tsx`의 보고 초안 버튼

## 3. 보고 이력 한 줄 표기에 피보고자·완료 시각 넣기

**접수**: 2026-09-02 · **상태**: 형식·입력 방식 확정, 나머지는 구현 시 제안값대로

**현상**
보고 이력 목록의 한 줄이 이렇게 보인다.

```
2026-09-08   2026-09-08 보고   확정   진행일지 7건
```

날짜가 두 번 나오고, 정작 **누구에게 보고한 것인지**가 없어서 이력으로서 쓸모가 떨어진다.

**바꿀 형식**

```
2026-09-08  [피보고자 또는 회의체명]  보고 완료(2026-09-08 17:40)
```

* 앞의 `2026-09-08` = 보고일
* `[피보고자 또는 회의체명]` = 누구에게 보고했는지 (예: 팀장, 연구소장, 주간회의체)
* `보고 완료(날짜 시간)` = 확정 시각 (`frozen_at`)

**필요한 것**
설계 때 예약만 해 두고 비워 둔 `audience`(피보고자) 필드를 실제로 쓰게 된다.
보고 문서 front matter에 이미 자리가 있으므로 입력칸과 표시만 붙이면 된다.

**입력 방식 — 결정됨 (2026-09-02)**
**자유 입력 + 기존 값 자동완성.** 피보고자·회의체는 대부분 정해져 있지만 고정 목록으로 막지 않는다.
그룹·담당자와 같은 방식으로, 한 번 쓴 값은 다음부터 목록에 떠서 골라 쓸 수 있게 한다.
(`GET /api/meta` 에 `audiences` 목록을 추가하고, 입력칸은 `<input list=…>` 로)

**나머지 세부 — 아래 제안값으로 구현하고, 써 보고 조정**

| 항목 | 제안값 |
|---|---|
| 입력 시점 | 보고 편집 화면 상단에 입력칸을 두어 **아무 때나** 입력·수정. 확정할 때 비어 있으면 "피보고자 없이 확정할까요?" 한 번만 확인 |
| 미입력일 때 | 목록에 `(피보고자 미입력)` 을 흐린 글씨로 표시 — 비워 두면 빠뜨린 것인지 알 수 없다 |
| 작성 중인 보고 | `2026-09-08  팀장  작성 중` 처럼 뒷부분만 다르게 |
| 확정된 보고의 피보고자 수정 | 확정 해제 없이 **피보고자만은** 고칠 수 있게 (오탈자 정정용). 본문은 그대로 잠금 |

**2번 항목과의 연결**
같은 날짜에 보고를 여러 건 남기게 되면(B안), 목록에서 이 둘을 구분해 주는 것이
바로 피보고자다. 두 항목을 같이 구현하는 편이 낫다.

**영향 범위**: `frontend/src/components/ProjectDetail.tsx`(보고 이력 목록),
`ReportEditor.tsx`(입력칸), `backend/app/api/reports.py`(audience 전달),
`backend/app/api/meta.py`(audiences 자동완성 목록),
`backend/app/services/reports.py`(초안 front matter)

## 4. 완료된 과제에도 마감 초과가 빨갛게 표시된다

**접수**: 2026-09-02 · **상태**: 확정 (아래대로 구현) · **난이도**: 낮음

**현상**
과제 목록 첫 화면에서, 상태가 **완료**인 과제에도 마감일에 `D+261 초과` 가 빨간색으로 뜬다.

```
2025년 수명평가 표준화   완료   국책과제   …   D+261 초과  2025-12-15
```

**왜 문제인가**
빨간 초과 표시는 "기한이 지났는데 아직 끝내지 못했다"는 경고다.
이미 끝난 과제에 띄우면 경고가 무의미해지고, 정작 **진짜 늦어지고 있는 과제**가 묻힌다.

**원인**
`frontend/src/util.ts` 의 `dueLabel()` 이 **날짜만 보고** 표시를 정한다. 상태를 보지 않는다.

```ts
if (days < 0) return { text: `D+${-days} 초과`, tone: "danger" };
```

**이렇게 고친다**

| 상태 | 마감 표시 |
|---|---|
| 완료 · 중단 | 초과 표시를 하지 않고 **마감일만 흐린 글씨로**. 끝난 과제라 남은 날짜도 의미 없다 |
| 보류 | 초과 표시는 유지한다. 멈춰 있을 뿐 끝난 것이 아니고, 오히려 챙겨야 할 대상이다 |
| 예정 · 검토중 · 진행중 | 지금 그대로 (D-7 이내는 주황, 초과는 빨강) |

* `dueLabel(due)` 에 상태를 함께 넘겨 판단하도록 바꾼다.
* 목록·보드 카드·과제 상세 세 곳에서 같은 함수를 쓰므로 한 번만 고치면 된다.

**완료일 기록 — 하지 않기로 함 (2026-09-02)**
완료 일자를 별도 필드로 두지 않는다. 실무에서 **완료 보고를 한 날을 완료로 보고** 관리하고 있고,
그 날짜는 이미 보고 이력에 남는다. 나중에 필요해지면 새 필드를 만들 것 없이
**마지막 확정 보고일**을 완료일로 쓰면 된다.

**영향 범위**: `frontend/src/util.ts`(`dueLabel`),
`ProjectList.tsx` · `ProjectBoard.tsx` · `ProjectDetail.tsx`(호출부)

### 6. 과제 상세 2단 레이아웃 + 상단 요약 ⭐

**지금 문제**: 매일 쓰는 "수행 이력"이 화면 852px 아래에 있어 매번 스크롤해야 한다.
1920×1080 화면에서 좌우 여백이 크게 남는다.

**이렇게 한다**

```
┌─────────────────────────────────────────────┐
│ 과제명 + 상태·속성 배지 + 액션 버튼          │
│ 요약: 담당자 · 기간 · 기록 N건 · 마지막 보고  │
│       · 미보고 N건 · 첨부 N건(용량)          │
├───────────────────────┬─────────────────────┤
│ 과제 개요             │ 수행 이력            │
│ 보고 이력             │ (기록 추가 + 타임라인)│
│ 첨부 자료             │                     │
└───────────────────────┴─────────────────────┘
```

* 넓은 화면에서 좌우로 나누고, 좁은 화면(약 1200px 미만)에서는 위아래로 쌓는다.
* 상단 요약에는 각 영역의 핵심 숫자를 모아, 펼쳐 보지 않아도 상태를 알 수 있게 한다.

### 7. 검색 결과에서 해당 진행일지로 이동

### 16. 넓은 화면의 좌우 여백 활용 ⭐ ✅ 반영

**원인**: `main { max-width: 1180px }` 로 고정돼 있다. 글 읽기 좋은 폭으로 잡았는데,
2단으로 나누면서 각 칸이 절반으로 줄어 오히려 불편해졌다.

**제안**: 화면 폭에 따라 컨테이너를 넓힌다.
* 1440px 미만 — 지금처럼 (여백 24px)
* 1440~1920px — `min(100% - 48px, 1720px)`
* 2560px 이상 — 1720px에서 멈춘다 (더 넓히면 시선 이동이 너무 커진다)
* 과제 목록·검색·보고 대상 화면에도 같이 적용

이것만으로 우측(수행 이력) 칸이 604 → 약 940px, 편집 칸이 273 → 약 450px가 된다.

**반영 결과** (2026-09-02, 실측)

| 화면 | 본문 폭 | 좌측 | 우측 | 진행일지 편집 칸 |
|---|---|---|---|---|
| 1366px | 1180 (그대로) | 504 | 604 | 273 |
| 1440px | 1180 → **1440** | 623 | **745** | — |
| 1920px | 1180 → **1720** | 700 | **948** | 273 → **445** |
| 2560px | **1720** (여기서 멈춤) | 700 | 948 | — |

과제 목록 표도 1124 → **1664px**로 늘었다. 1440px 미만 화면은 손대지 않았다.
좌측 칸은 `min(45%, 700px)`으로 묶어, 넓어진 폭이 수행 이력 쪽으로 가게 했다.

### 17. 보고 이력 행에서 삭제 버튼이 잘림 ⛔ 결함 ✅ 반영

**원인**: 행이 `flex` 인데 내부 요소에 `min-width: 0` 이 없어 줄어들지 않는다.
피보고자 이름이 길면(예: "차세대전지 개발 주간 협의체") 그대로 밀려 나간다.

**고칠 것**: 행 내부를 줄어들 수 있게 하고, 긴 텍스트는 말줄임(…) 처리한다.
삭제 버튼은 항상 오른쪽 끝에 고정한다.

**반영 내용** (2026-09-02)
* 행과 그 내부에 `min-width: 0` 을 줘서 줄어들 수 있게 했다.
* 삭제 버튼은 `flex: 0 0 auto` + `margin-left: auto` 로 항상 오른쪽 끝에 고정.
* 피보고자 이름이 가장 먼저 줄고, 넘치면 말줄임(…) 처리한다. 마우스를 올리면 전체 이름이 뜬다.
* **보고 일시는 줄이지 않는다.** 자리가 정말 부족하면 행이 두 줄로 접힌다(잘리지 않는다).
* 검증: 1210 / 1366 / 1440 / 1600 / 1920 / 2560px 여섯 폭에서
  삭제 버튼이 항상 행 안쪽 11px에 있고, 가로 스크롤이 생기지 않는 것을 확인했다.
  피보고자 이름 45자짜리 극단값으로도 넘치지 않는다.

### 18. 진행일지 편집 칸이 좁다 ✅ 반영

**선택지**

**반영 내용** (2026-09-02) — (a)+(b) 둘 다 넣었다.

### 19. 보고 편집기가 가장 좁은 칸에서 열린다 ✅ 반영

### 20. 좁은 칸에서 큰 표가 넘칠 수 있다 (예방) ✅ 반영

지금 데이터의 표는 190px라 문제가 없지만, 칸이 좁아진 만큼 열이 많은 표는 넘친다.

## 22. 진행일지 본문의 이미지가 저장 후 안 보임 ⛔ 결함 ✅ 반영

**접수**: 2026-09-02 (사용자) — 작성 중 미리보기에는 이미지가 보이는데,

**고친 것**: 목록 화면이 진행일지에는 `logs` 기준을 쓰도록 나눴다.
렌더링하는 자리 다섯 곳을 모두 확인해 기준이 맞는지 점검했다.
실제로 이미지를 올려 목록에서 뜨는 것과 실패 요청이 0건인 것을 확인했다.

## 24. 대시보드에 담당자별 과제 수 ✅ 반영

**접수**: 2026-09-02 (사용자)

속성 칩처럼, **사람별로 몇 개의 과제를 맡고 있는지** 대시보드에 간략히 보여 준다.

```
상태  [예정 2][검토중 1][진행중 3][보류 1][완료 1]
속성  [스마트과제 2][R&D 1][투자 2][기획보고 1][국책과제 1][미지정 1]
담당  [권경락 4][김현우 2][박서준 2][미지정 1]        ← 이 줄을 새로 만든다
```

담당자 필터(`?owner=`)와 `meta.owners` 는 이미 있으므로, 대시보드에 세는 줄만 더하면 된다.
누르면 그 사람 과제만 걸러지고 다시 누르면 해제되는 것도 속성 칩과 같다.

**정할 것 — 구현 전에 답이 필요한 것들**

1. **합이 총 과제 수와 다르다.** 한 과제에 담당자가 여러 명일 수 있어서
   담당 칩의 합이 전체보다 커진다(예: 전체 8건인데 담당 합이 11). 상태·속성 칩은
   합이 딱 맞으므로, 같은 모양으로 두면 잘못 읽힐 수 있다.
   → 줄 앞 라벨을 `담당 (중복 포함)` 으로 두거나, 합이 다를 때만 작게 알려 주는 방법.
2. **사람이 늘면 줄이 길어진다.** 지금은 팀 규모가 작아 괜찮지만 15명이 되면 두세 줄이 된다.
   → 상위 N명만 세우고 `+N명`으로 접는 방법 (누르면 전체).
3. **끝난 과제를 넣을지.** "지금 누가 몇 개를 들고 있나"를 보려면 완료·중단은 빼는 편이 맞고,
   "올해 누가 몇 개를 했나"를 보려면 넣는 편이 맞다. 대시보드의 다른 칩은 전부 포함이므로
   기준을 섞으면 또 어긋난다 — 21번에서 겪은 문제.
   → 상태 칩과 같이 **전부 포함**으로 두고, 특정 상태를 함께 누르면 그 상태 안에서
     사람별로 보이게 하는 쪽이 일관된다(칩을 겹쳐 걸 수 있게).

**로드맵 R1과의 관계**: R1(인원별 과제 성과 관리)은 기간별 실적·보고 건수까지 보는 별도 화면이다.
여기 24번은 그 앞단의 "지금 몇 개"만 세는 한 줄이라 서로 겹치지 않는다.
다만 24번을 만들 때 담당자 집계를 서비스 계층에 두면 R1에서 그대로 쓸 수 있다.

---

**반영 내용** (2026-09-02) — 위 세 가지를 아래처럼 정해 넣었다.

```
담당 중복 포함  [권경락 6][이수민 2][최지훈 2][한도윤 2][담당자1 1]…[담당자4 1]  [+1명]
```

1. **합이 다를 때만 밝힌다.** 담당 칩의 합이 전체 과제 수보다 크면 라벨 옆에
   작게 `중복 포함` 이 붙는다. 한 사람이 한 과제씩만 맡고 있으면 아무것도 안 붙는다.
   (실측: 전체 8건 / 담당 칩 합 17건 → 문구 표시됨)
2. **8명까지 세우고 나머지는 `[+N명]` 으로 접는다.** 누르면 전부 펼쳐지고 `[접기]` 로 되돌아간다.
   조작 버튼이라 점선 테두리에 흐린 글씨로 두어 세는 칩과 구분했다.
3. **끝난 과제도 포함한다** — 상태·속성 칩과 같은 기준. 상태 칩과 겹쳐 걸 수 있으므로
   "진행중 + 권경락" 처럼 좁혀 보면 된다.

담당자가 없는 과제는 `미지정` 칩으로 세고, 눌러서 거를 수 있다(`owner=none`).
많이 맡은 사람부터, 같으면 이름순으로 세운다.

**검증**
* `test_numbers_match_what_the_list_filters` 에 담당 칩을 추가했다 —
  모든 담당 칩의 수가 실제 목록 필터 결과와 같은지 대조한다.
* 담당자별 집계·중복 합·미지정 처리에 테스트 3건을 더했다 (전체 125건 통과).
* 화면에서 실측: 권경락 칩 6건 → 목록 6행, 이수민 2건 → 2행, 미지정 1건 → 1행.
  `[+1명]` 펼치기·접기, 고른 칩 색(파란 배경 + 흰 글씨) 모두 확인. JS 오류 0건.

## 25. 대시보드 칩을 고르면 글자가 안 보임 ⛔ 결함 ✅ 반영

**접수**: 2026-09-02 (사용자)

두 가지가 함께 보고됐고, 둘 다 재현했다. 원인은 하나다.

* **속성 칩을 고르면** 아래 목록은 제대로 걸러지는데 **글자가 흰색이 되어 사라진다.**
  R&D 칩을 고르면 칩이 통째로 빈칸으로 보인다.
* **상태 칩을 고른 뒤 마우스를 올리면** 파란 배경에 파란 글씨가 되어 역시 안 보인다.
  (속성 칩도 같다)

**원인**: CSS 규칙 순서. `styles.css` 에서

```css
.dash-chip:hover:not(:disabled) { border-color: …; color: var(--accent); }   /* 414 */
.dash-chip.on   { background: var(--accent); color: #fff; }                  /* 415 */
.dash-chip.type { background: #f8fafc; }                                     /* 416 */
```

`.dash-chip.type` 과 `.dash-chip.on` 은 **우선순위가 같아** 뒤에 쓴 쪽이 이긴다.
그래서 고른 속성 칩(`dash-chip type on`)은 배경만 거의 흰색(#f8fafc)으로 되돌아가고
글자색은 흰색(#fff)이 그대로 남는다. 흰 바탕에 흰 글씨 — 명암비 1.04:1.

두 번째 문제도 뿌리가 같다. `.dash-chip:hover:not(:disabled)` 는 `:hover` 때문에
우선순위가 `.dash-chip.on` 보다 **높아서** 고른 칩의 글자색까지 덮어 버린다.
그래서 고른 칩에 마우스를 올리면 파란 배경에 파란 글씨가 된다.

**실측한 네 경우** (모두 확인함)

| 칩 | 마우스 | 배경 | 글자 | 결과 |
|---|---|---|---|---|
| 상태 칩 선택 | 뗌 | `rgb(47,111,235)` | `rgb(255,255,255)` | 정상 |
| **상태 칩 선택** | **올림** | `rgb(47,111,235)` | `rgb(47,111,235)` | **안 보임** |
| **속성 칩 선택** | 뗌 | `rgb(248,250,252)` | `rgb(255,255,255)` | **안 보임** |
| 속성 칩 선택 | 올림 | `rgb(248,250,252)` | `rgb(47,111,235)` | 흐리게 보임 |

**고친 내용** (2026-09-02)

```css
.dash-chip.type:not(.on) { background: #f8fafc; }              /* 고르지 않았을 때만 */
.dash-chip:hover:not(.on) { border-color: ...; color: ...; }   /* 고르지 않았을 때만 */
.dash-chip.on { background: var(--accent); color: #fff; }      /* 고른 칩은 이 규칙이 끝까지 쥔다 */
.dash-chip.on:hover { filter: brightness(0.92); }              /* 색은 그대로, 밝기만 */
```

고른 칩에도 마우스 반응은 남겨야 하므로, 색을 바꾸는 대신 밝기만 낮췄다.

**검증 — 여덟 경우 모두 실측** (WCAG 명암비)

| 칩 | 선택 | 마우스 | 배경 | 글자 | 명암비 |
|---|---|---|---|---|---|
| 상태 | 아니오 | 뗌 | `252,252,253` | `28,32,36` | 15.98 |
| 상태 | 아니오 | 올림 | `252,252,253` | `47,111,235` | 4.46 |
| 상태 | **예** | 뗌 | `47,111,235` | `255,255,255` | 4.57 |
| 상태 | **예** | **올림** | `47,111,235` | `255,255,255` | **4.57 (전 1.00)** |
| 속성 | 아니오 | 뗌 | `248,250,252` | `28,32,36` | 15.66 |
| 속성 | 아니오 | 올림 | `248,250,252` | `47,111,235` | 4.37 |
| 속성 | **예** | 뗌 | `47,111,235` | `255,255,255` | **4.57 (전 1.04)** |
| 속성 | **예** | 올림 | `47,111,235` | `255,255,255` | 4.57 |

고르지 않은 칩에 마우스를 올렸을 때(4.37 · 4.46)는 AA 기준 4.5에 살짝 못 미친다.
다만 이번에 바뀐 값이 아니고, 앱 전체의 링크가 같은 파란색을 쓰므로 여기만 바꾸면
오히려 어긋난다. 손대려면 `--accent` 를 앱 전체에서 함께 조정해야 한다.

> 21번을 만들 때 규칙을 이어 붙이며 순서와 우선순위를 확인하지 않아 생긴 것이다.
> 게다가 확인한 것도 "마우스를 뗀 상태의 상태 칩" 한 경우뿐이었다.
> 칩처럼 상태가 여러 겹인 요소(기본 / 선택 / 마우스 올림 / 선택+마우스 올림)는
> 조합을 빠짐없이 확인해야 한다.

## 26. 과제별 효과(정량·정성)와 산출 근거 ✅ 반영

**접수**: 2026-09-02 (사용자)

과제를 쓸 때 **효과성**을 적을 자리가 없다. 과제 상세(개요)에서 서술할 수 있어야 하고,
**과제 목록에서도 과제별 정량·정성 효과가 한눈에 보여야** 한다.

**지금 상태 — 정말로 빠져 있다**

과제 개요 템플릿은 네 개뿐이다: `배경` · `목표` · `산출물` · `관련 링크`.
"목표"는 *무엇을 달성하면 끝인지*이고 "산출물"은 *무엇을 남기는지*라서,
**"그래서 회사에 얼마의 이익인가"는 어디에도 없다.** front matter 필드에도, DB 컬럼에도 없다.
과제 관리 도구에서 이건 빠뜨리면 안 되는 축이다.

---

### 설계에서 먼저 정해야 할 것

#### (1) 시점을 나눠야 한다 — 이게 가장 중요하다 ⭐

R&D·투자 과제는 **착수할 때 기대효과**를 쓰고, **끝난 뒤 실적효과**를 확인한다.
이 둘을 한 칸에 쓰면 나중에 "예상은 얼마였고 실제로 얼마였나"를 되짚을 수 없다.
성과 관리(로드맵 R1)가 서려면 **두 값이 나뉘어 있어야** 한다.

| 시점 | 언제 채우나 | 쓰임 |
|---|---|---|
| **기대효과** | 과제 등록 시 | 과제 선정·우선순위 판단 |
| **실적효과** | 완료 보고 시 | 성과 집계, 다음 과제의 추정 근거 |

→ 제안: 두 벌을 따로 두되, **실적효과는 비어 있어도 정상**으로 취급한다(진행 중인 과제).

#### (2) 정량 효과를 얼마나 구조화할 것인가

**목록에 세우고 합계를 내려면 자유 텍스트로는 안 된다.** 그렇다고 과하게 쪼개면 입력이 번거롭다.

| 안 | 형태 | 장점 | 단점 |
|---|---|---|---|
| A. 자유 텍스트 한 줄 | `연 1.2억원 절감` | 입력이 가장 쉽다 | 목록 정렬·합계 불가. 단위 표기가 제각각이 된다 |
| B. **금액 + 자유 지표** | `effect_krw: 120000000` + `effect_metric: "수율 +2.1%p"` | 금액은 합계·정렬 가능, 나머지는 자유롭게 | 필드가 둘로 늘어난다 |
| C. 완전 구조화 | 지표명·값·단위·기준연도를 각각 | 무엇이든 집계 가능 | 입력이 번거로워 결국 안 쓰게 된다 |

→ **B안을 제안한다.** 금액은 어차피 대부분의 과제가 환산해서 보고하므로 합칠 수 있고,
수율·시간 같은 지표는 과제마다 달라 자유 입력이 맞다.

#### (3) 산출 근거는 별도 칸이 필요하다 ⭐

**숫자만 있고 근거가 없으면 보고 자리에서 방어하지 못한다.**
"연 1.2억"이 어떤 가정과 계산에서 나왔는지(단가 × 물량 × 개선율 등)를 적는 칸을 반드시 함께 둔다.
길어질 수 있으므로 개요 문서의 서술 영역에 두고, 목록에는 **근거 유무만 표시**한다
(근거 없는 숫자에 작은 표시를 달아 두면 채우게 된다).

#### (4) 목록에서 어떻게 보여줄 것인가

과제 목록은 이미 9개 열이라 더 넣으면 좁아진다.

* 열 하나만 추가해 **정량 효과를 요약 표기** (`연 1.2억` · 실적이 있으면 `1.2억 → 1.4억`)
* 정성 효과는 **말줄임 + 마우스 올리면 전체** (담당자·피보고자와 같은 방식)
* 근거가 없으면 숫자 옆에 옅은 표시
* 정렬에 **효과 큰 순** 추가 → "어느 과제가 회사에 가장 큰 이익인가"를 바로 볼 수 있다

#### (5) 대시보드·집계와의 관계

* 대시보드에 **`올해 기대효과 합계 / 실적효과 합계`** 한 줄을 더할 수 있다.
  단, 21번에서 겪었듯 **세는 기준과 거르는 기준이 같아야** 한다 (중단된 과제를 넣을지 등).
* 로드맵 **R1(인원별 성과 관리)** 의 "성과의 정의"가 여기서 절반은 정해진다.
  → R1을 시작하기 전에 이 항목을 먼저 하는 편이 순서가 맞다.

---

### 예상 작업

| 범위 | 내용 |
|---|---|
| 개요 템플릿 | `## 기대효과` · `## 산출 근거` 절 추가 (기존 과제는 비어 있어도 정상) |
| front matter | 정량·정성 효과 필드 (기대/실적 두 벌) |
| DB · 색인 | 컬럼 추가 → 스키마 버전 올려 재색인 (3 → 4) |
| 과제 등록·수정 화면 | 입력 칸. 근거 없이 숫자만 넣으면 안내 |
| 과제 목록 | 효과 열 + 효과순 정렬 |
| 과제 상세 | 요약 바에 효과 표시 |
| 대시보드 | (선택) 기대/실적 합계 한 줄 |

**규모**: M (1~3일). 스키마가 바뀌므로 **데이터가 더 쌓이기 전에 하는 편이 싸다.**

### 사용자가 정한 것 (2026-09-02)

1. **금액 단위 = `억원/년`** — 사내에서 쓰는 표기를 그대로 따른다
2. **`기대효과` / `실증효과`** — 실제로 쓰는 용어다 ('실적효과'가 아니라 **실증**효과)
3. **정성 효과는 자유 문장**, 필요하면 엑셀·PPT를 첨부

## 반영 내용 (2026-09-02)

**정량 — front matter 에 숫자로**

```yaml
effect_expected: 1.2      # 기대효과 (억원/년)
effect_verified: 1.45     # 실증효과 — 과제가 끝나야 나오므로 대개 비어 있다
```

숫자로 두어야 목록 정렬과 합계가 된다. `EFFECT_UNIT` 은 `config.py` 한 곳에 두고
화면이 그것을 가져다 쓴다 (단위를 바꿀 일이 생기면 한 줄만 고친다).

**정성 · 근거 — 개요 문서에 서술**

과제 개요 템플릿에 두 절을 더했다. 길어질 수 있고 첨부와 함께 봐야 하는 내용이라 본문이 맞다.

* `## 정성적 효과` — 품질 향상, 리스크 저감, 기술 확보 등
* `## 효과 산출 근거` — 단가 × 물량 × 개선율, 가정, 출처

**개요에 직접 파일을 붙일 수 있게 했다** (`POST /api/projects/{id}/attachments`)
지금까지 첨부는 진행일지와 보고에만 붙었다. 효과 산출 근거(엑셀·PPT)는 특정 진행일지가 아니라
**과제 자체에 딸린 자료**라 붙일 자리가 없었다. 개요 카드에 [📎 파일 첨부] 를 두고
`assets/과제/` 아래에 모은다. 끌어다 놓아도 된다. 올리면 개요 본문 끝에 링크가 붙는다.

**목록 표시**

| 값 | 표기 | 뜻 |
|---|---|---|
| 기대 1.2 · 실증 1.45 | **1.2 → 1.4** (진하게) | 실증까지 확인됨 |
| 기대 5.0 만 | 5 (흐리게) | 아직 실증 전 |
| 둘 다 없음 | — | 미입력 |

정렬에 **효과 큰 순**을 더했다. 실증효과가 있으면 그것을, 없으면 기대효과를 기준으로 본다
(기대 9.0 이었지만 실증 1.0 인 과제는 1.0 자리에 놓인다). 효과를 안 적은 과제는 맨 뒤로 —
0으로 취급하면 실제로 효과가 0인 과제와 섞인다.

과제 상세 요약 바에도 `효과 억원/년 | 1.2 → 1.4` 로 한 칸을 더했다.

**비어 있는 것과 0은 다른 뜻이다.** 전자는 "아직 안 정했다", 후자는 "효과가 없다".
그래서 폼에서 칸을 비우면 `null` 로 보낸다. 이를 위해 `ProjectUpdate.changes()` 를
`exclude_unset=True` 로 바꿨다 — 보내지 않은 항목만 건너뛰고, 보낸 `null` 은 비우겠다는 뜻으로 받는다.
(전에는 어떤 항목도 지울 수 없었다)

**검증**

* 테스트 10건 추가, 전체 **135건 통과**. 왕복 저장, 기대/실증 분리, 빈 값과 0의 구분,
  값 지우기, 음수 거부, 효과순 정렬, 손으로 고친 파일에 숫자가 아닌 값이 들어와도 색인이
  멈추지 않는지, 과제 단위 첨부까지 다룬다.
* 스키마 3 → 4. **기존 vault 로 그대로 올려** 색인이 자동으로 다시 만들어지고
  과제 8건이 그대로 읽히는 것을 확인했다.
* 화면에서 목록 열·정렬·요약 바·입력 폼을 눈으로 확인했다.
* 개요 첨부는 **끌어다 놓기 경로로 끝까지 확인**했다(업로드 → 개요 본문에 링크 추가).
  [파일 첨부] 버튼 경로는 브라우저 자동화로 확인하지 못했는데, **기존 진행일지의
  같은 버튼도 자동화에서는 똑같이 반응하지 않는다** — 도구 쪽 한계이지 결함이 아니다.
  두 버튼은 같은 방식이고 진행일지 쪽은 실사용에서 확인된 경로다.

### 27. 엑셀 표 → 마크다운 표 ✅

엑셀·구글시트에서 셀을 복사하면 클립보드에 **탭으로 나뉜 텍스트**가 담긴다.
붙여넣을 때 그것을 알아보고 마크다운 표로 바꿔 넣는다.
진행일지 · 보고 문서 · 과제 개요 세 편집기 모두에 넣었다.

표로 볼 조건을 좁게 잡았다 — **두 줄 이상 + 모든 줄의 탭 개수가 같을 것.**
열이 하나뿐이면 그냥 여러 줄 텍스트라 건드리지 않는다. 셀 안의 `|` 는 벗어나게 하고
줄바꿈은 `<br>` 로 바꾼다. 첫 줄은 머리글로 본다(엑셀에서 대개 머리글부터 잡기 때문).

### 28. 진행일지 서식 ✅

기본 서식은 **`## 내용` · `## 진행` · `## 계획`** 세 줄이다 (2026-09-02 사용자 확정).

빈칸에서 시작하면 무엇을 적을지부터 고민하게 된다. **설정 → 진행일지 서식**에서
공통 서식과 **과제 속성별 서식**을 따로 둘 수 있다.
찾는 순서는 `속성별 → 공통 → 코드의 기본값` 이고, 비우면 한 단계 위로 되돌아간다.
서식이 있는 속성은 선택 목록에 `✓` 로 표시된다.

### 29. 보고 초안 서식 ✅

`## 보고 요약 / 특이사항 및 이슈 / 다음 계획` 이 코드에 박혀 있어 회의체마다 양식이
다르면 매번 손으로 고쳐야 했다. 설정에서 바꿀 수 있게 했다.

`{summary}` 자리에 마지막 보고 이후의 진행일지가 들어간다.
**`{summary}` 가 없으면 진행 내용이 통째로 사라지므로**, 화면에서 경고하고
그래도 저장하면 서버가 기본 서식으로 되돌린다(조용히 내용을 잃는 것보다 낫다).

### 30. 지난 기록 이어쓰기 ✅

기록 카드마다 **[이어쓰기]** 를 뒀다. 누르면 그 기록의 내용을 담아 **오늘 날짜로**
새 편집기가 열린다. 연속된 시험·측정에서 같은 표를 매번 다시 그리지 않아도 된다.

### 31. 수행 이력에 보고 시점 마커 ✅

**설계 문서 5.1 에 적어 놓고 빠뜨렸던 것.** 진행일지마다 "어느 확정 보고에 담겼는지"를
함께 내려 주고(`reported_on`), 타임라인에 `── 여기까지 2026-08-25 보고함 ──` 선을 긋는다.
기록이 최신순이므로 **선 위는 미보고, 아래는 보고 완료**다. 목록을 보는 것만으로
미보고 분량이 눈에 들어온다. 작성 중인 초안은 세지 않는다 — 아직 보고한 것이 아니다.

### 32. 삭제 복구 화면 ✅

지금까지 지운 것은 `.trash/` 로 옮겨졌지만 **어디서 왔는지가 남지 않아**,
되돌리려면 탐색기로 폴더 구조를 짚어 가며 손으로 옮겨야 했다.

옮길 때마다 `.trash/manifest.jsonl` 에 한 줄씩 적는다 — 무엇을, 언제, 어디서.
되돌리기는 그 줄을 거꾸로 읽는 일이다. JSONL 인 이유는 **덧붙이기만 하면 되기 때문**이다.
중간에 멈춰도 앞선 줄은 멀쩡하고, 한 줄이 깨져도 그 줄만 건너뛴다.

* 과제 · 진행일지 · 보고 문서 · 첨부 네 가지 모두 되돌린다.
* **덮어쓰지 않는다.** 지운 자리에 새 기록이 생겼으면 `-복구` 를 붙여 옆에 놓는다.
* 이 기능이 생기기 전에 지운 항목도 **숨기지 않고** 보여 준다(되돌리기는 안 되고 `수동` 표시).
  되돌리지는 못해도 무엇이 들어 있는지는 알아야 한다.
* `trash_name` 은 사용자가 보내는 값이라 보관함 밖을 가리키지 못하게 막고, 테스트로 고정했다.

## 38. 과제 번호 체계 · 담당자 명부 · 과제 생성자 — 미리 준비 ✅ 반영

**접수**: 2026-09-02 (사용자)

여러 팀장이 함께 쓰는 것(R2)은 **1인 사용이 정리된 뒤에** 고민하기로 했다.
다만 이 둘은 **데이터 구조가 걸린 일이라 지금 준비해 두는 편이 싸다.**
과제가 쌓인 뒤에 바꾸면 이관 작업이 붙는다.

### 38-1. 과제 번호 체계

지금은 `2026-001`. 팀장이 여럿이면 번호가 겹친다.

**준비 방식** — 설정에 **번호 앞자리(팀·부문 코드)** 를 둔다.
* 비워 두면 지금 그대로 `2026-001`
* `소재` 를 넣으면 이후 만드는 과제가 `2026-소재-001`
* **이미 만든 과제 번호는 바꾸지 않는다.** 번호는 식별자라 섞여도 문제없고,
  바꾸면 폴더명·링크가 모두 흔들린다.
* 지금 해 둘 일은 **두 형태를 모두 읽을 수 있게 만드는 것**. 그래야 나중에
  코드만 정하면 바로 쓴다.

### 38-2. 담당자 명부 (이름 ↔ 계정 매핑의 앞단계)

지금 담당자는 그냥 문자열이라 `권경락` / `권 경락` / `권경락 책임` 이 따로 쌓인다.
**지금도 문제이고**, 나중에 계정을 붙일 때는 더 큰 문제가 된다.

**준비 방식** — 설정에 **담당자 명부**를 둔다.
* 표준 이름 목록. 과제 등록 화면의 자동완성이 이 목록을 쓴다.
* 명부에 없는 이름을 넣으면 **막지 않되** "명부에 없는 이름입니다 — 추가할까요?" 로 물어본다.
  (막으면 급할 때 못 쓴다. 묻기만 한다) — **2026-09-02 사용자 확정**
* 각 사람에 **사번·계정 칸을 비워 둔 채로** 만들어 둔다. R2 에서 로그인이 생기면 그 칸만 채우면 된다.
* 이미 쓰인 표기가 명부와 다르면 **한 번에 바꾸는 기능**을 함께 둔다 (파일까지 반영).

**남은 것**: 명부를 설정 화면에 둘지 별도 화면으로 뺄지 — 만들 때 정한다.

### 38-3. 과제 생성자 기록 — *새로 찾은 것*

**진행일지에는 작성자가 있는데 과제에는 "누가 만들었는지"가 없다.**
`id · title · status · type · group · tags · owners · 기간 · 효과 · created_at · updated_at` 뿐이다.

* **담당자(owners)와 생성자는 다르다.** 담당자는 "누가 하는가", 생성자는 "누가 등록했는가"다.
* R2 의 권한("내 과제는 수정, 남의 과제는 읽기")은 **생성자 없이는 성립하지 않는다.**
* **소급이 안 된다.** 나중에 넣으면 그 전 과제는 생성자가 영영 빈칸이다.
  진행일지 작성자를 "지금부터 넣어야 나중에 성과 집계가 반쪽이 되지 않는다"고 했던 것과 같은 이유다.

**준비 방식** — 과제를 만들 때 `created_by` 에 **설정의 작성자**를 적는다.
로그인이 생기면 그 자리에 로그인 사용자가 들어온다. 화면에 굳이 드러내지 않아도 되고,
지금은 **기록만 해 두면 된다.** 비용이 거의 없다.

* **숫자만으로 된 코드는 거부한다** — 일련번호와 구분되지 않는다.

## 37. 데이터 안전망 — 로컬 전용 방식으로 (git 제외)

**접수**: 2026-09-02 (사용자) · **상태**: **안쪽(37-1) ✅ 반영 (2026-09-03)** · 바깥(T21) 대기

> **2026-09-02 사용자 판단**: *"안전망보다 데이터를 먼저 잘 쌓을 수 있게 하는 것이 우선"*
> → 38번(사전 준비)과 1인 완성도 작업 뒤로 미룬다. 방식과 설계는 아래대로 확정해 둔다.

**T20(vault 를 git 저장소로) 은 제외한다.** 사용자 판단을 따른다.

> 참고로 **원격을 등록하지 않은 로컬 git 은 밖으로 아무것도 보내지 않는다.**
> `git init` 만 한 폴더는 그 PC 안에서만 동작한다. 다만 사내에서 git 자체가
> 외부 서비스로 인식될 여지가 있고, 굳이 그 오해를 안고 갈 이유가 없다.
> 목적은 "잃지 않기"이지 git 이 아니므로 **다른 방식으로 같은 목적을 달성한다.**

**대신 할 것 — 두 겹의 안전망**

| 겹 | 무엇 | 막아 주는 것 |
|---|---|---|
| 안쪽 | **저장할 때 이전 버전을 남긴다** (`.versions/`) | 잘못 고쳤거나 덮어쓴 것 |
| 바깥 | **자동 백업 스케줄** (T21) | PC 고장·분실, 폴더 통째 사고 |

둘은 대체재가 아니다. 안쪽은 "어제 내용으로 되돌리기", 바깥은 "PC가 죽었을 때"다.

**안쪽 설계 초안**
* 진행일지·개요·보고를 저장할 때, **바뀌기 전 내용**을
  `vault/.versions/<과제폴더>/<파일명>/<저장시각>.md` 로 남긴다.
* 전부 텍스트라 용량은 미미하다. **기본 1년 보관** (2026-09-02 사용자 확정), 설정에서 조절.
* 되돌리기 화면은 **32번(삭제 보관함)과 같은 방식**으로 붙인다 — 목록 → 미리보기 → 되돌리기.
* 외부로 나가는 것은 없다. 폴더 하나가 늘 뿐이다.

**남은 것**: 되돌리기를 문서별로 둘지 설정에 모아 둘지 — 만들 때 정한다.

---

### 37-1 반영 (2026-09-03)

**"되돌리기를 어디에 둘지"는 문서별로 정했다.** 설정 화면까지 찾아가게 하면 정작
필요한 순간에 못 쓴다. 진행일지·과제 개요·보고 문서 각각에 **[이전 버전]** 단추를 두고,
같은 화면에서 목록 → 내용 보기 → 되돌리기까지 끝낸다. 설정에는 **현황만** 둔다
(몇 벌이 자리를 얼마나 쓰는지 — 안전망이 조용히 커지고 있지 않은지 볼 자리).

**어디에 걸었나**: `markdown.save()` **한 곳**. 문서를 쓰는 길이 전부 이 함수로 모이므로
(호출 12곳), 여기에 걸면 진행일지·개요·보고가 한 번에 지켜진다.

**남기는 모습** — 폴더 구조를 그대로 흉내 낸다. 탐색기로 열어도 무엇인지 알 수 있어야 한다.

```
vault/.versions/projects/2026-001-리튬전지-수명평가/logs/2026-09-01-1차-시험.md/
    2026-09-04_013455.md
    2026-09-04_013455-2.md
```

**정한 규칙 다섯**

1. **새로 만드는 파일은 남기지 않는다** — 남길 이전 내용이 없다.
2. **달라지는 것이 없으면 남기지 않는다.** `updated_at` 은 저장할 때마다 바뀌므로
   그것만 다른 두 벌은 같은 문서로 본다. 아니면 저장 단추만 눌러도 버전이 쌓인다.
3. **되돌리기도 하나의 저장이다.** 지금 내용이 먼저 버전으로 남아, 되돌린 것이
   잘못이었어도 다시 되돌릴 수 있다.
4. **한 문서당 200벌 · 365일** 상한. 안전망 자신이 무한정 자라면 안 된다.
5. **실패해도 저장을 막지 않는다.** `keep()` 안에도, 부르는 자리에도 방어를 두었다 —
   나중에 안이 바뀌더라도 저장만은 반드시 되도록.

**만들면서 잡은 것 셋** (전부 시험이 잡았다)

* 보관 폴더 이름이 `…시험.md` 로 끝나 **폴더를 버전으로 세고 있었다** (현황이 2배로 나옴).
* 같은 초에 여러 벌이 남으면 **목록에 똑같은 시각이 여러 줄** 보여 구분이 안 됐다 →
  `(2)` `(3)` 을 함께 보인다.
* 저장 직전 내용만 보고 중복을 걸렀더니, `updated_at` 때문에 **한 번도 걸리지 않았다** →
  새로 쓸 내용과 비교하도록 바꿨다.

## 35. 보고 완료 마커를 어디에 그을지 ✅ 반영

**접수**: 2026-09-02 (사용자) · **반영**: 2026-09-04

31번을 넣을 때 기준을 **"그 기록이 확정 보고에 담겼는가"** 로 잡았다.
동작은 하지만, 기준을 정하지 않고 만든 부분이 있어 다시 볼 필요가 있다.

**지금 규칙**
* 기록마다 그것이 담긴 **가장 이른 확정 보고**의 날짜를 붙인다.
* 목록은 날짜 내림차순이고, 그 값이 바뀌는 지점마다 선을 긋는다.
* 선 위는 미보고, 아래는 보고 완료.

**따져 볼 것**

1. **뒤늦게 쓴 지난 날짜 기록.** 8/25 보고를 확정한 뒤 8/20자로 기록을 추가하면,
   날짜순으로는 선 **아래**에 놓이는데 실제로는 **미보고**다.
   지금 구현은 이때 선이 두 번 그어진다. 이게 맞는 표현인지, 아니면
   "미보고" 표시를 기록 자체에 붙이는 편이 나은지.
2. **기준을 보고일로 볼 것인가, 담김 여부로 볼 것인가.** 지금은 담김 여부다.
   보고일 기준으로 하면 1번 경우가 단순해지지만, **보고에서 일부러 뺀 기록**이
   보고한 것처럼 보인다.
3. **여러 보고에 담긴 기록** — 지금은 가장 이른 보고를 쓴다. 마지막 보고가 나을 수도 있다.
4. **보고가 여러 건일 때 선을 몇 개 그을 것인가** — 지금은 보고마다 하나씩.
   보고 이력이 쌓이면 선이 많아진다. 가장 최근 보고 하나만 긋는 편이 나을 수도.

→ **2026-09-04 사용자 결정: 추천 방식(① 딱지 + ④ 선 하나)으로 진행.**

**반영한 것 둘**

*① 보고 여부를 기록 자체에 붙인다* — 미보고 기록에 **[미보고]** 딱지가 붙는다.
선만으로는 "8/25 보고를 확정한 뒤 8/20 자로 쓴 기록"을 표현할 수 없었다.
날짜순으로는 선 **아래**(보고한 것처럼 보이는 자리)에 놓이는데 실제로는 미보고이기
때문이다. 딱지는 그 기록이 어디에 놓이든 정확하다.

*④ 선은 가장 최근 보고 하나만* — 보고마다 그으면 이력이 쌓일수록 선이 늘어
정작 경계가 안 보인다. 개별 기록의 보고 여부는 딱지가 말해 주므로 선은 하나면 된다.

**②③ 은 그대로 둔다.** 기준은 여전히 "확정 보고에 담겼는가"이고(보고에서 일부러 뺀
기록이 보고한 것처럼 보이면 안 된다), 여러 보고에 담긴 기록은 가장 이른 보고를 쓴다.
①에서 딱지가 정확해졌으므로 이 둘을 바꿀 이유가 사라졌다.

  고치려면 확정을 먼저 풀어야 한다(피보고자·제목과 같은 규칙).
* 제목이 기본값(`2026-09-08 보고`)이면 날짜를 따라가고, 직접 쓴 제목은 건드리지 않는다.

**만들면서 함께 잡은 것 — 폴더를 옮기면 보고 id 가 바뀌던 문제**

잃고, 어떤 진행일지를 담았는지도 끊긴다. 옮기기 **전에** 경로를 먼저 갱신해 id 를 지켰다.
첨부 경로도 함께 옮긴다. (진행일지 이름 변경에서 같은 문제를 겪고 고쳤던 것과 같은 패턴)

## 46. 오류 기록 남기기 (T52) ✅ 반영

**접수**: 2026-09-03 (사용자 — 1·3층만, 2층은 보류)

지금까지 뭔가 잘못되면 **흔적이 남지 않았다.** 검은 창이 닫히면 끝이고 화면에는

**1층 · 파일로 남기기** — `vault/.logs/error-YYYY-MM.log` (JSONL, 한 달에 파일 하나)

* **기록에 실패해도 사용자의 동작을 막지 않는다.** 오류를 적다가 나는 오류 때문에
  저장이 막히면 본말이 뒤바뀐다.

**3층 · 설정 화면의 [최근 오류]** — 파일을 탐색기로 찾지 않고 화면에서 본다.

## 48. 뒤로 가기가 원래 있던 화면으로 ✅ 반영 (가·나 모두)

**접수**: 2026-09-03 (사용자)

> 보고 대상이나 보고 이력에서 과제를 클릭하면 과제 상세가 나오는데, 검토를 마치고
> 돌아가려면 메뉴를 다시 눌러야 해. 뒤로 가기가 "과제 목록"으로만 나오기 때문이지.
> 원래 선택했던 메뉴로 돌아가게 하는 방법이 있을까?

**현재**: `ProjectDetail.tsx:196` 의 뒤로 가기가 `href="#/"` 로 고정되어 있다.
과제 상세로 들어오는 길은 **5곳**(메인 대시보드·보고 대상·보고 이력·검색 결과·과제 목록)
인데 어디서 왔든 늘 과제 목록으로 보낸다.

**검토한 세 가지**

| 방식 | 판단 |
|---|---|
| ① 클릭 이력을 sessionStorage 에 기록 | **권하지 않음.** 화면 상태와 주소가 따로 논다 — 새로고침·주소 복사·탭 두 개에서 어긋나고, 재현이 안 되는 버그가 난다 |
| ② `history.back()` | **권하지 않음.** 주소를 직접 열면 앱 밖으로 나가고, 상세 안에서 진행일지를 열고 닫은 것까지 이력에 쌓여 엉뚱한 데로 간다 |
| ③ **주소에 출처를 실어 보낸다** (`?from=history`) | **이것으로 한다** |

**③ 을 고른 이유**: 기억할 것이 없다. 어디서 왔는지가 주소 안에 있으니 새로고침해도,
주소를 복사해 붙여도, 탭을 여러 개 띄워도 항상 맞다. 게다가 이 앱은 이미 `?report=12`,
`?entry=3` 을 같은 방식으로 쓰고 있어(`App.tsx:23`) **새 개념이 아니라 있던 규칙을
한 칸 넓히는 일**이다.

```
#/projects/2026-001?from=history          →  ← 보고 이력
#/projects/2026-001?report=12&from=reports →  ← 보고 대상
#/projects/2026-001                        →  ← 과제 목록 (지금과 같음)
```

**할 일**: 링크 8곳(`Dashboard`·`ReportCandidates`×3·`ReportHistory`·`SearchResults`×3)에
`from` 을 붙이고, 뒤로 가기가 그 값으로 주소와 문구를 함께 바꾸게 한다. **규모 S.**

**함께 정해야 할 것 — 돌아갔을 때 거른 조건**

보고 이력에서 피보고자·기간으로 걸러 놓고 과제를 열었다가 돌아오면, 화면은 맞게 돌아가도
**거른 조건은 초기화된다**. 이것까지 살리려면 조건도 주소에 실어야 한다
(`#/history?audience=전사 주요업무 보고&from=2026-08-01`). 덤으로 자주 보는 조건을
즐겨찾기해 둘 수 있게 된다.

- **(가) 화면만 제대로 돌아가게** — 규모 S
- **(나) 거른 조건까지 그대로** — 규모 M

→ **2026-09-03 사용자 판단: 전체 메뉴에 대해 가·나 모두 반영.**

---

**반영한 것**

*(가) 온 곳으로 돌아간다* — 들어오는 길 8곳 전부에 `back` 을 실었다.
`Dashboard` · `ReportCandidates`(3곳) · `ReportHistory` · `SearchResults`(3곳) ·
`ProjectList` · `ProjectBoard`. 뒤로 가기는 주소와 문구를 함께 바꾼다.

| 온 곳 | 뒤로 가기 |
|---|---|
| 보고 대상 | ← 보고 대상 |
| 보고 이력 | ← 보고 이력 |
| 검색 결과 | ← 검색 결과 |
| 그 외 | ← 과제 목록 (지금까지와 같음) |

*(나) 거른 조건이 주소에 산다* — 세 화면 모두.

* **과제 목록**: 상태·속성·그룹·태그·담당·마감·정렬
* **보고 대상**: 보고 예정일 · 보류·완료 포함 여부
* **보고 이력**: 피보고자 · 기간 · 검색어 · 상태

덤으로 **주소만으로 걸러진 화면을 열 수 있다.**
`#/history?audience=전사 주요업무 보고` 을 즐겨찾기해 두면 매번 조건을 다시 넣지 않아도 된다.

**만들면서 정한 것 셋**

1. **조건 바꾸기는 방문 기록을 남기지 않는다** (`replaceState`).
   조건 하나 고를 때마다 기록이 쌓이면 브라우저 뒤로가기를 열 번 눌러야 화면을 벗어난다.
   조건 바꾸기는 "이동"이 아니라 "지금 화면을 다듬는 일"이다.
2. **상세 → 상세로 이어져도 온 곳을 물려준다.** 그러지 않으면 되돌아갈 곳이
   상세 자신이 되어 제자리를 맴돈다 (`nav.ts` `projectLink`).
3. **주소가 화면을 속이지 않게 한다.** `#/?status=done` 에서 상단 [과제] 메뉴를 누르면
   주소는 `#/` 가 되는데, 조건이 화면에 남아 있으면 주소와 화면이 어긋난다.
   밖에서 주소가 바뀌면 조건을 그 주소에 맞춘다 (`useAddressBar`).

**화면 시험 9건 추가** (17 → 26). 뒤로 가기를 예전처럼 고정해 두면 실제로 실패하는 것까지
확인했다.

## 50. 주간 보고 요일을 설정에서 고르기 ✅ 반영

def default_report_date(today=None):

**반영 (2026-09-03)** — 설정 › 주간 보고 요일. 기본값은 지금까지와 같은 **화요일**이라

* 설정 파일이 깨져 있어도 기본값으로 물러난다 — 보고 예정일을 못 구해 도구가 멈추면 안 된다.

## 52. 보고 대상 목록을 대시보드에서 보고 대상 메뉴로 + 정렬 기준 손보기 ✅ 반영

**접수**: 2026-09-03 (사용자)

> 과제 메뉴에서 보고 대상 과제 목록 5개를 보여주는 부분을 보고 대상 메뉴로 이동할 것.
> 그리고 보고 이력 없음이 가장 상단에 있고, 그다음부터는 마지막 보고가 가장 오래된 것
> (D+100이 D+150보다 후순위)부터 하는 것이 맞는 것 같아.

> **2026-09-03 사용자 결정**: 홈 화면은 아직 설계가 없고 **다른 용도**로 생각 중이므로,
> 보고 대상 목록은 **보고 대상 메뉴에 두는 것이 맞다.** (56과의 연결 해제)

**52-1. 자리 옮기기**

지금은 대시보드(과제 화면 상단)에 상위 5건이 서 있다(`Dashboard.tsx`). 보고 대상 메뉴에는
같은 자료가 표로 전부 있으니 **한 자료가 두 곳에 있는 상태**다. 옮기는 데 동의.

착수 전 정할 것: 대시보드에서 뺀 뒤 **[보고 대상 N건] 같은 링크는 남길지**.
완전히 없애면 과제 화면에서 보고 주기로 넘어가는 길이 상단 메뉴뿐이 된다.

**반영 (2026-09-03)**

*52-1* — 대시보드에서 목록을 빼고 **[보고 대상 N건 보기 →]** 링크만 남겼다.
같은 자료가 두 곳에 있으면 한쪽만 고쳐져 어긋나기 쉽다.

*52-2* — 점수 계산을 걷어내고 **규칙 그대로** 줄을 세운다.

1. 한 번도 보고하지 않은 과제가 맨 위 (시작이 오래된 것부터)
2. 그다음은 **마지막 보고가 오래된 것부터**, **상한 없이**
3. 같으면 미보고가 많은 쪽, 그래도 같으면 과제 번호

경과일 상한(주기×8=56일)과 "진행 없으면 ×0.25" 계수를 **둘 다 없앴다.**
전자는 D+100 과 D+150 을 같게 만들었고, 후자는 오래 방치된 과제를 아래로 밀었다.
"오래된 것이 먼저"라는 규칙에 예외를 두면 그 순간 규칙이 아니게 된다.

**52-2. 정렬 — 지금 왜 그렇게 나오는지 원인을 확인했다**

`reports.py:302` 의 점수 계산에 두 가지가 걸려 있다.

```python
elapsed_term = min((days_since or 0) / cycle, MAX_ELAPSED_TERM)   # 상한 8.0
if not unreported:
    elapsed_term *= IDLE_PENALTY                                   # 0.25배
score = elapsed_term + len(unreported) * 0.5
```

**① 경과일에 상한이 있다.** `MAX_ELAPSED_TERM = 8.0` × 주기 7일 = **56일**.
그래서 **D+100 과 D+150 이 똑같이 8.0 으로 취급된다.** 말씀하신 그대로다 —
그 뒤로는 미보고 건수와 과제 번호 순서가 자리를 정한다.

> 예: D+150·미보고 0건 → 8.0 × 0.25 = **2.0**
> 　　D+100·미보고 3건 → 8.0 + 1.5 = **9.5**  ← 더 오래됐는데 아래로 간다

상한을 둔 것은 "오래 방치된 과제가 목록을 독점하지 않게" 하려던 것인데,
**보고 순서를 정하는 자리에서는 오히려 방해**가 된다.

**② 보고 이력이 없는 과제가 위로 오지 않는다.**
기준일이 `last_reported_at or start_date or created_at` 이라, 갓 만든 과제는
`days_since` 가 작고 미보고 진행일지도 없어 `× 0.25` 까지 먹는다.
→ 점수가 0.1 아래로 떨어져 **맨 아래**에 선다. "한 번도 보고 안 한 과제"가
가장 먼저 보여야 한다는 요청과 정반대다.

**손볼 방향 (착수 때 확정)**

1차 정렬을 **보고 이력 없음 → 있음**으로 나누고, 각 묶음 안에서 정렬한다.

| 묶음 | 정렬 |
|---|---|
| 보고 이력 없음 | 과제 시작일이 오래된 것부터 (오래 방치된 것이 먼저) |
| 보고 이력 있음 | **마지막 보고가 오래된 것부터** (D+150 → D+100), 상한 없이 |

미보고 진행일지 수를 점수에 섞을지는 다시 봐야 한다. 섞으면 "쓸 거리가 많은 과제"가
올라와 편하지만, 말씀하신 **"오래된 것부터"** 라는 단순한 규칙이 깨진다.
→ **동점일 때만 미보고 건수로 가르는** 쪽이 규칙이 명확할 것 같다. 착수 때 확인.

**주의**: 점수 계산을 바꾸면 `test_candidates_are_capped_and_ordered`,
`test_candidate_carries_what_the_row_shows` 등 기존 시험이 함께 바뀐다.
보고 대상 화면의 "점수" 칸과 화면 아래 설명 문구도 같이 손봐야 한다.

**반영 (2026-09-03)** — 과제 목록과 보고 대상, 두 표 모두.

* 열 이름을 누르면 그 열로 정렬하고, **다시 누르면 방향이 바뀐다.** 두 방향만 돈다.
* **세 번 돌려 해제하는 방식은 쓰지 않았다** (아래 논의 1번). 대신 보고 대상 표 위에
  **[기본 순서로]** 를 두었다. 정렬을 걸지 않았을 때는 그 자리에
  `기본 순서 · 보고 이력 없음 → 오래된 보고 순` 이라고 적어 둔다 (논의 2번).
* **[점수] 열은 없앴다** (논의 3번). 기본 순서가 더는 점수순이 아니라, 아무 데도 쓰이지
  않는 숫자가 됐다.
* **빈 값은 어느 방향에서나 뒤로 간다** (논의 4번). 오름차순일 때만 위로 오면 같은 열을
  두 번 눌렀을 때 빈 줄이 위아래로 튀어 예측이 안 된다.
* 담당자·태그처럼 **여러 값이 든 열은 맨 앞 하나**를 기준으로 삼는다. 개수로 세면
  "김현우" 를 찾는 사람에게 아무 도움이 안 된다.
* 과제 화면의 **정렬 선택 상자는 남겼다.** "보고 경과일순" 처럼 한 열로 표현할 수 없는
  정렬이 있고, 보드 보기에는 머리글이 없기 때문이다. 둘은 같은 값을 보므로 어긋나지 않는다.
* 정렬도 주소에 실린다 (`?sort=title&order=desc`).

**만들면서 잡은 것 — `_flip` 이 괄호 안의 쉼표까지 잘라 SQL 이 깨지던 문제**

## 53. 검색이 태그·담당자·보고 문서까지 찾도록 ✅ 반영

**현재 무엇이 검색되는지 확인했다.** 색인(`search_fts`)에 들어가는 것은 **둘뿐**이다

| | 색인됨 | |
|---|---|---|
| 과제 | 제목 · 본문(개요) | ✅ |
| 진행일지 | 제목 · 본문 | ✅ |
| **태그** | | ❌ |

**착수 전 정할 것**

* **보고 문서를 검색 결과에 넣을 것인가.** 넣는 게 맞다고 보지만, 진행일지 내용이

  종류를 나눠 보여 주거나(지금도 과제/진행일지/첨부로 나뉜다), 확정된 보고만 넣는 방법.
* **태그·담당자를 본문에 섞어 넣을지, 따로 셀지.** 섞으면 구현이 간단한데
  "권경락" 을 검색하면 그 사람이 담당인 과제가 전부 나와 결과가 넘칠 수 있다.
  `태그:소재` 같은 **한정 검색**을 붙이는 방법도 있다 (규모가 커진다).
* 색인 구조가 바뀌므로 **`SCHEMA_VERSION` 을 올려야 한다** — 올리면 기존 사용자의
  색인이 md 파일에서 자동으로 다시 만들어진다(설계상 정상 동작).

**반영 (2026-09-03)** — 색인에 **보고 문서(제목·본문·피보고자)**와 **태그·담당자**를 넣었다.

* 검색 결과에 **보고** 갈래가 생겼다. 누르면 그 보고 문서가 바로 열린다.

  "김현우" 로 찾으면 그 사람이 맡은 과제가 나오는 것이 자연스럽다.
* 목록의 검색 칸(`?q=`)도 같은 색인을 쓰므로, **보고에 걸려도 그 과제가 남는다.**

  md 파일에서 자동으로 다시 만들어진다.
* **보고 이력 화면(TODO 43)은 그대로 둔다.** 그쪽은 "찾기"가 아니라 *훑어보기*다.

TODO 48에서 "주소가 화면을 속이지 않게 한다"고 해 두었는데, **실사용 경로에서는
듣지 않고 있었다.**

* 화면에서 조건을 바꿀 때는 `replaceState` 로 주소만 갈아 끼운다(방문 기록을 안 남기려고).
* 그런데 `replaceState` 는 `hashchange` 를 일으키지 않는다. 그래서 **화면 위쪽(App)이
  기억하는 주소가 실제 주소보다 뒤처진다.**
* `useAddressBar` 는 그 뒤처진 값과 비교하고 있었다. 결과적으로
  "조건을 걸어 둔 상태에서 상단 메뉴를 눌렀다"를 알아채지 못했다.

시험이 통과했던 이유는, 그 시험이 주소로 직접 들어간 뒤(=위쪽 기억이 최신인 상태)
메뉴를 눌렀기 때문이다. **사람이 실제로 하는 순서 — 조건을 고르고 나서 메뉴를 누르는
경우 — 는 지나가지 않았다.**

**고친 것**: 들어오는 쪽은 **주소를 직접 읽는다.** 위쪽이 넘겨주는 값을 믿지 않는다.
`hashchange` 를 스스로 듣고 그 시점의 `window.location` 과 "우리가 마지막으로 쓴 주소"를
견준다. 떠나는 중(다른 화면 주소)이면 아무것도 하지 않는다.

> 남길 만한 교훈: **시험이 실제 사용 순서를 지나가지 않으면, 통과해도 지켜지지 않는다.**
> 화면 시험의 `go()` 도 `page.goto` 대신 **사람이 링크를 누르는 것과 같은 방식**으로
> 바꿨다 — `goto` 는 주소의 `#` 뒤만 바뀔 때 `hashchange` 를 일으키지 않아,
> 시험만 통과하고 실제로는 안 되는 상태를 만들 수 있었다.

## 59. 팀 코드에 윈도우가 못 쓰는 문자가 통과하던 문제 ✅ 반영

**발견**: 2026-09-03 자체 점검

팀 코드는 **그대로 폴더 이름에 들어간다** (`2026-소재-001-제목`). 과제명은 슬러그로
다듬어지는데 **코드는 다듬지 않는다.** 그런데 검사가 `/ \ 공백` 만 막고 있었다.

```
소재:개발  소재*  소재?  소재"  소재<개발  소재|팀   ← 전부 통과했다
```

전부 **윈도우에서 파일·폴더 이름에 쓸 수 없는 문자**다. 이 코드로 과제를 만들거나
번호를 일괄 변경하면 폴더 생성·이동이 실패한다. 사내 PC가 윈도우이므로 실제로 터진다.

**고친 것**: `: * ? " < > | / \ 공백·탭` 을 모두 막고, 끝의 점(탐색기가 잘라 낸다),
점만으로 된 코드, 20자 초과(경로 260자 제한)도 막는다. 저장뿐 아니라
**일괄 변경 미리보기·실행에도 같은 검사**가 걸린다 — 한쪽만 막으면 소용이 없다.
시험 16건 추가.

## 60. 보관함에 있는 과제는 번호 일괄 변경에서 빠진다 ✅ 반영

**발견**: 2026-09-03 자체 점검 · **아직 안 고침, 판단 필요**

```
1. 과제를 보관함(.trash)으로 옮긴다        → 2026-002 지울 과제
2. 팀 코드를 넣고 번호를 일괄 변경한다      → 나머지는 2026-소재-00N
3. 보관함에서 되돌린다                    → 2026-002 로 그대로 살아난다
```

되돌린 과제만 **옛 번호 체계로 남는다.** 번호가 겹치지는 않아 자료가 깨지지는 않지만,
목록에 두 형태가 섞여 일괄 변경을 한 의미가 사라진다.

**왜 이렇게 되나**: 일괄 변경은 색인에 있는 과제만 훑는데, 보관함 항목은 색인에 없다.
보관함 기록(`manifest.jsonl`)의 `origin` 도 옛 경로 그대로 남는다.

**고칠 방법 세 가지** (사용자 판단 필요)

| | 방법 | 평 |
|---|---|---|
| (가) | 미리보기에 **"보관함에 N건이 있습니다. 되돌리면 옛 번호로 돌아옵니다"** 경고만 | 가장 싸다. 사실을 알려 주고 사람이 판단 |
| (나) | 보관함 항목까지 함께 바꾼다 (폴더 안 `index.md` + manifest 의 origin) | 가장 깔끔하지만 보관함 내부를 건드린다 |
| (다) | 되돌릴 때 그 시점의 코드로 번호를 맞춘다 | 되돌리기가 조용히 번호를 바꾸는 셈이라 놀랄 수 있다 |

→ **2026-09-04 사용자 결정: (나) 함께 바꾼다.**

**반영** — 보관함 과제도 같은 규칙으로 바꾼다.

* 보관된 폴더 안 `index.md` 의 id 와, 되돌아갈 자리를 적어 둔 보관함 기록의 경로를
  **둘 다** 고친다. 하나만 고치면 되돌린 뒤에 어긋난다.
* **보관함 과제가 쓰고 있는 번호는 다른 과제에 주지 않는다.** 살아 있는 과제와
  **같은 밀기 규칙**을 쓴다 — 겹친 채 되돌리면 폴더가 서로를 덮는다.
* 미리보기에 바뀔 보관함 과제도 함께 보인다.
* 과제가 아닌 보관 항목(진행일지·보고만 든 것)은 건드리지 않는다.

## 64. 가끔 나던 500 오류와 "목록이 나왔다 안 나왔다" ✅ 반영

**접수**: 2026-09-04 (사용자 — 실사용 중)

> ```
> 500 GET /api/project
> bad parameter or other API misuse
> 직전 : GET /api/report-candidates → GET /api/reports → GET /api/report-candidates
> ```
> *"메인 페이지에서 F5를 누르면 과제 목록이 나왔다가 안 나왔다가 하는 현상도 확인했다"*

**두 증상은 같은 원인이었다.**

화면을 새로고침하면 여러 API 를 **동시에** 부른다(직전 동작 기록이 그것을 보여 준다).
FastAPI 는 동기 엔드포인트를 **스레드 풀**에서 돌리므로 요청들이 실제로 겹쳐 흐른다.
그런데 이 도구는 **커넥션 하나를 모두가 나눠 쓰고 있었다** (`deps.py`).

* 한쪽이 커서를 훑는 도중 다른 쪽이 커밋하면 그 커서가 끊긴다
  → `sqlite3.ProgrammingError: bad parameter or other API misuse`
* 같은 커넥션이면 **아직 커밋하지 않은 중간 상태까지 보인다**

**목록이 비어 보인 것도 이 500 이었다.** 화면은 `GET /api/projects` 가 실패하면
과제를 하나도 그리지 않는다. 그래서 "가끔 목록이 안 나오는" 것처럼 보였다.

**재현했다.** 읽기와 쓰기를 섞어 동시에 던지니 500 이 실제로 났다
(410건 중 3건, `TypeError: 'NoneType' object is not subscriptable` — 재인덱싱이
방금 만든 과제를 못 보고 색인에서 지우는 경합도 함께 나왔다).

**고친 것 셋**

1. **요청마다 커넥션을 따로 연다.** WAL 이라 읽기는 서로를 막지 않고, 각자
   **마지막으로 커밋된 상태**만 본다. 여는 비용은 마이크로초 단위다.
2. **쓰는 요청은 한 번에 하나씩.** SQLite 는 읽던 커넥션이 쓰기로 올라설 때
   다른 쪽이 쓰고 있으면 기다리지 않고 곧바로 `database is locked` 를 낸다
   (`busy_timeout` 이 듣지 않는 구간이다). 게다가 두 쓰기가 겹치면 논리적으로도
   어긋난다 — 과제를 만드는 사이에 전체 재인덱싱이 끼어들면 그 과제를 지워 버린다.
   **한 사람이 쓰는 도구라 쓰기를 줄 세워도 잃는 것이 없다.**
3. **한 파일에 덧붙이는 곳에 자물쇠**를 뒀다 (오류 기록·보관함 기록).
   줄이 섞이거나, 자르는 도중 덧붙인 줄을 잃을 수 있었다.

**결과**: 같은 시험을 1,230건 돌려 **실패 0건 · 서버 예외 0건**.
예전 코드에서는 같은 시험이 매번 실패했다.

**함께 고친 것 — 못 불러왔을 때 화면이 침묵하던 문제**
빨간 글씨 한 줄만 남고 표는 빈 채로 있었다. 그래서 "과제가 없는 것"과 "못 불러온 것"이
구분되지 않았다. 이제 무엇이 잘못됐는지 말하고 **[다시 시도]** 를 함께 준다.
성공하면 지난 오류를 지운다 — 예전에는 한 번 실패하면 그 글씨가 계속 남았다.

**시험 6건 추가** — 커넥션이 요청마다 따로인지, 쓰기가 줄을 서는지, 읽기는 안 막히는지,
예외가 나도 자물쇠를 놓는지.

* 남겨 둘 개수(기본 10)를 넘으면 **오래된 것부터** 버린다.
* **백업 폴더를 데이터 폴더 안에 둘 수 없다** — 백업이 다음 백업에 담겨 눈덩이처럼 커진다.
* **없는 폴더는 거절한다.** 오타로 엉뚱한 곳에 폴더가 생기는 것보다 먼저 만들라고 하는 편이 안전하다.
* 폴더에 있는 **남의 파일은 건드리지 않는다** (공유 폴더를 백업 위치로 잡을 수 있다).
* 네트워크 드라이브가 끊기면 화면에 그렇게 알리고, **프로그램은 멈추지 않는다.**

마지막 백업 시각은 따로 적지 않고 **폴더의 파일에서 읽는다** — 상태 파일과 실제가
어긋날 일이 없다. 실패만 따로 기록한다(파일이 안 생기므로).

사용자 요청으로 **"한 사람이 쓰는 도구로서 남은 것이 있나"** 를 훑었다.
문서를 다시 읽은 것이 아니라, 빈 vault 로 서버를 띄워 **한 주 흐름을 끝까지 밟고**
1년 치 자료를 만들어 재 보았다.

**이상 없던 것** (같은 걱정을 다시 하지 않도록 남긴다)

| 확인 | 결과 |
|---|---|
| 한 주 흐름 전체 — 과제 → 진행일지 → 초안 → 확정 | 정상 |
| 내보내기 4종 (md · zip · html · backup) · 전체 백업 | 모두 200 |
| 탐색기에서 md 를 고친 뒤 [다시 읽기] | 반영됨 |

성능은 걱정하던 것보다 여유가 크다. **T23(대용량 확인)은 사실상 해소**로 본다.

## 66. 검색 결과가 60건에서 조용히 잘린다

**발견**: 2026-09-04 자체 점검 · **규모 S**

진행일지 1,000건을 만든 뒤 흔한 낱말(`시험`)로 찾으니 **정확히 60건**이 나왔다.
화면은 `"시험" 검색 결과 60건` 이라고만 적는다. **실제로는 훨씬 많은데, 사용자는
그게 전부인 줄 안다.**

```python
def search(conn, query, limit: int = 60):   # services/search.py
    refs = _matching_refs(conn, query, limit)   # 종류 구분 없이 통째로 60개
```

문제가 둘이다.

1. **잘렸다는 말을 안 한다.** 60건이 "전부 60건"인지 "60건까지만 보여 준 것"인지
   구분할 수 없다. 흔한 낱말일수록 잘리는데, 그럴수록 사용자는 다 봤다고 믿는다.
2. **한 종류가 자리를 다 먹을 수 있다.** 상한이 과제·진행일지·보고에 **공통**이라,
   진행일지가 60칸을 채우면 **제목이 딱 맞는 과제가 밀려날 수** 있다.
   (지금은 FTS 순위 덕에 대체로 살아남지만, 보장되지 않는다)

**고칠 방향**

* 상한을 **종류마다 따로** 둔다 (예: 과제 30 · 진행일지 40 · 보고 30 · 첨부 20).
  한 종류가 다른 종류를 밀어내는 일이 사라진다.
* **잘렸으면 그렇게 말한다** — `60건 이상 (좁혀서 다시 찾아 보세요)`.
* 종류별 [더 보기] 는 그다음. 우선은 **거짓말을 하지 않는 것**이 먼저다.

## 67. 해가 바뀌면 지난해 과제가 계속 섞인다

**발견**: 2026-09-04 자체 점검 · **규모 S**

과제 목록을 거르는 기준은 **상태·속성·그룹·태그·담당자·마감** 여섯이다.
**연도나 기간이 없다.** 2027년이 되면 2026년 과제가 목록에 그대로 남아,
"올해 무엇을 하고 있나"를 보려면 눈으로 걸러야 한다.

1년을 만들어 보니 과제 201건 중 대부분이 이미 끝난 것이었다. 상태로 거를 수는 있지만
**기본 화면이 늘 전체**라, 해가 갈수록 첫 화면의 쓸모가 떨어진다.

**고칠 방향** — 과제 번호에 이미 연도가 들어 있어(`2026-001`) 싸게 만들 수 있다.

* 목록에 **연도 거르기**를 둔다. 기본값을 "올해"로 할지 "전체"로 할지는 판단 필요 —
  기본을 올해로 하면 첫 화면이 늘 가벼워지지만, 지난해 과제를 찾을 때 한 번 더 눌러야 한다.
* 조건은 주소에 실린다 (TODO 48 규칙).
* 대시보드의 수도 같은 조건을 따라야 한다 (DESIGN 5.8 — 수와 목록이 어긋나면 안 된다).

→ **기본값을 무엇으로 할지 사용자 판단이 필요하다.**

## 68. 과제 안에서 찾기가 없다

**발견**: 2026-09-04 자체 점검 · **규모 S · 우선순위 낮음**

진행일지가 쌓인 과제에서 "그 조건으로 시험한 게 언제였지"를 찾으려면,
접혀 있는 기록은 **화면에 글자 자체가 없어** 브라우저 찾기(Ctrl+F)로도 안 걸린다
(펼친 것만 본문을 그린다).

지금도 길은 있다 — **[모두 펼치기]** 를 누르면 전부 그려지고, 상단 검색으로도 찾을 수 있다.
그래서 급하지는 않다. 다만 진행일지가 수십 건인 과제에서는 손이 한 번 더 간다.

**고칠 방향**: 과제 상세에 작은 찾기 칸을 두어, 친 낱말이 든 기록만 남기고
그 기록은 자동으로 펼친다. 상단 검색과 달리 **이 과제 안에서만** 본다.

## 69. ROADMAP 의 R1 설명이 실제와 다르다 ✅ 반영

**발견**: 2026-09-04 자체 점검

ROADMAP R1(인원별 성과 관리)에 *"기록 하나하나를 누가 썼는지는 남지 않는다"* 고
적혀 있는데, **실제로는 남는다.** 진행일지·보고 모두 `author` 를 기록하고 있고

문서가 낡으면 다음 단계를 잘못 계획하게 되므로 바로잡았다.
R1 에 남은 것은 "작성자 기록"이 아니라 **집계 화면**이다.
