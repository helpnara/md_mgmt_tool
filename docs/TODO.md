## 1. 보고 초안의 기본 내용 — 다 채울지, 비워 둘지

**접수**: 2026-09-02 · **상태**: **B안으로 결정** (2026-09-02)

**현상**
[보고 초안 만들기]를 누르면 마지막 보고 이후의 진행일지 **본문 전체**가 초안에 붙어 나온다.

**불편한 점**
실제로는 그중 필요한 것만 골라 직접 정리해 쓰고 싶은데, 쓰기 전에 지우는 일부터 해야 한다.

**선택지**

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 초안을 **빈 칸**으로 시작 (요약·특이사항·다음 계획 뼈대만) | 바로 쓰기 시작 가능 | 무엇을 보고할지 다시 찾아봐야 함 |
| **B ← 채택** | 지금처럼 채우되 **[내용 지우기]** 버튼 추가 | 참고하며 쓰다가 필요할 때 지움 | 기본은 여전히 긴 초안 |
| C | 기본값을 **설정으로 선택** (빈 칸 / 채움) | 취향대로 | 설정 항목이 하나 늘어남 |

**구현 제안값** (이대로 만들고, 써 보고 조정)

| 항목 | 제안값 |
|---|---|
| 버튼 위치 | 보고 편집 화면 위쪽, [엑셀 셀로 복사] 옆 |
| 지우는 범위 | **"진행 내용" 절만** 지우고 `## 보고 요약` · `## 특이사항 및 이슈` · `## 다음 계획` 뼈대는 남긴다. 전부 지우면 목차까지 사라져 결국 다시 타이핑하게 된다 |
| 문구 | `진행 내용 지우기` (무엇이 지워지는지 버튼에 드러나게) |
| 실수 방지 | 누르면 확인창 한 번. 지운 뒤에는 저장하지 않고 화면을 닫으면 원래대로 돌아온다 |

전부를 비우고 싶을 때는 편집창에서 Ctrl+A 로 지우면 되므로 별도 버튼은 두지 않는다.

**영향 범위**: `backend/app/services/reports.py`의 `_draft_body`, `frontend/src/components/ReportEditor.tsx`

## 2. 같은 과제에 보고를 여러 번 남길 수 없음

**접수**: 2026-09-02 · **상태**: **B안으로 결정** (2026-09-02) · **중요도**: 높음

**현상**
보고 이력이 1건 있는 상태에서 [보고 초안 만들기]를 누르면
`2026-09-08 보고 문서가 이미 있습니다.` 가 뜨고 더 이상 진행되지 않는다.

**원인 (확인함)**
보고 문서를 `reports/<보고일>/report.md` 로 저장하기 때문에 **날짜 하나당 보고 하나**다.
그런데 과제 상세의 [보고 초안 만들기] 버튼은 날짜를 묻지 않고 **항상 그 주 화요일**을
기본값으로 쓴다. 그래서 같은 주에 두 번째 보고를 만들려 하면 막힌다.

| 시도 | 결과 |
|---|---|
| 1회차 초안 생성 | 201 정상 |
| 2회차, 같은 날짜 | **409 막힘** ← 지금 겪는 상황 |
| 2회차, 날짜를 직접 지정(예: 2026-09-15) | 201 정상 |
| 1회차를 확정한 뒤 같은 날짜 | 409 막힘 |

즉 기능 자체는 여러 번 보고를 지원하지만, **버튼이 날짜를 고를 방법을 주지 않는 것**이 문제다.
(보고 대상 후보 화면에는 보고 예정일 입력칸이 있어 그쪽에서는 지정할 수 있다)

**선택지**

| 안 | 내용 | 비고 |
|---|---|---|
| A | [보고 초안 만들기]를 누르면 **보고일을 먼저 묻는다** | 가장 단순하고 의도가 분명함 |
| **B ← 채택** | 같은 날짜면 **자동으로 뒤에 번호를 붙인다** (`reports/2026-09-08-2/`) | 누르면 바로 만들어진다. 하루에 중간·완료 보고를 각각 남기는 경우도 대응 |
| C | A + B 둘 다 | 날짜는 고르되, 같은 날 여러 건도 허용 |

**B안 구현 시 정할 것**
- 폴더명 규칙: `reports/2026-09-08/`, 두 번째부터 `reports/2026-09-08-2/`, `-3/` …
- 같은 날짜에 **아직 작성 중인** 보고가 있으면 새로 만들지, 그것을 열지
  (→ 3번 항목의 피보고자 구분이 들어오면 새로 만드는 쪽이 자연스럽다)
- 보고 문서의 `report_date` 는 폴더명이 아니라 front matter 값을 따른다 (둘 다 같은 날짜)

**함께 볼 것**
- 409 메시지가 다음 행동을 알려 주지 않는다. "이미 있는 보고를 열까요, 새 날짜로 만들까요?" 처럼
  선택지를 주는 편이 낫다.
- 이미 있는 그 날짜의 보고가 **작성 중**이면 새로 만들 것이 아니라 그것을 열어 주는 게 자연스럽다.

**결정 필요**: A / B / C 중 선택

**영향 범위**: `backend/app/services/reports.py`의 `create_draft`,
`frontend/src/components/ProjectDetail.tsx`의 보고 초안 버튼

## 3. 보고 이력 한 줄 표기에 피보고자·완료 시각 넣기

**접수**: 2026-09-02 · **상태**: 형식·입력 방식 확정, 나머지는 구현 시 제안값대로

**현상**
보고 이력 목록의 한 줄이 이렇게 보인다.

```
2026-09-08   2026-09-08 보고   확정   진행일지 7건
```

날짜가 두 번 나오고, 정작 **누구에게 보고한 것인지**가 없어서 이력으로서 쓸모가 떨어진다.

**바꿀 형식**

```
2026-09-08  [피보고자 또는 회의체명]  보고 완료(2026-09-08 17:40)
```

* 앞의 `2026-09-08` = 보고일
* `[피보고자 또는 회의체명]` = 누구에게 보고했는지 (예: 팀장, 연구소장, 주간회의체)
* `보고 완료(날짜 시간)` = 확정 시각 (`frozen_at`)

**필요한 것**
설계 때 예약만 해 두고 비워 둔 `audience`(피보고자) 필드를 실제로 쓰게 된다.
보고 문서 front matter에 이미 자리가 있으므로 입력칸과 표시만 붙이면 된다.

**입력 방식 — 결정됨 (2026-09-02)**
**자유 입력 + 기존 값 자동완성.** 피보고자·회의체는 대부분 정해져 있지만 고정 목록으로 막지 않는다.
그룹·담당자와 같은 방식으로, 한 번 쓴 값은 다음부터 목록에 떠서 골라 쓸 수 있게 한다.
(`GET /api/meta` 에 `audiences` 목록을 추가하고, 입력칸은 `<input list=…>` 로)

**나머지 세부 — 아래 제안값으로 구현하고, 써 보고 조정**

| 항목 | 제안값 |
|---|---|
| 입력 시점 | 보고 편집 화면 상단에 입력칸을 두어 **아무 때나** 입력·수정. 확정할 때 비어 있으면 "피보고자 없이 확정할까요?" 한 번만 확인 |
| 미입력일 때 | 목록에 `(피보고자 미입력)` 을 흐린 글씨로 표시 — 비워 두면 빠뜨린 것인지 알 수 없다 |
| 작성 중인 보고 | `2026-09-08  팀장  작성 중` 처럼 뒷부분만 다르게 |
| 확정된 보고의 피보고자 수정 | 확정 해제 없이 **피보고자만은** 고칠 수 있게 (오탈자 정정용). 본문은 그대로 잠금 |

**2번 항목과의 연결**
같은 날짜에 보고를 여러 건 남기게 되면(B안), 목록에서 이 둘을 구분해 주는 것이
바로 피보고자다. 두 항목을 같이 구현하는 편이 낫다.

**영향 범위**: `frontend/src/components/ProjectDetail.tsx`(보고 이력 목록),
`ReportEditor.tsx`(입력칸), `backend/app/api/reports.py`(audience 전달),
`backend/app/api/meta.py`(audiences 자동완성 목록),
`backend/app/services/reports.py`(초안 front matter)

## 4. 완료된 과제에도 마감 초과가 빨갛게 표시된다

**접수**: 2026-09-02 · **상태**: 확정 (아래대로 구현) · **난이도**: 낮음

**현상**
과제 목록 첫 화면에서, 상태가 **완료**인 과제에도 마감일에 `D+261 초과` 가 빨간색으로 뜬다.

```
2025년 수명평가 표준화   완료   국책과제   …   D+261 초과  2025-12-15
```

**왜 문제인가**
빨간 초과 표시는 "기한이 지났는데 아직 끝내지 못했다"는 경고다.
이미 끝난 과제에 띄우면 경고가 무의미해지고, 정작 **진짜 늦어지고 있는 과제**가 묻힌다.

**원인**
`frontend/src/util.ts` 의 `dueLabel()` 이 **날짜만 보고** 표시를 정한다. 상태를 보지 않는다.

```ts
if (days < 0) return { text: `D+${-days} 초과`, tone: "danger" };
```

**이렇게 고친다**

| 상태 | 마감 표시 |
|---|---|
| 완료 · 중단 | 초과 표시를 하지 않고 **마감일만 흐린 글씨로**. 끝난 과제라 남은 날짜도 의미 없다 |
| 보류 | 초과 표시는 유지한다. 멈춰 있을 뿐 끝난 것이 아니고, 오히려 챙겨야 할 대상이다 |
| 예정 · 검토중 · 진행중 | 지금 그대로 (D-7 이내는 주황, 초과는 빨강) |

* `dueLabel(due)` 에 상태를 함께 넘겨 판단하도록 바꾼다.
* 목록·보드 카드·과제 상세 세 곳에서 같은 함수를 쓰므로 한 번만 고치면 된다.

**완료일 기록 — 하지 않기로 함 (2026-09-02)**
완료 일자를 별도 필드로 두지 않는다. 실무에서 **완료 보고를 한 날을 완료로 보고** 관리하고 있고,
그 날짜는 이미 보고 이력에 남는다. 나중에 필요해지면 새 필드를 만들 것 없이
**마지막 확정 보고일**을 완료일로 쓰면 된다.

**영향 범위**: `frontend/src/util.ts`(`dueLabel`),
`ProjectList.tsx` · `ProjectBoard.tsx` · `ProjectDetail.tsx`(호출부)

### 6. 과제 상세 2단 레이아웃 + 상단 요약 ⭐

**지금 문제**: 매일 쓰는 "수행 이력"이 화면 852px 아래에 있어 매번 스크롤해야 한다.
1920×1080 화면에서 좌우 여백이 크게 남는다.

**이렇게 한다**

```
┌─────────────────────────────────────────────┐
│ 과제명 + 상태·속성 배지 + 액션 버튼          │
│ 요약: 담당자 · 기간 · 기록 N건 · 마지막 보고  │
│       · 미보고 N건 · 첨부 N건(용량)          │
├───────────────────────┬─────────────────────┤
│ 과제 개요             │ 수행 이력            │
│ 보고 이력             │ (기록 추가 + 타임라인)│
│ 첨부 자료             │                     │
└───────────────────────┴─────────────────────┘
```

* 넓은 화면에서 좌우로 나누고, 좁은 화면(약 1200px 미만)에서는 위아래로 쌓는다.
* 상단 요약에는 각 영역의 핵심 숫자를 모아, 펼쳐 보지 않아도 상태를 알 수 있게 한다.

### 7. 검색 결과에서 해당 진행일지로 이동

### 16. 넓은 화면의 좌우 여백 활용 ⭐ ✅ 반영

**원인**: `main { max-width: 1180px }` 로 고정돼 있다. 글 읽기 좋은 폭으로 잡았는데,
2단으로 나누면서 각 칸이 절반으로 줄어 오히려 불편해졌다.

**제안**: 화면 폭에 따라 컨테이너를 넓힌다.
* 1440px 미만 — 지금처럼 (여백 24px)
* 1440~1920px — `min(100% - 48px, 1720px)`
* 2560px 이상 — 1720px에서 멈춘다 (더 넓히면 시선 이동이 너무 커진다)
* 과제 목록·검색·보고 대상 화면에도 같이 적용

이것만으로 우측(수행 이력) 칸이 604 → 약 940px, 편집 칸이 273 → 약 450px가 된다.

**반영 결과** (2026-09-02, 실측)

| 화면 | 본문 폭 | 좌측 | 우측 | 진행일지 편집 칸 |
|---|---|---|---|---|
| 1366px | 1180 (그대로) | 504 | 604 | 273 |
| 1440px | 1180 → **1440** | 623 | **745** | — |
| 1920px | 1180 → **1720** | 700 | **948** | 273 → **445** |
| 2560px | **1720** (여기서 멈춤) | 700 | 948 | — |

과제 목록 표도 1124 → **1664px**로 늘었다. 1440px 미만 화면은 손대지 않았다.
좌측 칸은 `min(45%, 700px)`으로 묶어, 넓어진 폭이 수행 이력 쪽으로 가게 했다.

### 17. 보고 이력 행에서 삭제 버튼이 잘림 ⛔ 결함 ✅ 반영

**원인**: 행이 `flex` 인데 내부 요소에 `min-width: 0` 이 없어 줄어들지 않는다.
피보고자 이름이 길면(예: "차세대전지 개발 주간 협의체") 그대로 밀려 나간다.

**고칠 것**: 행 내부를 줄어들 수 있게 하고, 긴 텍스트는 말줄임(…) 처리한다.
삭제 버튼은 항상 오른쪽 끝에 고정한다.

**반영 내용** (2026-09-02)
* 행과 그 내부에 `min-width: 0` 을 줘서 줄어들 수 있게 했다.
* 삭제 버튼은 `flex: 0 0 auto` + `margin-left: auto` 로 항상 오른쪽 끝에 고정.
* 피보고자 이름이 가장 먼저 줄고, 넘치면 말줄임(…) 처리한다. 마우스를 올리면 전체 이름이 뜬다.
* **보고 일시는 줄이지 않는다.** 자리가 정말 부족하면 행이 두 줄로 접힌다(잘리지 않는다).
* 검증: 1210 / 1366 / 1440 / 1600 / 1920 / 2560px 여섯 폭에서
  삭제 버튼이 항상 행 안쪽 11px에 있고, 가로 스크롤이 생기지 않는 것을 확인했다.
  피보고자 이름 45자짜리 극단값으로도 넘치지 않는다.

### 18. 진행일지 편집 칸이 좁다 ✅ 반영

**선택지**

**반영 내용** (2026-09-02) — (a)+(b) 둘 다 넣었다.

### 19. 보고 편집기가 가장 좁은 칸에서 열린다 ✅ 반영

### 20. 좁은 칸에서 큰 표가 넘칠 수 있다 (예방) ✅ 반영

지금 데이터의 표는 190px라 문제가 없지만, 칸이 좁아진 만큼 열이 많은 표는 넘친다.

## 22. 진행일지 본문의 이미지가 저장 후 안 보임 ⛔ 결함 ✅ 반영

**접수**: 2026-09-02 (사용자) — 작성 중 미리보기에는 이미지가 보이는데,

**고친 것**: 목록 화면이 진행일지에는 `logs` 기준을 쓰도록 나눴다.
렌더링하는 자리 다섯 곳을 모두 확인해 기준이 맞는지 점검했다.
실제로 이미지를 올려 목록에서 뜨는 것과 실패 요청이 0건인 것을 확인했다.

## 24. 대시보드에 담당자별 과제 수 ✅ 반영

**접수**: 2026-09-02 (사용자)

속성 칩처럼, **사람별로 몇 개의 과제를 맡고 있는지** 대시보드에 간략히 보여 준다.

```
상태  [예정 2][검토중 1][진행중 3][보류 1][완료 1]
속성  [스마트과제 2][R&D 1][투자 2][기획보고 1][국책과제 1][미지정 1]
담당  [권경락 4][김현우 2][박서준 2][미지정 1]        ← 이 줄을 새로 만든다
```

담당자 필터(`?owner=`)와 `meta.owners` 는 이미 있으므로, 대시보드에 세는 줄만 더하면 된다.
누르면 그 사람 과제만 걸러지고 다시 누르면 해제되는 것도 속성 칩과 같다.

**정할 것 — 구현 전에 답이 필요한 것들**

1. **합이 총 과제 수와 다르다.** 한 과제에 담당자가 여러 명일 수 있어서
   담당 칩의 합이 전체보다 커진다(예: 전체 8건인데 담당 합이 11). 상태·속성 칩은
   합이 딱 맞으므로, 같은 모양으로 두면 잘못 읽힐 수 있다.
   → 줄 앞 라벨을 `담당 (중복 포함)` 으로 두거나, 합이 다를 때만 작게 알려 주는 방법.
2. **사람이 늘면 줄이 길어진다.** 지금은 팀 규모가 작아 괜찮지만 15명이 되면 두세 줄이 된다.
   → 상위 N명만 세우고 `+N명`으로 접는 방법 (누르면 전체).
3. **끝난 과제를 넣을지.** "지금 누가 몇 개를 들고 있나"를 보려면 완료·중단은 빼는 편이 맞고,
   "올해 누가 몇 개를 했나"를 보려면 넣는 편이 맞다. 대시보드의 다른 칩은 전부 포함이므로
   기준을 섞으면 또 어긋난다 — 21번에서 겪은 문제.
   → 상태 칩과 같이 **전부 포함**으로 두고, 특정 상태를 함께 누르면 그 상태 안에서
     사람별로 보이게 하는 쪽이 일관된다(칩을 겹쳐 걸 수 있게).

**로드맵 R1과의 관계**: R1(인원별 과제 성과 관리)은 기간별 실적·보고 건수까지 보는 별도 화면이다.
여기 24번은 그 앞단의 "지금 몇 개"만 세는 한 줄이라 서로 겹치지 않는다.
다만 24번을 만들 때 담당자 집계를 서비스 계층에 두면 R1에서 그대로 쓸 수 있다.

---

**반영 내용** (2026-09-02) — 위 세 가지를 아래처럼 정해 넣었다.

```
담당 중복 포함  [권경락 6][이수민 2][최지훈 2][한도윤 2][담당자1 1]…[담당자4 1]  [+1명]
```

1. **합이 다를 때만 밝힌다.** 담당 칩의 합이 전체 과제 수보다 크면 라벨 옆에
   작게 `중복 포함` 이 붙는다. 한 사람이 한 과제씩만 맡고 있으면 아무것도 안 붙는다.
   (실측: 전체 8건 / 담당 칩 합 17건 → 문구 표시됨)
2. **8명까지 세우고 나머지는 `[+N명]` 으로 접는다.** 누르면 전부 펼쳐지고 `[접기]` 로 되돌아간다.
   조작 버튼이라 점선 테두리에 흐린 글씨로 두어 세는 칩과 구분했다.
3. **끝난 과제도 포함한다** — 상태·속성 칩과 같은 기준. 상태 칩과 겹쳐 걸 수 있으므로
   "진행중 + 권경락" 처럼 좁혀 보면 된다.

담당자가 없는 과제는 `미지정` 칩으로 세고, 눌러서 거를 수 있다(`owner=none`).
많이 맡은 사람부터, 같으면 이름순으로 세운다.

**검증**
* `test_numbers_match_what_the_list_filters` 에 담당 칩을 추가했다 —
  모든 담당 칩의 수가 실제 목록 필터 결과와 같은지 대조한다.
* 담당자별 집계·중복 합·미지정 처리에 테스트 3건을 더했다 (전체 125건 통과).
* 화면에서 실측: 권경락 칩 6건 → 목록 6행, 이수민 2건 → 2행, 미지정 1건 → 1행.
  `[+1명]` 펼치기·접기, 고른 칩 색(파란 배경 + 흰 글씨) 모두 확인. JS 오류 0건.

## 25. 대시보드 칩을 고르면 글자가 안 보임 ⛔ 결함 ✅ 반영

**접수**: 2026-09-02 (사용자)

두 가지가 함께 보고됐고, 둘 다 재현했다. 원인은 하나다.

* **속성 칩을 고르면** 아래 목록은 제대로 걸러지는데 **글자가 흰색이 되어 사라진다.**
  R&D 칩을 고르면 칩이 통째로 빈칸으로 보인다.
* **상태 칩을 고른 뒤 마우스를 올리면** 파란 배경에 파란 글씨가 되어 역시 안 보인다.
  (속성 칩도 같다)

**원인**: CSS 규칙 순서. `styles.css` 에서

```css
.dash-chip:hover:not(:disabled) { border-color: …; color: var(--accent); }   /* 414 */
.dash-chip.on   { background: var(--accent); color: #fff; }                  /* 415 */
.dash-chip.type { background: #f8fafc; }                                     /* 416 */
```

`.dash-chip.type` 과 `.dash-chip.on` 은 **우선순위가 같아** 뒤에 쓴 쪽이 이긴다.
그래서 고른 속성 칩(`dash-chip type on`)은 배경만 거의 흰색(#f8fafc)으로 되돌아가고
글자색은 흰색(#fff)이 그대로 남는다. 흰 바탕에 흰 글씨 — 명암비 1.04:1.

두 번째 문제도 뿌리가 같다. `.dash-chip:hover:not(:disabled)` 는 `:hover` 때문에
우선순위가 `.dash-chip.on` 보다 **높아서** 고른 칩의 글자색까지 덮어 버린다.
그래서 고른 칩에 마우스를 올리면 파란 배경에 파란 글씨가 된다.

**실측한 네 경우** (모두 확인함)

| 칩 | 마우스 | 배경 | 글자 | 결과 |
|---|---|---|---|---|
| 상태 칩 선택 | 뗌 | `rgb(47,111,235)` | `rgb(255,255,255)` | 정상 |
| **상태 칩 선택** | **올림** | `rgb(47,111,235)` | `rgb(47,111,235)` | **안 보임** |
| **속성 칩 선택** | 뗌 | `rgb(248,250,252)` | `rgb(255,255,255)` | **안 보임** |
| 속성 칩 선택 | 올림 | `rgb(248,250,252)` | `rgb(47,111,235)` | 흐리게 보임 |

**고친 내용** (2026-09-02)

```css
.dash-chip.type:not(.on) { background: #f8fafc; }              /* 고르지 않았을 때만 */
.dash-chip:hover:not(.on) { border-color: ...; color: ...; }   /* 고르지 않았을 때만 */
.dash-chip.on { background: var(--accent); color: #fff; }      /* 고른 칩은 이 규칙이 끝까지 쥔다 */
.dash-chip.on:hover { filter: brightness(0.92); }              /* 색은 그대로, 밝기만 */
```

고른 칩에도 마우스 반응은 남겨야 하므로, 색을 바꾸는 대신 밝기만 낮췄다.

**검증 — 여덟 경우 모두 실측** (WCAG 명암비)

| 칩 | 선택 | 마우스 | 배경 | 글자 | 명암비 |
|---|---|---|---|---|---|
| 상태 | 아니오 | 뗌 | `252,252,253` | `28,32,36` | 15.98 |
| 상태 | 아니오 | 올림 | `252,252,253` | `47,111,235` | 4.46 |
| 상태 | **예** | 뗌 | `47,111,235` | `255,255,255` | 4.57 |
| 상태 | **예** | **올림** | `47,111,235` | `255,255,255` | **4.57 (전 1.00)** |
| 속성 | 아니오 | 뗌 | `248,250,252` | `28,32,36` | 15.66 |
| 속성 | 아니오 | 올림 | `248,250,252` | `47,111,235` | 4.37 |
| 속성 | **예** | 뗌 | `47,111,235` | `255,255,255` | **4.57 (전 1.04)** |
| 속성 | **예** | 올림 | `47,111,235` | `255,255,255` | 4.57 |

고르지 않은 칩에 마우스를 올렸을 때(4.37 · 4.46)는 AA 기준 4.5에 살짝 못 미친다.
다만 이번에 바뀐 값이 아니고, 앱 전체의 링크가 같은 파란색을 쓰므로 여기만 바꾸면
오히려 어긋난다. 손대려면 `--accent` 를 앱 전체에서 함께 조정해야 한다.

> 21번을 만들 때 규칙을 이어 붙이며 순서와 우선순위를 확인하지 않아 생긴 것이다.
> 게다가 확인한 것도 "마우스를 뗀 상태의 상태 칩" 한 경우뿐이었다.
> 칩처럼 상태가 여러 겹인 요소(기본 / 선택 / 마우스 올림 / 선택+마우스 올림)는
> 조합을 빠짐없이 확인해야 한다.

## 26. 과제별 효과(정량·정성)와 산출 근거 ✅ 반영

**접수**: 2026-09-02 (사용자)

과제를 쓸 때 **효과성**을 적을 자리가 없다. 과제 상세(개요)에서 서술할 수 있어야 하고,
**과제 목록에서도 과제별 정량·정성 효과가 한눈에 보여야** 한다.

**지금 상태 — 정말로 빠져 있다**

과제 개요 템플릿은 네 개뿐이다: `배경` · `목표` · `산출물` · `관련 링크`.
"목표"는 *무엇을 달성하면 끝인지*이고 "산출물"은 *무엇을 남기는지*라서,
**"그래서 회사에 얼마의 이익인가"는 어디에도 없다.** front matter 필드에도, DB 컬럼에도 없다.
과제 관리 도구에서 이건 빠뜨리면 안 되는 축이다.

---

### 설계에서 먼저 정해야 할 것

#### (1) 시점을 나눠야 한다 — 이게 가장 중요하다 ⭐

R&D·투자 과제는 **착수할 때 기대효과**를 쓰고, **끝난 뒤 실적효과**를 확인한다.
이 둘을 한 칸에 쓰면 나중에 "예상은 얼마였고 실제로 얼마였나"를 되짚을 수 없다.
성과 관리(로드맵 R1)가 서려면 **두 값이 나뉘어 있어야** 한다.

| 시점 | 언제 채우나 | 쓰임 |
|---|---|---|
| **기대효과** | 과제 등록 시 | 과제 선정·우선순위 판단 |
| **실적효과** | 완료 보고 시 | 성과 집계, 다음 과제의 추정 근거 |

→ 제안: 두 벌을 따로 두되, **실적효과는 비어 있어도 정상**으로 취급한다(진행 중인 과제).

#### (2) 정량 효과를 얼마나 구조화할 것인가

**목록에 세우고 합계를 내려면 자유 텍스트로는 안 된다.** 그렇다고 과하게 쪼개면 입력이 번거롭다.

| 안 | 형태 | 장점 | 단점 |
|---|---|---|---|
| A. 자유 텍스트 한 줄 | `연 1.2억원 절감` | 입력이 가장 쉽다 | 목록 정렬·합계 불가. 단위 표기가 제각각이 된다 |
| B. **금액 + 자유 지표** | `effect_krw: 120000000` + `effect_metric: "수율 +2.1%p"` | 금액은 합계·정렬 가능, 나머지는 자유롭게 | 필드가 둘로 늘어난다 |
| C. 완전 구조화 | 지표명·값·단위·기준연도를 각각 | 무엇이든 집계 가능 | 입력이 번거로워 결국 안 쓰게 된다 |

→ **B안을 제안한다.** 금액은 어차피 대부분의 과제가 환산해서 보고하므로 합칠 수 있고,
수율·시간 같은 지표는 과제마다 달라 자유 입력이 맞다.

#### (3) 산출 근거는 별도 칸이 필요하다 ⭐

**숫자만 있고 근거가 없으면 보고 자리에서 방어하지 못한다.**
"연 1.2억"이 어떤 가정과 계산에서 나왔는지(단가 × 물량 × 개선율 등)를 적는 칸을 반드시 함께 둔다.
길어질 수 있으므로 개요 문서의 서술 영역에 두고, 목록에는 **근거 유무만 표시**한다
(근거 없는 숫자에 작은 표시를 달아 두면 채우게 된다).

#### (4) 목록에서 어떻게 보여줄 것인가

과제 목록은 이미 9개 열이라 더 넣으면 좁아진다.

* 열 하나만 추가해 **정량 효과를 요약 표기** (`연 1.2억` · 실적이 있으면 `1.2억 → 1.4억`)
* 정성 효과는 **말줄임 + 마우스 올리면 전체** (담당자·피보고자와 같은 방식)
* 근거가 없으면 숫자 옆에 옅은 표시
* 정렬에 **효과 큰 순** 추가 → "어느 과제가 회사에 가장 큰 이익인가"를 바로 볼 수 있다

#### (5) 대시보드·집계와의 관계

* 대시보드에 **`올해 기대효과 합계 / 실적효과 합계`** 한 줄을 더할 수 있다.
  단, 21번에서 겪었듯 **세는 기준과 거르는 기준이 같아야** 한다 (중단된 과제를 넣을지 등).
* 로드맵 **R1(인원별 성과 관리)** 의 "성과의 정의"가 여기서 절반은 정해진다.
  → R1을 시작하기 전에 이 항목을 먼저 하는 편이 순서가 맞다.

---

### 예상 작업

| 범위 | 내용 |
|---|---|
| 개요 템플릿 | `## 기대효과` · `## 산출 근거` 절 추가 (기존 과제는 비어 있어도 정상) |
| front matter | 정량·정성 효과 필드 (기대/실적 두 벌) |
| DB · 색인 | 컬럼 추가 → 스키마 버전 올려 재색인 (3 → 4) |
| 과제 등록·수정 화면 | 입력 칸. 근거 없이 숫자만 넣으면 안내 |
| 과제 목록 | 효과 열 + 효과순 정렬 |
| 과제 상세 | 요약 바에 효과 표시 |
| 대시보드 | (선택) 기대/실적 합계 한 줄 |

**규모**: M (1~3일). 스키마가 바뀌므로 **데이터가 더 쌓이기 전에 하는 편이 싸다.**

### 사용자가 정한 것 (2026-09-02)

1. **금액 단위 = `억원/년`** — 사내에서 쓰는 표기를 그대로 따른다
2. **`기대효과` / `실증효과`** — 실제로 쓰는 용어다 ('실적효과'가 아니라 **실증**효과)
3. **정성 효과는 자유 문장**, 필요하면 엑셀·PPT를 첨부

## 반영 내용 (2026-09-02)

**정량 — front matter 에 숫자로**

```yaml
effect_expected: 1.2      # 기대효과 (억원/년)
effect_verified: 1.45     # 실증효과 — 과제가 끝나야 나오므로 대개 비어 있다
```

숫자로 두어야 목록 정렬과 합계가 된다. `EFFECT_UNIT` 은 `config.py` 한 곳에 두고
화면이 그것을 가져다 쓴다 (단위를 바꿀 일이 생기면 한 줄만 고친다).

**정성 · 근거 — 개요 문서에 서술**

과제 개요 템플릿에 두 절을 더했다. 길어질 수 있고 첨부와 함께 봐야 하는 내용이라 본문이 맞다.

* `## 정성적 효과` — 품질 향상, 리스크 저감, 기술 확보 등
* `## 효과 산출 근거` — 단가 × 물량 × 개선율, 가정, 출처

**개요에 직접 파일을 붙일 수 있게 했다** (`POST /api/projects/{id}/attachments`)
지금까지 첨부는 진행일지와 보고에만 붙었다. 효과 산출 근거(엑셀·PPT)는 특정 진행일지가 아니라
**과제 자체에 딸린 자료**라 붙일 자리가 없었다. 개요 카드에 [📎 파일 첨부] 를 두고
`assets/과제/` 아래에 모은다. 끌어다 놓아도 된다. 올리면 개요 본문 끝에 링크가 붙는다.

**목록 표시**

| 값 | 표기 | 뜻 |
|---|---|---|
| 기대 1.2 · 실증 1.45 | **1.2 → 1.4** (진하게) | 실증까지 확인됨 |
| 기대 5.0 만 | 5 (흐리게) | 아직 실증 전 |
| 둘 다 없음 | — | 미입력 |

정렬에 **효과 큰 순**을 더했다. 실증효과가 있으면 그것을, 없으면 기대효과를 기준으로 본다
(기대 9.0 이었지만 실증 1.0 인 과제는 1.0 자리에 놓인다). 효과를 안 적은 과제는 맨 뒤로 —
0으로 취급하면 실제로 효과가 0인 과제와 섞인다.

과제 상세 요약 바에도 `효과 억원/년 | 1.2 → 1.4` 로 한 칸을 더했다.

**비어 있는 것과 0은 다른 뜻이다.** 전자는 "아직 안 정했다", 후자는 "효과가 없다".
그래서 폼에서 칸을 비우면 `null` 로 보낸다. 이를 위해 `ProjectUpdate.changes()` 를
`exclude_unset=True` 로 바꿨다 — 보내지 않은 항목만 건너뛰고, 보낸 `null` 은 비우겠다는 뜻으로 받는다.
(전에는 어떤 항목도 지울 수 없었다)

**검증**

* 테스트 10건 추가, 전체 **135건 통과**. 왕복 저장, 기대/실증 분리, 빈 값과 0의 구분,
  값 지우기, 음수 거부, 효과순 정렬, 손으로 고친 파일에 숫자가 아닌 값이 들어와도 색인이
  멈추지 않는지, 과제 단위 첨부까지 다룬다.
* 스키마 3 → 4. **기존 vault 로 그대로 올려** 색인이 자동으로 다시 만들어지고
  과제 8건이 그대로 읽히는 것을 확인했다.
* 화면에서 목록 열·정렬·요약 바·입력 폼을 눈으로 확인했다.
* 개요 첨부는 **끌어다 놓기 경로로 끝까지 확인**했다(업로드 → 개요 본문에 링크 추가).
  [파일 첨부] 버튼 경로는 브라우저 자동화로 확인하지 못했는데, **기존 진행일지의
  같은 버튼도 자동화에서는 똑같이 반응하지 않는다** — 도구 쪽 한계이지 결함이 아니다.
  두 버튼은 같은 방식이고 진행일지 쪽은 실사용에서 확인된 경로다.

### 27. 엑셀 표 → 마크다운 표 ✅

엑셀·구글시트에서 셀을 복사하면 클립보드에 **탭으로 나뉜 텍스트**가 담긴다.
붙여넣을 때 그것을 알아보고 마크다운 표로 바꿔 넣는다.
진행일지 · 보고 문서 · 과제 개요 세 편집기 모두에 넣었다.

표로 볼 조건을 좁게 잡았다 — **두 줄 이상 + 모든 줄의 탭 개수가 같을 것.**
열이 하나뿐이면 그냥 여러 줄 텍스트라 건드리지 않는다. 셀 안의 `|` 는 벗어나게 하고
줄바꿈은 `<br>` 로 바꾼다. 첫 줄은 머리글로 본다(엑셀에서 대개 머리글부터 잡기 때문).

### 28. 진행일지 서식 ✅

기본 서식은 **`## 내용` · `## 진행` · `## 계획`** 세 줄이다 (2026-09-02 사용자 확정).

빈칸에서 시작하면 무엇을 적을지부터 고민하게 된다. **설정 → 진행일지 서식**에서
공통 서식과 **과제 속성별 서식**을 따로 둘 수 있다.
찾는 순서는 `속성별 → 공통 → 코드의 기본값` 이고, 비우면 한 단계 위로 되돌아간다.
서식이 있는 속성은 선택 목록에 `✓` 로 표시된다.

### 29. 보고 초안 서식 ✅

`## 보고 요약 / 특이사항 및 이슈 / 다음 계획` 이 코드에 박혀 있어 회의체마다 양식이
다르면 매번 손으로 고쳐야 했다. 설정에서 바꿀 수 있게 했다.

`{summary}` 자리에 마지막 보고 이후의 진행일지가 들어간다.
**`{summary}` 가 없으면 진행 내용이 통째로 사라지므로**, 화면에서 경고하고
그래도 저장하면 서버가 기본 서식으로 되돌린다(조용히 내용을 잃는 것보다 낫다).

### 30. 지난 기록 이어쓰기 ✅

기록 카드마다 **[이어쓰기]** 를 뒀다. 누르면 그 기록의 내용을 담아 **오늘 날짜로**
새 편집기가 열린다. 연속된 시험·측정에서 같은 표를 매번 다시 그리지 않아도 된다.

### 31. 수행 이력에 보고 시점 마커 ✅

**설계 문서 5.1 에 적어 놓고 빠뜨렸던 것.** 진행일지마다 "어느 확정 보고에 담겼는지"를
함께 내려 주고(`reported_on`), 타임라인에 `── 여기까지 2026-08-25 보고함 ──` 선을 긋는다.
기록이 최신순이므로 **선 위는 미보고, 아래는 보고 완료**다. 목록을 보는 것만으로
미보고 분량이 눈에 들어온다. 작성 중인 초안은 세지 않는다 — 아직 보고한 것이 아니다.

### 32. 삭제 복구 화면 ✅

지금까지 지운 것은 `.trash/` 로 옮겨졌지만 **어디서 왔는지가 남지 않아**,
되돌리려면 탐색기로 폴더 구조를 짚어 가며 손으로 옮겨야 했다.

옮길 때마다 `.trash/manifest.jsonl` 에 한 줄씩 적는다 — 무엇을, 언제, 어디서.
되돌리기는 그 줄을 거꾸로 읽는 일이다. JSONL 인 이유는 **덧붙이기만 하면 되기 때문**이다.
중간에 멈춰도 앞선 줄은 멀쩡하고, 한 줄이 깨져도 그 줄만 건너뛴다.

* 과제 · 진행일지 · 보고 문서 · 첨부 네 가지 모두 되돌린다.
* **덮어쓰지 않는다.** 지운 자리에 새 기록이 생겼으면 `-복구` 를 붙여 옆에 놓는다.
* 이 기능이 생기기 전에 지운 항목도 **숨기지 않고** 보여 준다(되돌리기는 안 되고 `수동` 표시).
  되돌리지는 못해도 무엇이 들어 있는지는 알아야 한다.
* `trash_name` 은 사용자가 보내는 값이라 보관함 밖을 가리키지 못하게 막고, 테스트로 고정했다.

### 33. 태그 자동완성 ✅

태그 칸은 쉼표로 여러 개를 적는 자리라 `<datalist>` 로는 두 번째 태그부터 도움이 안 된다.
**입력칸 아래에 쓰던 태그를 칩으로 보여 주고, 누르면 덧붙는다.** 이미 고른 것은 빼고 12개까지.
과제 등록·수정과 진행일지 편집기 양쪽에 넣었다.

## 35. 보고 완료 마커를 어디에 그을지 — 기준 재검토

**접수**: 2026-09-02 (사용자) · **상태**: 내일 논의

31번을 넣을 때 기준을 **"그 기록이 확정 보고에 담겼는가"** 로 잡았다.
동작은 하지만, 기준을 정하지 않고 만든 부분이 있어 다시 볼 필요가 있다.

**지금 규칙**
* 기록마다 그것이 담긴 **가장 이른 확정 보고**의 날짜를 붙인다.
* 목록은 날짜 내림차순이고, 그 값이 바뀌는 지점마다 선을 긋는다.
* 선 위는 미보고, 아래는 보고 완료.

**따져 볼 것**

1. **뒤늦게 쓴 지난 날짜 기록.** 8/25 보고를 확정한 뒤 8/20자로 기록을 추가하면,
   날짜순으로는 선 **아래**에 놓이는데 실제로는 **미보고**다.
   지금 구현은 이때 선이 두 번 그어진다. 이게 맞는 표현인지, 아니면
   "미보고" 표시를 기록 자체에 붙이는 편이 나은지.
2. **기준을 보고일로 볼 것인가, 담김 여부로 볼 것인가.** 지금은 담김 여부다.
   보고일 기준으로 하면 1번 경우가 단순해지지만, **보고에서 일부러 뺀 기록**이
   보고한 것처럼 보인다.
3. **여러 보고에 담긴 기록** — 지금은 가장 이른 보고를 쓴다. 마지막 보고가 나을 수도 있다.
4. **보고가 여러 건일 때 선을 몇 개 그을 것인가** — 지금은 보고마다 하나씩.
   보고 이력이 쌓이면 선이 많아진다. 가장 최근 보고 하나만 긋는 편이 나을 수도.
